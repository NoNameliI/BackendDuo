# Правила учебного контента

Действуют для всех курсов платформы. Формат файлов описан в `src/content/schema.ts` и в README («Как добавить урок»); `npm run validate:content` проверяет то, что можно проверить автоматически.

## Главное правило: полнота теории

Новичок должен решить каждое задание, опираясь только на теорию и подсказки.

- Каждая конструкция, использованная в эталонном решении задания (команда, ключевое слово, флаг, функция, оператор, формат литерала, элемент интерфейса тренажёра), объяснена в теории этого урока или одного из предыдущих (порядок уроков — как в `manifest.json`).
- Если сомневаетесь, объясните.
- После изменения уроков пройдите курс по порядку и сверьте каждое решение с уже изученным.

## Структура теории урока

1. Короткий кейс (2–4 предложения): зачем это нужно в реальной работе.
2. По разделу `###` на каждую новую конструкцию:
   - что она делает — одним-двумя простыми предложениями;
   - шаблон синтаксиса в обычном блоке кода с русскими «заглушками» (`SELECT столбец FROM таблица;`);
   - список, объясняющий каждую часть шаблона, порядок частей и пунктуацию;
   - хотя бы один **запускаемый пример** и его настоящий результат.
3. `### Частые ошибки` — 2–4 пункта «так неправильно → так правильно» с причиной.
4. `### Шпаргалка` — краткий список синтаксиса урока.

Длина — сколько нужно: обычно 500–1500 слов. Короткие абзацы, без воды.

## Запускаемые примеры

- Пишутся блоком с меткой `<язык> example` (например, `sql example`); в приложении у них кнопка «Выполнить» и результат под примером.
- Примеры урока выполняются по порядку в отдельной учебной песочнице, стартовое состояние — `setup` первого задания урока, которое его имеет.
- `validate:content` выполняет каждый пример и падает при ошибке.
- Пример учит конструкции, но не совпадает с решением задания: другая таблица, файл, ветка или условие.

## Задания

- Порядок — от простого к сложному. Первое практическое задание решается адаптацией первого примера; в первых мирах у него есть стартовый каркас с пропусками `…` (он не должен проходить проверку).
- Условие называет все исходные объекты (таблицы и их столбцы, файлы, ветки) и точно описывает ожидаемый результат.
- Подсказка 1 отсылает к разделу теории по его заголовку; последняя — шаблон с пропусками, а не готовое решение.
- Данные детерминированы; порядок результата задаётся однозначно.
- `choice` и `review`: 3–4 варианта, разбор объясняет и верный, и неверные ответы.

## Стиль

Обращение на «вы», короткие предложения, без восклицательных знаков в теории и без эмодзи. Ключевые слова и идентификаторы — в `коде`. Никаких упоминаний о том, как и чем создавался текст.

## Курс Git: формат заданий

- Движок курса — `"engine": "git"`. Песочница — учебная модель Git (`docs/engine-differences.md`).
- Задание: блок ```` ```sh setup ```` (команды подготовки, можно с `cat > файл <<'EOF'`) и ```` ```sh solution ```` (команды эталона по одной в строке). Подготовка заканчивается в папке, где ученик начнёт работать; проверка смотрит репозиторий этой папки (или `check.repo`).
- Типы:
  - `graph` — история: ветки (по умолчанию все ветки эталона), теги, положение HEAD; `messages: "exact"` требует точных сообщений коммитов — тогда условие называет их дословно, иначе `"ignore"`;
  - `worktree` — файлы рабочей папки, индекс и неотслеживаемые файлы (`files`, `index`, `untracked`);
  - `commands` — набранные команды: `require` (успешно выполненная команда подходит под регулярное выражение) и `forbid`, у каждого правила своё сообщение ученику;
  - `hosting` — учебный хостинг: репозитории и форки, ветки, pull/merge request и их состояние, задачи, релизы, защита веток;
  - `ci` — исход последних запусков CI на ветке (по умолчанию основной).
- Проверка сравнивает состояние ученика с результатом эталона, поэтому лишние команды (`git status`, `git log`) не мешают. `validate:content` требует, чтобы эталон проходил проверку, а одна подготовка — нет.
- Служебные команды подготовки: `hosting flavor github|gitlab`, `hosting create владелец/имя --from папка`, `hosting protect владелец/имя ветка [--approvals N] [--checks]`, `as пользователь команда` (действие от имени коллеги). В условии их не упоминают.
- Примеры теории — ```` ```sh example ````: команды выполняются по порядку в отдельной песочнице и не должны завершаться ошибкой (показать ошибку можно обычным блоком кода с текстом вывода).
- `errors.json` курса Git — список `{ "pattern": "регулярное выражение", "hint": "объяснение" }`: подсказка появляется в терминале под ошибкой git.
- `solutionAfterAttempts` в манифесте: после скольких неудачных проверок можно открыть решение (в Git — 3).

## Курс API: формат заданий

- Движок курса — `"engine": "api"`. Учебные серверы — `courses/api/servers/*.json` (+ `.graphql`, `.proto`), подключаются в манифесте (`servers`), задание ссылается на сервер полем `server`.
- Типы: `request` (запрос из композера), `response` (ответ сервера), `cors` (настройки CORSMiddleware), `graphql`, `proto`, `fastapi`, а также `choice`/`review`.
- Блоки: ```` ```http starter|solution|setup|tests ````, ```` ```graphql starter|solution ````, ```` ```proto starter|solution ````, ```` ```python starter|solution ````, ```` ```json starter|solution ```` (CORS).
- `fastapi`: ученик пишет `main.py`; запросы из ```` ```http tests ```` (через `###`) уходят в эталон и в код ученика, сравниваются код ответа, JSON и заголовки из `check.headers`. `check.code` — правила к тексту кода (`pattern`, `message`, `forbid`). Условие описывает поведение, но тестовые запросы не перечисляет.
- Примеры теории: ```` ```http example ```` (сервер урока), ```` ```graphql example ````, ```` ```proto example ```` (после `###` — строки `Тип {json}` или `Сервис/Метод {json}`), ```` ```python example ```` (код `main.py`, после каждой строки `###` — запрос). Запрос после `### 500` должен уронить обработчик — так показывают ошибку `500`; любое другое падение примера — ошибка контента.

## Курс FastAPI: формат заданий

- Курс `courses/fastapi`, движок `"engine": "api"`, в манифесте `solutionAfterAttempts: 3`. Ученик работает над проектом из нескольких файлов; сервера и `servers` не нужны.
- Блоки кода: ```` ```python starter|solution [path=файл] ````. Без `path` это `main.py`; с `path` — файл проекта (`path=routers/items.py`, `path=tests/test_items.py`), блоки можно смешивать. Задание с одним `main.py` пишется как раньше (курс API не меняется). `entry` в метаданных — модуль с `app` (по умолчанию `main.py`); он должен быть и в заготовке, и в решении.
- Неверные решения: ```` ```python wrong id=<имя> [path=] ````. Блок накладывается на файлы решения (заменяет или добавляет только перечисленные); несколько блоков с одним `id` — один вариант. Проверка обязана отклонить каждый такой вариант. Поле `wrong` — необязательные пояснения `{ "<имя>": "почему неверно" }`; у каждого пояснения должен быть блок.
- Мутанты (только `pytest`): ```` ```python mutant id=<имя> [path=] ```` — решение приложения с намеренной ошибкой. Для каждого мутанта обязательно описание в `mutants` (его увидит ученик). Мутанты трогают только код приложения, не `tests/`.
- Метаданные для всех типов: `entry`, `packages` (группы из `public/pyodide/groups.json`: client, pytest, db, bcrypt, multipart, jwt, settings; заданиям с `tests/` и типу `pytest` client и pytest добавляются сами), `tree` (дерево файлов; по умолчанию включено, если файлов больше одного), `readonly` (файлы только для чтения: редактор их не меняет, а проверка берёт копии из решения).
- Типы:
  - `fastapi` — скрытые запросы ```` ```http tests ```` (через `###`) уходят в проект ученика и в эталон на всём проекте (жизненный цикл и база включены);
  - `fix-bug` — то же, но заготовка — сломанный проект; заготовка обязана не проходить проверку, а упавший тест или неверный ответ должны указывать на ошибку. Метка в интерфейсе: «Найдите и исправьте ошибку»;
  - `refactor` — поведение как у эталона, плюс автоматически совпадающий набор маршрутов (метод и путь в `/openapi.json`) и правила `check.static` о структуре кода;
  - `pytest` — тесты ученика (файлы в `tests/`) запускаются на эталонном приложении (файлы решения вне `tests/`): все проходят, их не меньше `check.minTests` (по умолчанию 1), а на каждом мутанте хотя бы один падает. Иначе: «Тесты не заметили ошибку: …» (не больше двух);
  - `openapi` — `/openapi.json` ученика сравнивается с эталонным: набор маршрутов всегда, `check.compare` добавляет `operationId`, `tags`, `summary`, `responses` (коды ответов), `params` (имя, место, обязательность), `schemas` (имена, поля, обязательные поля);
  - `static` — только правила `check.static` и `check.code`, запросов нет.
- `check.static` — список правил, каждое можно снабдить своим `message`. Код разбирается модулем `ast` и не выполняется. Правила: `uses {name, file?}`, `imports {module, name?}`, `no-blocking-in-async {calls?, file?}` (по умолчанию `time.sleep`, `requests.*`, `httpx.Client`), `router {file}` (в файле есть `APIRouter` с маршрутом, а входной модуль вызывает `include_router`), `response-model-hides {field}`, `no-literal-secret {names}`, `pattern {regex, forbid?}`. Статические правила проверяются первыми и останавливают проверку при ошибке. `check.code` — прежние правила с регулярными выражениями.
- `validate:content` требует: решение проходит свою проверку (у `pytest` — его тесты проходят и ловят каждого мутанта), заготовка и каждый `wrong` не проходят, имена мутантов и описаний совпадают, `packages` есть в `groups.json`, примеры теории выполняются. Теоретический `python example` остаётся однофайловым (`main.py` и запросы после `###`); многофайловый код в теории — обычный блок `python` с путём в строке перед ним.
