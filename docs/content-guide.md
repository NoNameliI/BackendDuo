# Правила учебного контента

Действуют для всех курсов платформы. Формат файлов описан в `src/content/schema.ts` и в README («Как добавить урок»); `npm run validate:content` проверяет то, что можно проверить автоматически.

## Главное правило: полнота теории

Новичок должен решить каждое задание, опираясь только на теорию и подсказки.

- Каждая конструкция, использованная в эталонном решении задания (команда, ключевое слово, флаг, функция, оператор, формат литерала, элемент интерфейса тренажёра), объяснена в теории этого урока или одного из предыдущих (порядок уроков — как в `manifest.json`).
- Если сомневаетесь, объясните.
- После изменения уроков пройдите курс по порядку и сверьте каждое решение с уже изученным.

## Структура теории урока

1. Короткий кейс (2–4 предложения): зачем это нужно в реальной работе.
2. По разделу `###` на каждую новую конструкцию:
   - что она делает — одним-двумя простыми предложениями;
   - шаблон синтаксиса в обычном блоке кода с русскими «заглушками» (`SELECT столбец FROM таблица;`);
   - список, объясняющий каждую часть шаблона, порядок частей и пунктуацию;
   - хотя бы один **запускаемый пример** и его настоящий результат.
3. `### Частые ошибки` — 2–4 пункта «так неправильно → так правильно» с причиной.
4. `### Шпаргалка` — краткий список синтаксиса урока.

Длина — сколько нужно: обычно 500–1500 слов. Короткие абзацы, без воды.

## Запускаемые примеры

- Пишутся блоком с меткой `<язык> example` (например, `sql example`); в приложении у них кнопка «Выполнить» и результат под примером.
- Примеры урока выполняются по порядку в отдельной учебной песочнице, стартовое состояние — `setup` первого задания урока, которое его имеет.
- `validate:content` выполняет каждый пример и падает при ошибке.
- Пример учит конструкции, но не совпадает с решением задания: другая таблица, файл, ветка или условие.

## Задания

- Порядок — от простого к сложному. Первое практическое задание решается адаптацией первого примера; в первых мирах у него есть стартовый каркас с пропусками `…` (он не должен проходить проверку).
- Условие называет все исходные объекты (таблицы и их столбцы, файлы, ветки) и точно описывает ожидаемый результат.
- Подсказка 1 отсылает к разделу теории по его заголовку; последняя — шаблон с пропусками, а не готовое решение.
- Данные детерминированы; порядок результата задаётся однозначно.
- `choice` и `review`: 3–4 варианта, разбор объясняет и верный, и неверные ответы.

## Стиль

Обращение на «вы», короткие предложения, без восклицательных знаков в теории и без эмодзи. Ключевые слова и идентификаторы — в `коде`. Никаких упоминаний о том, как и чем создавался текст.

## Курс Git: формат заданий

- Движок курса — `"engine": "git"`. Песочница — учебная модель Git (`docs/engine-differences.md`).
- Задание: блок ```` ```sh setup ```` (команды подготовки, можно с `cat > файл <<'EOF'`) и ```` ```sh solution ```` (команды эталона по одной в строке). Подготовка заканчивается в папке, где ученик начнёт работать; проверка смотрит репозиторий этой папки (или `check.repo`).
- Типы:
  - `graph` — история: ветки (по умолчанию все ветки эталона), теги, положение HEAD; `messages: "exact"` требует точных сообщений коммитов — тогда условие называет их дословно, иначе `"ignore"`;
  - `worktree` — файлы рабочей папки, индекс и неотслеживаемые файлы (`files`, `index`, `untracked`);
  - `commands` — набранные команды: `require` (успешно выполненная команда подходит под регулярное выражение) и `forbid`, у каждого правила своё сообщение ученику;
  - `hosting` — учебный хостинг: репозитории и форки, ветки, pull/merge request и их состояние, задачи, релизы, защита веток;
  - `ci` — исход последних запусков CI на ветке (по умолчанию основной).
- Проверка сравнивает состояние ученика с результатом эталона, поэтому лишние команды (`git status`, `git log`) не мешают. `validate:content` требует, чтобы эталон проходил проверку, а одна подготовка — нет.
- Служебные команды подготовки: `hosting flavor github|gitlab`, `hosting create владелец/имя --from папка`, `hosting protect владелец/имя ветка [--approvals N] [--checks]`, `as пользователь команда` (действие от имени коллеги). В условии их не упоминают.
- Примеры теории — ```` ```sh example ````: команды выполняются по порядку в отдельной песочнице и не должны завершаться ошибкой (показать ошибку можно обычным блоком кода с текстом вывода).
- `errors.json` курса Git — список `{ "pattern": "регулярное выражение", "hint": "объяснение" }`: подсказка появляется в терминале под ошибкой git.
- `solutionAfterAttempts` в манифесте: после скольких неудачных проверок можно открыть решение (в Git — 3).
