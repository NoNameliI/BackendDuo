# Индекс B-Tree

У «Полки» 200 тысяч заказов, и менеджеры жалуются: история заказов клиента открывается секундами. Чтобы понять причину, нужно посмотреть, **как** PostgreSQL выполняет запрос, — это показывает план выполнения. В этом уроке вы научитесь читать план, создавать индексы и проверять, что они действительно используются.

Примеры работают с таблицей `orders (id, customer_id, status, total, created_at)` на 200 000 строк. `status` — одно из значений `new`, `paid`, `shipped`, `cancelled`, `total` — сумма заказа от 99 до 5099 ₽.

```sql example
SELECT id, customer_id, status, total, created_at
FROM orders
ORDER BY id
LIMIT 5;
```

| id | customer_id | status | total | created_at |
|---|---|---|---|---|
| 1 | 7920 | paid | 102.70 | 2024-01-01 00:01:00 |
| 2 | 15839 | shipped | 106.40 | 2024-01-01 00:02:00 |
| 3 | 3758 | cancelled | 110.10 | 2024-01-01 00:03:00 |
| 4 | 11677 | new | 113.80 | 2024-01-01 00:04:00 |
| 5 | 19596 | paid | 117.50 | 2024-01-01 00:05:00 |

### EXPLAIN: план выполнения запроса

Прежде чем выполнить запрос, PostgreSQL выбирает способ его выполнения — **план**. Команда `EXPLAIN` показывает план, но сам запрос не выполняет, поэтому она мгновенна даже на огромной таблице.

```sql
EXPLAIN запрос;
```

- `EXPLAIN` пишут прямо перед обычным `SELECT`, всё остальное в запросе не меняется;
- результат — таблица из одного столбца `QUERY PLAN`, каждая строка — часть плана.

```sql example
EXPLAIN SELECT id, total FROM orders WHERE total > 5000;
```

```text
Seq Scan on orders  (cost=0.00..4027.00 rows=3626 width=10)
  Filter: (total > '5000'::numeric)
```

**Seq Scan** (последовательное сканирование) значит: база читает таблицу `orders` целиком, строку за строкой, и к каждой применяет фильтр `Filter`. Чтобы найти несколько тысяч дорогих заказов, она проверяет все 200 тысяч.

### Как читать план

Каждая строка без отступа или со стрелкой `->` — это **узел** плана, одна операция. Рядом в скобках — оценки планировщика:

- `cost=0.00..4027.00` — **стоимость** в условных единицах. Первое число — сколько стоит получить первую строку, второе — все строки. Единица примерно равна чтению одной страницы таблицы с диска. Это не миллисекунды: стоимость нужна, чтобы сравнивать планы между собой;
- `rows=3626` — сколько строк, по мнению планировщика, вернёт узел. Это оценка по статистике, а не точный подсчёт;
- `width=10` — средний размер строки в байтах;
- строки с отступом под узлом — его детали: `Filter` — условие, которое проверяется для каждой строки, `Index Cond` — условие, по которому ищут в индексе, `Sort Key` — по чему сортируют.

Узлы вложены друг в друга: у узла со стрелкой `->` есть родитель выше. План читают изнутри наружу: самый вложенный узел выполняется первым и передаёт строки родителю. Стоимость верхнего узла — стоимость всего запроса.

Главные узлы, которые вы встретите:

| Узел | Что делает |
|---|---|
| `Seq Scan` | читает всю таблицу |
| `Index Scan` | находит строки по индексу и читает только их |
| `Index Scan Backward` | то же, но идёт по индексу в обратном порядке (для `DESC`) |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | сначала собирает по индексу адреса всех подходящих строк, потом читает их из таблицы |
| `Sort` | сортирует строки для `ORDER BY` |
| `Limit` | останавливается, получив нужное число строк для `LIMIT` |

Числа в ваших планах могут немного отличаться от показанных: статистика строится по случайной выборке строк.

У первичного ключа индекс есть всегда: PostgreSQL создаёт его автоматически, как и для `UNIQUE`. Поиск по `id` идёт через него:

```sql example
EXPLAIN SELECT id, total FROM orders WHERE id = 777;
```

```text
Index Scan using orders_pkey on orders  (cost=0.42..8.44 rows=1 width=10)
  Index Cond: (id = 777)
```

Стоимость 8 вместо 4027: база за несколько шагов спустилась по индексу `orders_pkey` к нужной строке.

### CREATE INDEX: создаём индекс

**Индекс B-Tree** — отсортированное дерево значений столбца, где у каждого значения есть ссылка на строку таблицы. Как алфавитный указатель в конце книги: чтобы найти слово, не нужно листать всю книгу. B-Tree — тип индекса по умолчанию.

```sql
CREATE INDEX имя_индекса ON таблица (столбец);
```

- `имя_индекса` — любое уникальное имя. Принято `таблица_столбец_idx`, например `orders_total_idx`;
- `ON таблица` — для какой таблицы строится индекс;
- в скобках — столбец, по значениям которого будет вестись поиск;
- индекс сразу заполняется всеми существующими строками и дальше обновляется сам при каждом `INSERT`, `UPDATE` и `DELETE`;
- запросы менять не нужно: планировщик сам решит, использовать ли индекс.

```sql example
CREATE INDEX orders_total_idx ON orders (total);

EXPLAIN SELECT id, total FROM orders WHERE total > 5000;
```

```text
Bitmap Heap Scan on orders  (cost=72.52..1644.85 rows=3626 width=10)
  Recheck Cond: (total > '5000'::numeric)
  ->  Bitmap Index Scan on orders_total_idx  (cost=0.00..71.61 rows=3626 width=0)
        Index Cond: (total > '5000'::numeric)
```

Читаем изнутри наружу. `Bitmap Index Scan` нашёл в индексе `orders_total_idx` адреса всех заказов дороже 5000. `Bitmap Heap Scan` прочитал из таблицы только эти строки. Стоимость упала с 4027 до 1645. Если подходящих строк совсем мало, база выбирает обычный `Index Scan`, как в примере с `id = 777`.

### Индекс отдаёт строки по порядку: Sort и Limit

Значения в B-Tree уже отсортированы. Поэтому индекс ускоряет не только `WHERE`, но и `ORDER BY`: база читает индекс по порядку и не сортирует строки отдельно. С `LIMIT` она останавливается, как только наберёт нужное число строк.

```sql example
EXPLAIN SELECT id, total FROM orders ORDER BY total DESC LIMIT 5;
```

```text
Limit  (cost=0.42..0.70 rows=5 width=10)
  ->  Index Scan Backward using orders_total_idx on orders  (cost=0.42..11316.31 rows=200000 width=10)
```

`Index Scan Backward` идёт по индексу от самых дорогих заказов. Его полная стоимость 11316 — столько стоило бы прочитать все 200 тысяч строк. Но `Limit` забирает первые пять и останавливает чтение, поэтому весь запрос стоит 0,70.

### Когда индекс не помогает

Индекс выгоден, когда условие отбирает **малую долю** строк. Если подходит большая часть таблицы, прочитать её целиком дешевле, чем прыгать по индексу к каждой строке:

```sql example
EXPLAIN SELECT id, total FROM orders WHERE total > 500;
```

```text
Seq Scan on orders  (cost=0.00..4027.00 rows=183795 width=10)
  Filter: (total > '500'::numeric)
```

Индекс по `total` есть, но под условие подходит 92 % заказов, и планировщик выбрал `Seq Scan`. Это правильное решение, а не ошибка.

У индексов есть и цена. Каждый `INSERT`, `UPDATE` и `DELETE` обновляет не только таблицу, но и все её индексы, а сами индексы занимают место. Создавайте индексы под реальные частые запросы, а не на каждый столбец.

### Какие индексы уже есть и как удалить лишний

Список индексов хранится в системном представлении `pg_indexes`: его можно читать обычным `SELECT`. Удаляет индекс команда `DROP INDEX`.

```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'таблица';
DROP INDEX имя_индекса;
```

- `indexname` — имя индекса, `indexdef` — команда, которой его можно создать заново;
- имя таблицы в `WHERE` пишут в одинарных кавычках, как любой текст;
- `DROP INDEX` удаляет только индекс, данные таблицы не меняются.

```sql example
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
ORDER BY indexname;
```

| indexname | indexdef |
|---|---|
| orders_pkey | CREATE UNIQUE INDEX orders_pkey ON public.orders USING btree (id) |
| orders_total_idx | CREATE INDEX orders_total_idx ON public.orders USING btree (total) |

`USING btree` — тот самый тип по умолчанию. Удалим индекс по `total` и посмотрим запрос, где есть и фильтр, и сортировка:

```sql example
DROP INDEX orders_total_idx;

EXPLAIN SELECT id, total FROM orders
WHERE status = 'cancelled'
ORDER BY total DESC
LIMIT 5;
```

```text
Limit  (cost=4872.65..4872.66 rows=5 width=10)
  ->  Sort  (cost=4872.65..4999.93 rows=50913 width=10)
        Sort Key: total DESC
        ->  Seq Scan on orders  (cost=0.00..4027.00 rows=50913 width=10)
              Filter: (status = 'cancelled'::text)
```

Три шага: прочитать всю таблицу, отобрать 50 тысяч отменённых заказов, отсортировать их все — и только потом взять пять. Обратите внимание: у `Limit` первое число стоимости почти равно второму. Первую строку он получит, только когда сортировка закончится.

### Составной индекс

Индекс можно построить по нескольким столбцам. Индекс `(a, b)` упорядочивает строки сначала по `a`, а при равных `a` — по `b`. Как телефонный справочник: он отсортирован по фамилии, а внутри одной фамилии — по имени.

```sql
CREATE INDEX имя_индекса ON таблица (столбец1, столбец2);
```

- столбцы перечисляют через запятую, порядок важен;
- индекс хорошо ищет по первому столбцу или по первому и второму вместе. По одному второму столбцу он помогает плохо: в справочнике трудно найти всех Иванов, не зная фамилии;
- первым ставьте столбец из условия равенства (`status = 'cancelled'`), вторым — столбец из диапазона или `ORDER BY`. Тогда все нужные строки лежат в индексе подряд и уже в нужном порядке.

```sql example
CREATE INDEX orders_status_total_idx ON orders (status, total);

EXPLAIN SELECT id, total FROM orders
WHERE status = 'cancelled'
ORDER BY total DESC
LIMIT 5;
```

```text
Limit  (cost=0.42..1.17 rows=5 width=10)
  ->  Index Scan Backward using orders_status_total_idx on orders  (cost=0.42..7649.50 rows=50913 width=10)
        Index Cond: (status = 'cancelled'::text)
```

Узлов `Seq Scan` и `Sort` больше нет. База нашла в индексе участок `cancelled`, внутри него строки уже упорядочены по `total`, и она взяла последние пять. Стоимость упала с 4873 до 1,17.

Индекс только по столбцу сортировки тоже убрал бы `Sort`, но фильтр по статусу пришлось бы проверять для каждой строки подряд. Когда подходящих строк мало, например полпроцента, база перебрала бы тысячи лишних, прежде чем набрать нужные.

### Задания на оптимизацию: как работает проверка

В заданиях этого типа в карточке задания показан запрос, который нужно ускорить. Менять его нельзя: вы пишете в редакторе `CREATE INDEX`.

1. Нажмите «Показать план» под запросом. Справа откроется вкладка «План»: дерево узлов, у каждого — `cost` и `rows`, сверху — общая стоимость. `Seq Scan` выделен жёлтым, узлы с индексами — зелёным.
2. Напишите в редакторе `CREATE INDEX …` и нажмите «Выполнить». Индекс появится в песочнице задания.
3. Снова нажмите «Показать план» и убедитесь, что `Seq Scan` исчез, а стоимость упала.
4. Нажмите «Проверить». Проверка создаёт базу заново, выполняет ваш код и строит план запроса.

Решение засчитывается по плану, а не по времени. Условия зависят от задания: в плане нет `Seq Scan` по указанной таблице; таблица читается через индекс; стоимость плана не больше заданной доли исходной. «Упасть хотя бы в 20 раз» значит: новая стоимость не больше 1/20 от стоимости до ваших изменений. Проверка также следит, что запрос возвращает те же строки.

Если вы создали неудачный индекс, удалите его через `DROP INDEX` или нажмите «Сбросить базу». Кнопка «План» на панели редактора строит план для кода из редактора — она нужна, когда переписываете сам запрос.

### SQL-инъекция: значения из формы

Приложение отправляет в базу текст запроса. Опасно собирать этот текст, вклеивая в него ввод пользователя:

```python
status = request.args["status"]          # то, что ввёл пользователь
sql = "SELECT id, status, total FROM orders WHERE status = '" + status + "'"
conn.execute(sql)
```

- `+` склеивает строки, и значение становится частью SQL;
- если ввести `' OR '1' = '1`, кавычка закроет строку, и к условию добавится `OR '1' = '1'` — оно истинно всегда.

Вот какой запрос получит база:

```sql example
SELECT id, status, total
FROM orders
WHERE status = '' OR '1' = '1'
ORDER BY id
LIMIT 3;
```

| id | status | total |
|---|---|---|
| 1 | paid | 102.70 |
| 2 | shipped | 106.40 |
| 3 | cancelled | 110.10 |

Статуса `''` не существует, но запрос вернул все заказы подряд. В форме входа так можно войти под чужим аккаунтом, а через `;` — дописать ещё одну команду.

Правильно передавать значения **параметрами**: в тексте запроса пишут метку (`%s` в Python, `$1` в Node.js), а значение передают отдельно:

```python
conn.execute("SELECT id, status, total FROM orders WHERE status = %s", (status,))
```

Драйвер отправляет значение отдельно от текста запроса, и оно никогда не станет частью SQL. Индекс от инъекции не защищает: это вопрос безопасности, а не скорости.

### Частые ошибки

- `CREATE INDEX ON orders total;` → `CREATE INDEX orders_total_idx ON orders (total);`. Столбцы всегда пишут в скобках. Имя можно опустить, но с именем индекс проще найти и удалить.
- Нажимать «План» на панели редактора, когда там `CREATE INDEX` → нажимайте «Показать план» под целевым запросом. Кнопка редактора строит план для кода из редактора, а `CREATE INDEX` — не запрос.
- `CREATE INDEX … ON orders (total, status)` для `WHERE status = … ORDER BY total` → `(status, total)`. Сначала столбец равенства, потом столбец сортировки.
- Ждать, что индекс ускорит любой запрос → проверяйте план. Если условие отбирает большую часть таблицы, `Seq Scan` — честно лучший вариант.

### Шпаргалка

- `EXPLAIN запрос;` — план без выполнения.
- `cost=первая..все` — условная стоимость; `rows` — оценка числа строк.
- `Seq Scan` — вся таблица; `Index Scan`, `Bitmap Index Scan` + `Bitmap Heap Scan` — по индексу; `Sort` — сортировка; `Limit` — ранняя остановка.
- `CREATE INDEX таблица_столбец_idx ON таблица (столбец);`
- `CREATE INDEX имя ON таблица (столбец_равенства, столбец_сортировки);`
- `SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'таблица';`
- `DROP INDEX имя;`
- Значения из приложения — только параметрами: `WHERE email = %s`.

Таблица `orders (id, customer_id, status, total, created_at)` — 200 000 заказов. Менеджеры разбирают новые заказы по очереди: экран показывает 20 самых старых заказов со статусом `new` (запрос ниже). Новых заказов мало, около половины процента, остальные давно оплачены, отгружены или отменены.

Создайте **один** индекс, по которому PostgreSQL сразу найдёт новые заказы, причём уже в нужном порядке: без чтения всей таблицы (`Seq Scan`) и без отдельной сортировки (`Sort`). Стоимость плана должна упасть хотя бы в 40 раз.

```sql setup
CREATE TABLE orders (
  id int PRIMARY KEY,
  customer_id int NOT NULL,
  status text NOT NULL,
  total numeric(10, 2) NOT NULL,
  created_at timestamp NOT NULL
);
INSERT INTO orders
SELECT g,
       (g * 7919) % 20000 + 1,
       CASE
         WHEN g % 200 = 0 THEN 'new'
         WHEN g % 10 = 1 THEN 'cancelled'
         WHEN g % 10 < 5 THEN 'paid'
         ELSE 'shipped'
       END,
       ((g * 37) % 50000) / 10.0 + 99,
       TIMESTAMP '2024-01-01' + ((g * 7919) % 200000) * INTERVAL '2 minutes'
FROM generate_series(1, 200000) AS g;
```

```sql query
SELECT id, customer_id, total, created_at
FROM orders
WHERE status = 'new'
ORDER BY created_at
LIMIT 20;
```

```sql solution
CREATE INDEX orders_status_created_at_idx ON orders (status, created_at);
```
