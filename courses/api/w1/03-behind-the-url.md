# Что происходит, когда вы открываете адрес

Пользователи пишут в поддержку: «Приложение доставки открывается долго» или «Сайт не находится». Чтобы понять, где искать причину, полезно знать, какой путь проходит запрос от нажатия Enter до картинки на экране. В этом уроке — короткий обзор этого пути без глубоких подробностей, а затем главный инструмент фронтенд- и бэкенд-разработчика: лента запросов и время ответа.

### Путь запроса: общая картина

Вы ввели `https://food.local` и нажали Enter. Дальше происходит шесть шагов:

```text
1. DNS        имя food.local → IP-адрес сервера
2. Соединение браузер «стучится» в сервер по IP-адресу и порту 443
3. TLS        договариваются о шифровании, браузер проверяет сертификат
4. Запрос     браузер отправляет HTTP-запрос: GET /
5. Ответ      сервер присылает код статуса, заголовки и тело (HTML)
6. Отрисовка  браузер строит страницу и догружает всё, что в ней упомянуто
```

Шаги 1–3 — подготовка: найти сервер и установить с ним защищённую связь. Шаги 4–5 вы уже знаете — это HTTP-запрос и ответ из прошлых уроков. Шаг 6 — работа браузера.

### Шаг 1. DNS: имя превращается в адрес

Компьютеры в сети находят друг друга по **IP-адресам** — числам вроде `203.0.113.10`. Людям удобнее имена, поэтому есть **DNS** — служба, которая отвечает на вопрос «какой IP-адрес у имени `api.food.local`?». Это похоже на телефонную книгу: имя → номер.

- Ответ DNS запоминается (кэшируется), поэтому при следующем запросе этот шаг почти ничего не стоит.
- Если имя не нашлось, дальше дело не идёт: браузер пишет что-то вроде «Не удаётся найти IP-адрес сервера», а ответа сервера с кодом статуса нет вовсе.

В тренажёре сервер живёт внутри приложения, и DNS не нужен. Но хост в адресе всё равно решает, куда уйдёт запрос: запрос на другое имя до учебного сервера не дойдёт. Отправьте запрос с полным адресом:

```http example
GET https://api.food.local/restaurants/5
```

### Шаг 2. Соединение

Зная IP-адрес, браузер открывает **соединение** с сервером на нужном порту: `443` для `https`, `80` для `http`. Стороны обмениваются короткими служебными сообщениями («можно?» — «можно» — «начинаем»), и канал готов. Этим занимается протокол **TCP**, подробности его работы для этого курса не нужны.

Если сервер выключен или порт закрыт, браузер сообщит, что не может подключиться. Кода статуса опять не будет: до HTTP дело не дошло.

### Шаг 3. TLS: шифрование и сертификат

Буква `s` в `https` означает, что поверх соединения работает **TLS** — шифрование. На этом шаге:

- сервер показывает **сертификат** — документ, подтверждающий, что это действительно `api.food.local`, а не подделка;
- браузер проверяет сертификат, и стороны договариваются о ключах шифрования.

После этого всё, что идёт по соединению — путь и параметры адреса, заголовки, пароли, тело, — зашифровано. Открытым остаётся только имя сервера: без него запрос не доставить. По `http` те же данные идут открытым текстом, и их может прочитать любой, через чьё оборудование проходит запрос. Поэтому API в реальной работе доступны только по `https`. Если сертификат не прошёл проверку, браузер покажет предупреждение и не отправит запрос.

### Шаги 4–5. HTTP-запрос и ответ

Теперь по готовому защищённому каналу идёт обычный HTTP-запрос, а сервер присылает ответ — это то, что вы делали в прошлых уроках. Соединение после ответа не закрывается сразу: следующие запросы к тому же серверу идут по нему же, и шаги 1–3 повторять не нужно.

### Шаг 6. Отрисовка и новые запросы

На адрес сайта сервер обычно отвечает HTML-страницей. Браузер читает её и видит, что ещё нужно: стили (`.css`), код (`.js`), картинки. Каждый такой файл — отдельный запрос. Затем код страницы обращается к API за данными — получает JSON и рисует из него список ресторанов, карточку, корзину.

Так одна открытая страница превращается в десятки запросов. Как именно код страницы отправляет запросы к API, разберём в мире «Фронтенд и бэкенд».

### Лента запросов

Все запросы страницы видны в инструментах разработчика браузера: клавиша `F12`, вкладка **Network** («Сеть»). Каждая строка — один запрос:

```text
Name (путь)                 Method  Status  Type    Time
/                           GET     200     html    48 ms
app.js                      GET     200     script  95 ms
/restaurants?city=Казань    GET     200     fetch   31 ms
/restaurants/9              GET     404     fetch   12 ms
```

- **Name** — путь запроса, **Method** — метод, **Status** — код статуса.
- **Type** — что это: страница, скрипт, картинка или запрос к API из кода страницы (`fetch`).
- **Time** — сколько прошло от отправки запроса до конца ответа.
- Щелчок по строке открывает подробности: заголовки запроса и ответа, тело ответа.

В рабочей области тренажёра такая лента — вкладка **Лента запросов** рядом с панелью «Ответ»: столбцы «Метод», «Путь», «Статус», «Тип» и «Время». Новые запросы появляются сверху. Если запрос не получил ответа (например, ушёл на другой хост), в столбце «Статус» будет «ошибка».

Страница ресторана в приложении доставки делает несколько запросов подряд. В примере их три, разделённых строкой `###`:

```http example
GET /restaurants/2
###
GET /restaurants?cuisine=japanese
###
GET /orders/1
```

### Время ответа

Время в ленте складывается из нескольких частей: дорога по сети туда и обратно, работа сервера (найти данные, посчитать) и передача тела ответа. У самого первого запроса к серверу добавляются шаги 1–3. В браузере подробную разбивку показывает вкладка **Timing** у выбранного запроса: DNS, соединение, TLS, ожидание ответа сервера, загрузка тела.

Ориентиры для API:

- десятки миллисекунд — быстро;
- сотни миллисекунд — терпимо, но пользователь уже замечает задержку;
- больше секунды — медленно: экран ждёт, пользователь нервничает.

Если медленный один запрос, а остальные к тому же серверу быстрые, проблема в нём самом: обычно сервер долго ищет или собирает данные. В тренажёре время ответа видно в ленте и в строке статуса панели «Ответ», например `200 OK 9 мс 312 Б`.

### Частые ошибки

- Видеть «не удаётся найти сервер» и искать ошибку в коде ответа → кода нет: запрос не дошёл до HTTP, проблема на шаге DNS или соединения.
- `http://api.food.local/orders` для API → `https://api.food.local/orders`: без TLS данные идут открытым текстом.
- Считать, что страница — это один запрос → откройте ленту: страница, скрипты, картинки и данные из API — отдельные запросы.
- Винить сеть во всех задержках → сравните время запросов в ленте: если медленный один, причина в нём.

### Шпаргалка

- Путь запроса: DNS → соединение → TLS → HTTP-запрос → ответ → отрисовка.
- DNS: имя хоста → IP-адрес. Соединение — на порт `443` (`https`) или `80` (`http`). TLS: шифрование и проверка сертификата.
- Нет ответа с кодом статуса — проблема до HTTP (DNS, соединение, сертификат). Есть код — читайте его по первой цифре.
- Лента запросов: `F12` → Network; в тренажёре — вкладка «Лента запросов». Столбцы: метод, путь, статус, тип, время.
- Время ответа: десятки мс — быстро, больше секунды — медленно.

Мобильное приложение доставки отправляет запросы только по защищённому соединению. Отправьте запрос и посмотрите на ответ.

```http starter
GET …://api.food.local/…
```

```http solution
GET https://api.food.local/orders/1
```

## task api-slow-request

```json
{
  "type": "response",
  "title": "Самый медленный запрос",
  "server": "food",
  "hints": [
    "Разделы «Лента запросов» и «Время ответа».",
    "Отправьте все три запроса по очереди и сравните столбец «Время» в ленте запросов. Затем снова наберите в композере самый медленный из них.",
    "`GET /…` — путь того запроса, у которого время в ленте самое большое"
  ]
}
```

Главный экран приложения доставки при открытии делает три запроса: `GET /restaurants?city=Казань`, `GET /orders` и `GET /promo`. Пользователи жалуются, что экран грузится долго. Отправьте учебному серверу все три запроса и найдите во вкладке «Лента запросов» тот, что отвечает дольше всех. Оставьте в композере именно этот запрос и нажмите «Проверить».

```http starter
GET /…
```

```http solution
GET /promo
```
