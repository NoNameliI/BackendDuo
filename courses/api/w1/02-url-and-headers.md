# Адрес, параметры и заголовки

Пользователь ищет рестораны в Нижнем Новгороде, и в журнале сервера появляется адрес с непонятными `%D0%9D%D0%B8…`. А фронтенд-разработчик просит: «Посмотри заголовки ответа, там написано, куда переехал список». Чтобы понимать такие разговоры, нужно уметь разбирать адрес на части и читать заголовки запроса и ответа. Этим и займёмся.

### Части адреса

Полный адрес (URL) состоит из нескольких частей, и у каждой своя работа:

```http
схема://хост:порт/путь?имя=значение&имя=значение
```

- **Схема** — как разговаривать с сервером: `https` — по защищённому (зашифрованному) соединению, `http` — без шифрования. После схемы пишут `://`.
- **Хост** — имя сервера: `api.food.local`. По нему клиент находит, куда отправить запрос.
- **Порт** — номер «двери» на сервере, пишется после двоеточия: `:443`. Его почти всегда опускают: у `https` стандартный порт `443`, у `http` — `80`. Адреса `https://api.food.local/restaurants` и `https://api.food.local:443/restaurants` ведут в одно место.
- **Путь** — какой ресурс нужен: `/restaurants`, `/restaurants/2`. Начинается с `/`.
- **Параметры запроса** (query) — после `?`, пары `имя=значение` через `&`. Порядок пар не важен.

Иногда в конце адреса бывает ещё `#раздел` — **фрагмент**. Он нужен только браузеру (прокрутить страницу к разделу), на сервер он не отправляется.

Запрос можно написать и с полным адресом — тогда видны все части сразу:

```http example
GET https://api.food.local/restaurants?cuisine=japanese&city=Казань
Accept: application/json
```

Схема, хост и порт вместе называются **origin** — «откуда» сервер. Если в запросе написан только путь (`/restaurants`), клиент подставляет origin сам: в тренажёре это учебный сервер задания `https://api.food.local`. Стандартный порт можно указать явно — ответ будет тот же:

```http example
GET https://api.food.local:443/restaurants/3
```

### Пробелы и кириллица в адресе

В адресе можно использовать только латинские буквы, цифры и несколько знаков. Всё остальное — пробелы, кириллицу, а также `&`, `=`, `?`, `#` внутри значения — **кодируют**: каждый байт символа записывают как `%` и две шестнадцатеричные цифры.

```text
пробел        → %20 (в параметрах ещё можно +)
М             → %D0%9C (кириллическая буква занимает два байта)
&             → %26
```

- Город `Москва` в параметре превращается в `city=%D0%9C%D0%BE%D1%81%D0%BA%D0%B2%D0%B0`. Сервер раскодирует значение обратно и получит `Москва`.
- Пробел обязательно кодировать: в первой строке запроса `МЕТОД адрес` пробел отделяет метод от адреса, и лишний пробел внутри адреса ломает запрос.
- `&` внутри значения тоже кодируют (`%26`), иначе сервер решит, что начался следующий параметр.

Вот запрос с закодированной Москвой:

```http example
GET /restaurants?city=%D0%9C%D0%BE%D1%81%D0%BA%D0%B2%D0%B0
```

Вручную кодировать не обязательно. Браузер, библиотеки и тренажёр делают это сами: если заполнить параметры во вкладке **Params**, тренажёр закодирует их при отправке, а кириллицу можно писать прямо в адресе. Пробел в значении параметра проще всего записать как `%20` или `+`:

```http example
GET /restaurants?city=Нижний+Новгород&cuisine=italian
```

Сервер получил `city` = `Нижний Новгород` и нашёл итальянский ресторан этого города.

### Заголовки запроса

Заголовки — строки `Имя: значение` после первой строки запроса. В них клиент рассказывает о себе и о том, какой ответ ему нужен.

```http
МЕТОД адрес
Имя-заголовка: значение
```

- Имя и значение разделяет двоеточие, после него обычно пробел.
- Регистр в имени не важен: `Accept`, `accept` и `ACCEPT` — один и тот же заголовок.
- Каждый заголовок — на своей строке, порядок строк не важен.

Три заголовка встречаются особенно часто:

- `Accept` — в каком формате клиент ждёт ответ: `application/json` — JSON, `text/html` — веб-страница.
- `User-Agent` — какая программа отправила запрос: браузер, мобильное приложение, `curl`. Серверы пишут его в журнал, чтобы понимать, кто к ним ходит.
- `Authorization` — «пропуск»: доказательство, что запрос отправил тот, кому можно. Обычно это слово `Bearer` и токен: `Authorization: Bearer demo-token-123`. Как получают и проверяют токены, разберём в мире «Фронтенд и бэкенд».

Например, так мобильное приложение просит карточку ресторана:

```http example
GET /restaurants/2
Accept: application/json
User-Agent: FoodApp/2.4 (Android 14)
```

Сервер доставки не требует пропуска для списка заказов, поэтому заголовок `Authorization` здесь просто ни на что не влияет. Сервер, которому пропуск нужен, без этого заголовка ответил бы `401`.

```http example
GET /orders
Authorization: Bearer demo-token-123
```

### Заголовки ответа

Сервер тоже присылает заголовки — между строкой статуса и телом. Главные из них:

- `Content-Type` — формат тела ответа: `application/json`, `text/html; charset=utf-8` (часть после `;` уточняет кодировку текста).
- `Content-Length` — длина тела в байтах. По ней клиент понимает, где тело кончается. Учебный сервер этот заголовок не присылает, а длину тела тренажёр показывает в строке статуса рядом с временем ответа, например `61 Б`.
- `Location` — адрес, куда смотреть дальше. Его присылают вместе с `201 Created` (где теперь лежит созданная запись) и с кодами `3xx` (куда переехал ресурс).

Создайте заказ и посмотрите на заголовки ответа:

```http example
POST /orders
Content-Type: application/json

{"restaurant_id": 3, "dish": "Чебурек с бараниной", "quantity": 4}
```

Под строкой `201 Created` видно `location: /orders/2` (если вы уже создавали заказы, номер будет больше): новый заказ лежит по этому адресу. Учебный сервер пишет имена заголовков строчными буквами — это нормально, регистр в именах не важен. Заберите заказ по этому адресу:

```http example
GET /orders/2
```

С кодами `3xx` заголовок `Location` говорит, куда переехал ресурс. Ответ выглядит так, а тело у него обычно пустое:

```http
301 Moved Permanently
Location: /новый-путь
```

Браузер, получив такой ответ, сам отправляет запрос по новому адресу. В тренажёре переход делаете вы: читаете `Location` и отправляете запрос туда.

Бывают и заголовки, которые сервер придумал сам, их имена часто начинаются с `x-`. Например, на список ресторанов сервер доставки присылает `x-total-count` — сколько всего записей нашлось. Подробнее о таких заголовках — в мире «REST».

### Где читать заголовки в тренажёре

- В примерах теории заголовки ответа показаны серым под строкой статуса.
- В рабочей области у панели **Ответ** две вкладки: **Тело** и **Заголовки**. На вкладке «Заголовки» — все заголовки ответа, слева имя, справа значение.
- Заголовки своего запроса вы задаёте во вкладке **Headers** композера или строками на вкладке **Как текст**.
- В **Ленте запросов** каждая строка — один отправленный запрос. Щелчок по строке снова показывает его ответ в панели «Ответ».

### Частые ошибки

- `GET /search?q=пицца маргарита` → `GET /search?q=пицца%20маргарита`: пробел в адресе разрывает первую строку запроса на части.
- `?city=Казань?cuisine=japanese` → `?city=Казань&cuisine=japanese`: `?` ставится один раз, дальше параметры разделяет `&`.
- `https//api.food.local/orders` → `https://api.food.local/orders`: после схемы нужно двоеточие и две косые черты.
- Искать новый адрес в теле ответа `301` → он в заголовке `Location`, тело у такого ответа обычно пустое.

### Шпаргалка

- Адрес: `схема://хост:порт/путь?имя=значение&имя=значение#фрагмент`.
- Стандартные порты: `https` — `443`, `http` — `80`; их не пишут. Фрагмент `#…` на сервер не уходит.
- Кодирование: пробел — `%20` или `+`, кириллица — `%D0%…`, `&` в значении — `%26`.
- Заголовки запроса: `Accept` — какой формат нужен, `User-Agent` — кто спрашивает, `Authorization` — пропуск.
- Заголовки ответа: `Content-Type` — формат тела, `Content-Length` — длина тела в байтах, `Location` — куда смотреть дальше.
- Имена заголовков не зависят от регистра. В тренажёре: панель «Ответ» → вкладка «Заголовки».

## task api-url-parts

```json
{
  "type": "request",
  "title": "Адрес целиком",
  "server": "food",
  "hints": [
    "Раздел «Части адреса».",
    "Схема, хост и путь пишутся подряд: `https`, затем `://`, имя сервера и путь. Параметры — после `?`, между ними `&`. Формат ответа задаёт заголовок `Accept`.",
    "`GET https://…/restaurants?cuisine=…&sort=…` и строка `Accept: application/…`"
  ],
  "check": { "headers": ["Accept"] }
}
```

Фронтенд-разработчик просит прислать ему готовый адрес для экрана «Итальянская кухня». Соберите запрос `GET` с полным адресом: схема `https`, хост `api.food.local`, порт стандартный (его не пишите), путь `/restaurants`, параметры `cuisine` со значением `italian` и `sort` со значением `-rating` (сначала с высоким рейтингом). Добавьте заголовок `Accept`, который просит ответ в формате JSON.

```http starter
GET https://api.food.local/…?cuisine=…&sort=…
Accept: …
```

```http solution
GET https://api.food.local/restaurants?cuisine=italian&sort=-rating
Accept: application/json
```

## task api-follow-location

```json
{
  "type": "response",
  "title": "Куда переехал список",
  "server": "food",
  "hints": [
    "Разделы «Заголовки ответа» и «Где читать заголовки в тренажёре».",
    "Ответ `301` означает «ресурс переехал». Новый путь — в заголовке `location` на вкладке «Заголовки» панели «Ответ». К нему добавьте параметр `city`.",
    "`GET /…?city=…` — вместо `/…` путь из заголовка `location`"
  ]
}
```

Старая версия приложения запрашивает список ресторанов по адресу `/v1/restaurants`. Отправьте `GET /v1/restaurants` и найдите в заголовках ответа, куда переехал список. Затем запросите по новому адресу рестораны города `Москва` (параметр `city`): сервер должен ответить `200 OK` и вернуть рестораны Москвы. Оставьте этот запрос в композере и нажмите «Проверить».

```http starter
GET /v1/restaurants
```

```http solution
GET /restaurants?city=Москва
```
