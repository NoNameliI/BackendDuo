# Списки, ошибки и версии

В каталоге настоящего магазина тысячи товаров. Отдать их одним ответом нельзя: телефон будет долго грузить мегабайты JSON, а покупателю нужны только смартфоны, от дешёвых к дорогим, первые двадцать. Ещё две заботы большого API — чтобы все ошибки выглядели одинаково и чтобы обновление сервера не сломало приложения, которые пользователи давно не обновляли. Этот урок про параметры списков, единый формат ошибок, версии и правило stateless.

### Фильтры

Фильтр оставляет в списке только записи с нужным значением поля. В REST его передают параметром запроса (query) с именем поля:

```
GET /коллекция?поле=значение
GET /коллекция?поле1=значение1&поле2=значение2
```

- `?` начинает параметры, `&` разделяет их.
- `поле` — имя поля записи, по которому фильтруют, например `category_id`.
- `значение` — что должно быть в этом поле. Числа и слова пишутся без кавычек.
- Несколько фильтров действуют вместе: запись попадёт в ответ, только если подходит под все условия.

Товары категории «Аксессуары» (`category_id` равен 3):

```http example
GET /products?category_id=3
```

Оплаченные заказы покупателя 1 — два фильтра сразу:

```http example
GET /orders?customer_id=1&status=paid
```

Заказы покупателя можно получить и вложенным адресом `/customers/1/orders` из первого урока. Оба варианта встречаются. Вложенный адрес подчёркивает принадлежность, фильтр удобнее, когда условий несколько.

### Сортировка

Порядок списка задают параметром `sort` с именем поля:

```
GET /коллекция?sort=поле
GET /коллекция?sort=-поле
```

- `sort=поле` — по возрастанию: от меньшего к большему, от А к Я, от ранней даты к поздней.
- `sort=-поле` — минус перед именем означает убывание.
- `sort` сочетается с фильтрами через `&`.

Аксессуары, сначала самые дорогие:

```http example
GET /products?category_id=3&sort=-price
```

Название параметра — договорённость конкретного API. Встречаются `order_by=price` или `sort=price:desc`. Правило одно: оно описано в документации, и все списки API используют его одинаково. В учебном магазине — `sort` и минус для убывания.

### Пагинация

Пагинация — выдача списка по страницам. В магазине для этого два параметра:

```
GET /коллекция?page=номер_страницы&limit=записей_на_странице
```

- `limit` — сколько записей на одной странице. В учебном магазине от 1 до 100, без параметра — 10.
- `page` — номер страницы, начиная с 1. Без параметра — первая.
- Заголовок ответа `X-Total-Count` — сколько записей всего подходит под запрос. По нему фронтенд рисует номера страниц: страниц `X-Total-Count / limit`, с округлением вверх.

Пагинацию почти всегда используют вместе с сортировкой: без неё «вторая страница» может каждый раз состоять из разных записей. Каталог по возрастанию цены, по 3 товара, первая и третья страницы:

```http example
GET /products?sort=price&page=1&limit=3
###
GET /products?sort=price&page=3&limit=3
```

В заголовках обоих ответов `x-total-count: 8`: страниц три, на последней только два товара. Слишком большую страницу сервер не отдаст — ответит `422`:

```http example
GET /products?limit=500
```

Кроме `page` и `limit` встречаются `offset` (сколько записей пропустить) и курсор (`cursor` — метка «продолжить после этой записи»). Смысл тот же: клиент сам говорит, какой кусок списка ему нужен.

### Единый формат ошибок

Фронтенд должен разбирать ошибки одним кодом, а не отдельно для каждого адреса. Поэтому у API один формат тела ошибки. В FastAPI и в учебном магазине это объект с полем `detail`:

```json
{"detail": "текст ошибки"}
{"detail": [{"type": "вид ошибки", "loc": ["где", "поле"], "msg": "что не так", "input": "что пришло"}]}
```

- `detail` строкой — простая ошибка: `404`, `401`, `409`.
- `detail` списком — ошибки проверки данных (`422`): по одному объекту на каждую проблему.
- `loc` — где ошибка: `["body", "email"]` — поле `email` в теле, `["query", "status"]` — параметр запроса `status`.
- `msg` — описание, `type` — вид ошибки для программы, `input` — значение, которое пришло.

Заказа 50 нет — простая ошибка:

```http example
GET /orders/50
```

Статуса `lost` у заказов не бывает — ошибка проверки параметра, в `loc` указан `status`:

```http example
GET /orders?status=lost
```

Главное правило: **код статуса должен соответствовать результату**. Ответ `200 OK` с телом `{"error": "not found"}` — ошибка проектирования. Клиент, монитор и кэш сначала смотрят на код, видят «всё хорошо» и не замечают сбоя.

### Версии API

Мобильное приложение, выпущенное год назад, до сих пор установлено у части покупателей и ждёт ответ в старом формате. Если сервер переименует поле `name` в `title`, такие приложения сломаются. Поэтому изменения делят на два вида:

- **совместимые** — добавить новое поле или новый адрес. Старые клиенты просто не заметят нового;
- **ломающие** — переименовать или удалить поле, поменять его тип, поменять смысл кода ответа. Для них выпускают новую версию API.

Самый распространённый способ — номер версии первым сегментом пути:

```
/v1/коллекция
/v1/коллекция/идентификатор
```

- `v1` — версия API: буква `v` и номер.
- Остальная часть адреса — как обычно. Старая версия работает, пока ей пользуются клиенты.

Один и тот же товар в первой и второй версиях:

```http example
GET /v1/products/3
###
GET /v2/products/3
```

Во второй версии поле `name` стало `title`, цена превратилась в объект с валютой, а `stock` — в признак `in_stock`. Старое приложение продолжает ходить в `/v1` и ничего не замечает. Версию иногда передают и в заголовке, но в пути её видно сразу — в журнале, в браузере, в документации.

В учебном магазине маршруты есть и без версии (`/products`) — так было проще в первых уроках. Настоящий API обычно выбирает один вариант для всех адресов.

### Stateless: каждый запрос сам по себе

REST-сервер **не хранит состояние разговора** с клиентом (stateless — «без состояния»). Он не помнит, какую страницу вы смотрели, какого покупателя выбрали и предъявляли ли токен минуту назад. Каждый запрос несёт всё нужное сам: токен, фильтры, номер страницы.

- Токен — в заголовке `Authorization` **каждого** запроса.
- Номер страницы, фильтры и сортировка — в параметрах **каждого** запроса.
- Данные в базе (заказы, корзина) — это состояние ресурсов, оно хранится. Не хранится только «память о разговоре».

Адрес `/me` — профиль того, кто прислал запрос. Первый запрос предъявляет токен, второй — нет, и сервер его уже не узнаёт:

```http example
GET /me
Authorization: Bearer demo-token-123
###
GET /me
```

Зачем это нужно: запрос можно отправить на любой из десяти одинаковых серверов, и любой ответит правильно. Не нужно помнить, на каком сервере «живёт» ваш разговор.

### Частые ошибки

- `GET /products/sorted-by-price` → `GET /products?sort=price`: порядок списка — параметр, а не новый адрес.
- `GET /products?page=2` без сортировки → `GET /products?sort=price&page=2&limit=20`: без порядка страницы не определены.
- `200 OK` с телом `{"error": "..."}` → код ошибки (`404`, `409`, `422`) и тело `{"detail": ...}`.
- `GET /orders/next-page` → `GET /orders?page=3`: сервер не помнит, какая страница была предыдущей.

### Шпаргалка

- Фильтр: `?поле=значение`, несколько через `&` — все условия сразу.
- Сортировка: `sort=поле` по возрастанию, `sort=-поле` по убыванию.
- Страницы: `page` (с 1) и `limit`; всего записей — заголовок `X-Total-Count`.
- Ошибки: правильный код и `{"detail": "текст"}` или `{"detail": [{"loc": ..., "msg": ...}]}`.
- Версия: `/v1/...`; новая версия — только для ломающих изменений.
- Stateless: токен и параметры — в каждом запросе.

```json
  "server": "shop",
  "hints": [

    "`GET /products?category_id=…&sort=…`"
  ]
}
```

На странице «Смартфоны» сайт показывает товары категории с идентификатором `2`, от дешёвых к дорогим. Соберите запрос к коллекции `/products`: фильтр по полю `category_id` и сортировка по полю `price` по возрастанию. Других параметров не добавляйте.

```http starter
GET /products?category_id=…&sort=…
```

```http solution
GET /products?category_id=2&sort=price
```

```http starter
GET /products
```

```http solution
GET /products?sort=-price&page=2&limit=3
```
