# Методы и коды статусов

Покупатель в метро нажал «Сохранить адрес», связь пропала, ответа нет. Можно ли приложению молча отправить запрос ещё раз — или покупатель получит два одинаковых заказа? А когда ответ пришёл, по коду статуса фронтенд решает, что показать: «Готово», «Войдите в аккаунт» или «Такой email уже занят». В этом уроке — как выбрать метод для изменения, какие запросы можно повторять и каким кодом отвечать в каждой ситуации.

### PUT и PATCH: заменить или поправить

Оба метода изменяют существующую запись по адресу `/коллекция/идентификатор`, но по-разному.

**PATCH** — частичное изменение: в теле только те поля, которые меняются. Остальные остаются как были.

```
PATCH /коллекция/идентификатор
Content-Type: application/json

{"поле": новое_значение}
```

- `PATCH` — метод частичного изменения.
- `/коллекция/идентификатор` — какую запись менять.
- `Content-Type: application/json` — тело в формате JSON.
- В теле — только изменяемые поля; можно одно, можно несколько через запятую.

На складе прибыли наушники — у товара 5 стало 18 штук:

```http example
PATCH /products/5
Content-Type: application/json

{"stock": 18}
```

Сервер ответил `200 OK` и вернул товар целиком: изменился только `stock`, название и цена прежние.

**PUT** — полная замена: в теле новая версия записи целиком, со всеми полями. Поле, которого нет в теле, не сохранится, поэтому сервер магазина требует все поля товара: `name`, `category_id`, `price`, `stock`.

```
PUT /коллекция/идентификатор
Content-Type: application/json

{"поле1": значение, "поле2": значение, ...все поля записи}
```

```http example
PUT /products/7
Content-Type: application/json

{"name": "Зарядка 65 Вт", "category_id": 3, "price": 2790, "stock": 15}
```

Если отправить `PUT` только с ценой, сервер откажет с кодом `422` и перечислит недостающие поля:

```http example
PUT /products/7
Content-Type: application/json

{"price": 2590}
```

Правило выбора: меняете одно-два поля — `PATCH`; у клиента на руках вся запись целиком (например, форма редактирования со всеми полями) — можно `PUT`.

### Безопасные и идемпотентные методы

Два свойства методов определяют, что можно делать с запросом без опаски.

- **Безопасный** метод ничего не меняет на сервере, только читает. Такой запрос можно отправлять сколько угодно раз.
- **Идемпотентный** метод при повторе даёт то же состояние данных, что и при одном вызове. Повторили — ничего нового не случилось.

| Метод | Безопасный | Идемпотентный | Почему |
|---|---|---|---|
| `GET` | да | да | только читает |
| `PUT` | нет | да | второй раз записывает ту же самую версию |
| `DELETE` | нет | да | после первого раза записи уже нет, после второго — тоже нет |
| `PATCH` | нет | не обязательно | правка «увеличить на 1» при повторе даст другой результат |
| `POST` | нет | нет | каждый вызов создаёт новую запись |

Идемпотентность — про состояние данных, а не про код ответа. Удалим чехол (товар 6) два раза подряд:

```http example
DELETE /products/6
###
DELETE /products/6
```

Первый ответ — `204 No Content`, второй — `404 Not Found`, но итог одинаковый: товара 6 нет. А вот два одинаковых `POST` создают две разные записи — посмотрите на `id` в ответах:

```http example
POST /products
Content-Type: application/json

{"name": "Кабель USB-C", "category_id": 3, "price": 490, "stock": 100}
###
POST /products
Content-Type: application/json

{"name": "Кабель USB-C", "category_id": 3, "price": 490, "stock": 100}
```

Отсюда практическое правило: при обрыве связи `GET`, `PUT` и `DELETE` клиент может повторить автоматически. `POST` повторять вслепую нельзя — можно создать дубль заказа или платежа.

### Успешные ответы: 200, 201, 204 и заголовок Location

- `200 OK` — запрос выполнен, в теле результат: найденная запись, список, изменённая запись.
- `201 Created` — создана новая запись. В теле — она сама с выданным `id`, а в заголовке **`Location`** — её адрес.
- `204 No Content` — выполнено, тело не нужно. Обычный ответ на `DELETE`.

```
201 Created
Location: /коллекция/новый_идентификатор
Content-Type: application/json

{"id": новый_идентификатор, ...поля записи}
```

- `Location` — заголовок ответа: где теперь живёт созданный ресурс. Клиенту не нужно собирать адрес самому.
- Тело `201` — созданная запись целиком, вместе с `id`.

Зарегистрируем покупателя и сразу прочитаем его по адресу из `Location`:

```http example
POST /customers
Content-Type: application/json

{"name": "Дина Соколова", "email": "dina@example.com", "city": "Казань"}
###
GET /customers/4
```

В ответе на `POST` есть заголовок `location: /customers/4` — это и есть адрес из второго запроса.

### Ошибки клиента: какой код выбрать

Коды `4xx` говорят «исправьте запрос». Каждый объясняет, **что именно** не так, и фронтенд реагирует по-разному.

| Код | Когда | Что делает фронтенд |
|---|---|---|
| `400 Bad Request` | запрос в целом некорректен: не разобрать, нарушает правило, которое не сводится к одному полю | показывает общую ошибку |
| `401 Unauthorized` | сервер не знает, кто вы: нет токена или он неверный | отправляет на вход |
| `403 Forbidden` | сервер знает, кто вы, но вам это нельзя | «Недостаточно прав» |
| `404 Not Found` | нет такого адреса или записи с таким `id` | «Не найдено» |
| `409 Conflict` | запрос противоречит текущим данным: например, такой email уже занят | «Такой email уже зарегистрирован» |
| `422 Unprocessable Content` | данные не прошли проверку: нет обязательного поля, не тот тип, число вне диапазона | подсвечивает поля формы |

Разберём их на сервере магазина. Покупателя с номером 99 нет — `404`:

```http example
GET /customers/99
```

Не передан обязательный `email` — `422`, и в ответе указано, какое поле виновато:

```http example
POST /customers
Content-Type: application/json

{"name": "Без почты"}
```

Данные правильные, но email `anna@example.com` уже есть у другого покупателя — `409`:

```http example
POST /customers
Content-Type: application/json

{"name": "Анна Петрова", "email": "anna@example.com"}
```

Чтобы показать `401` и `403`, нужен заголовок **`Authorization`**: в нём клиент передаёт токен — строку, по которой сервер узнаёт пользователя.

```
Authorization: Bearer токен
```

- `Authorization` — имя заголовка.
- `Bearer` — способ передачи: «предъявитель этого токена». Подробно о токенах — в мире «Фронтенд и бэкенд».
- `токен` — у учебного магазина это фиктивный `demo-token-123`, токен обычного покупателя.

Удалять покупателей может только администратор. Без токена сервер не знает, кто вы, — `401`:

```http example
DELETE /customers/3
```

С токеном покупателя сервер вас узнал, но удалять не разрешает — `403`:

```http example
DELETE /customers/3
Authorization: Bearer demo-token-123
```

Запомните пару: `401` — «кто вы?», `403` — «знаю, кто вы, но нельзя».

Про `400` и `422`: оба — ошибки клиента. `422` — когда виноваты конкретные поля данных; FastAPI выбирает его автоматически. `400` — когда запрос плох целиком, его разработчик бэкенда возвращает сам (как — в мире «FastAPI: первые шаги»).

Ещё один код пригодится при отладке: адрес существует, но метод не тот — `405 Method Not Allowed`, а заголовок `Allow` перечисляет разрешённые методы:

```http example
PUT /customers/1
Content-Type: application/json

{"name": "Анна Смирнова", "email": "anna@example.com", "city": "Самара"}
```

### Порядок выбора кода

Когда вы проектируете ответ, задавайте вопросы по порядку:

1. Есть ли такой адрес? Нет — `404`. Адрес есть, но метод не тот — `405`.
2. Знает ли сервер, кто прислал запрос (если это важно)? Нет — `401`.
3. Разрешено ли ему это действие? Нет — `403`.
4. Правильные ли данные? Нет — `422` (или `400`, если запрос плох целиком).
5. Есть ли запись с таким идентификатором? Нет — `404`.
6. Не противоречит ли запрос текущим данным? Противоречит — `409`.
7. Успех: создано — `201` с `Location`, нечего возвращать — `204`, иначе — `200`.

Права проверяют раньше, чем ищут запись: иначе посторонний по ответам `404` и `403` узнал бы, какие записи существуют.

### Частые ошибки

- `PUT /products/7` с одним полем `{"price": 2590}` → для частичного изменения `PATCH`: `PUT` заменяет запись целиком.
- Ответ `200` на создание → `201 Created` и заголовок `Location`: клиент сразу видит, что запись новая, и знает её адрес.
- `403` без токена → `401`: пока сервер не знает, кто вы, говорить о правах рано.
- Автоматический повтор `POST` при обрыве связи → повторяйте только идемпотентные `GET`, `PUT`, `DELETE`.

### Шпаргалка

- `PATCH` — изменить часть полей; `PUT` — заменить запись целиком (все поля).
- Из этих пяти методов безопасный только `GET`. Идемпотентные — `GET`, `PUT`, `DELETE`. `POST` — ни то ни другое.
- `200` — результат в теле; `201` — создано, `Location: /коллекция/id`; `204` — без тела.
- `400` — плохой запрос, `401` — неизвестно кто, `403` — нельзя, `404` — нет записи, `409` — конфликт с данными, `422` — неверные поля.
- `Authorization: Bearer токен` — как клиент представляется серверу.
