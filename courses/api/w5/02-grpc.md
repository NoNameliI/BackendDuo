# gRPC и protobuf

Внутри сервиса доставки работают десятки программ: одна принимает заказы, другая считает цену, третья ищет курьера. Они вызывают друг друга тысячи раз в секунду, и каждый лишний байт и каждая лишняя миллисекунда складываются в деньги. Для такого общения часто выбирают **gRPC**: клиент вызывает метод другого сервиса как обычную функцию, а данные идут в компактном двоичном формате **Protocol Buffers** (коротко protobuf). В этом уроке вы опишете сообщения и сервисы в файле `.proto` и вызовете методы учебного сервера.

### HTTP/2 в одну фразу

gRPC работает поверх **HTTP/2** — второй версии HTTP, где по одному соединению одновременно идёт много запросов и ответов, а заголовки сжимаются; для вас это значит «быстрее и можно передавать потоки сообщений». Методы, адреса и коды статусов вы уже знаете, только в gRPC их скрывает библиотека: вы вызываете метод, а она сама отправляет `POST /пакет.Сервис/Метод`.

### Protocol Buffers: схема сообщения

Данные в gRPC передаются **сообщениями**. Форму каждого сообщения заранее описывают в файле `.proto`:

```proto
syntax = "proto3";
package пакет;

message Имя {
  тип имя_поля = номер;
  repeated тип список = номер;
}
```

- `syntax = "proto3";` — версия языка, первая строка файла.
- `package` — пространство имён, чтобы имена сообщений разных сервисов не путались.
- `message` — описание одного сообщения; внутри фигурных скобок — поля.
- Поле: тип, имя, знак `=`, **номер поля** и точка с запятой. Частые типы: `int32` (целое число), `double` (дробное), `string` (строка), `bool` (да/нет).
- `repeated` перед типом — список значений этого типа.
- Номера полей уникальны внутри сообщения и начинаются с 1.
- Тип поля может быть другим сообщением: `repeated Restaurant restaurants = 1;` — список ресторанов.

Номер — главное в поле. По сети уходят не имена, а номера и значения, поэтому сообщение в protobuf заметно меньше JSON.

```proto example
syntax = "proto3";
package demo;

message Courier {
  int32 id = 1;
  string name = 2;
  bool on_shift = 3;
}
###
Courier {"id": 150, "name": "Алина", "on_shift": true}
Courier {"id": 150, "name": "Алина", "on_shift": false}
```

Строки после `###` в примерах закодированы в байты. В шестнадцатеричном виде видно, что имён полей там нет: только номера, значения и длины. Во второй строке поле `on_shift` вообще не попало в байты. В proto3 значение по умолчанию (`0`, пустая строка, `false`) не передаётся: получатель и так подставит его, если поля нет.

В заданиях с `.proto` справа три вкладки: «Структура» показывает разобранные сообщения и номера полей, «Байты» кодирует значение, записанное в JSON, по выбранному сообщению, «Вызов gRPC» вызывает метод учебного сервера.

### Номера полей и совместимость

Файл `.proto` — договор между сервисами. Его обновляют по частям: сервер уже знает новую версию, а часть клиентов ещё работает со старой. Чтобы ничего не сломалось, соблюдают правила:

- **Добавлять** поле можно, если дать ему новый, ещё не использованный номер. Старый клиент встретит незнакомый номер и просто пропустит его.
- **Менять номер** у существующего поля нельзя. Старый клиент прочитает по прежнему номеру уже другое поле или потеряет значение.
- **Менять тип** поля тоже нельзя: байты одного типа не читаются как другой.
- **Удалять** поле можно, но его номер больше никогда не используют. Чтобы никто не занял его случайно, номер записывают в `reserved`.

```proto
message Имя {
  reserved номер;
}
```

- `reserved` — список номеров, которые больше нельзя выдавать полям; несколько номеров пишутся через запятую.
- Если позже кто-то объявит поле с таким номером, файл не соберётся.

```proto example
syntax = "proto3";
package demo;

message Courier {
  int32 id = 1;
  string name = 2;
  reserved 3;
  string vehicle = 4;
}
###
Courier {"id": 150, "name": "Алина", "vehicle": "велосипед"}
```

Поле `on_shift` удалили, номер `3` закрыли, а новое поле `vehicle` получило свободный номер `4`. Клиент, который ещё знает старую версию, по номеру `3` ничего не найдёт и не перепутает поля.

### Сервис и метод

В gRPC клиент вызывает метод сервиса, как функцию. Сервис описывают в том же `.proto`:

```proto
service ИмяСервиса {
  rpc Метод (СообщениеЗапроса) returns (СообщениеОтвета);
}
```

- `service` — набор методов одного сервиса, внутри фигурных скобок.
- `rpc` — объявление метода. В круглых скобках после имени — сообщение, которое метод принимает, после `returns` — сообщение, которое он возвращает. В конце точка с запятой.
- Метод всегда принимает ровно одно сообщение. Даже если нужен один номер, для него заводят своё сообщение: `message RestaurantRequest { int32 id = 1; }`.
- Сообщение можно объявить в одну строку: поля внутри скобок идут подряд, каждое со своей точкой с запятой.

Вызов уходит по HTTP/2 как `POST /пакет.Сервис/Метод`, в теле — байты protobuf. Результат сообщает не код HTTP, а **gRPC-статус**: `0 OK`, `5 NOT_FOUND` (не найдено), `3 INVALID_ARGUMENT` (неверный запрос), `12 UNIMPLEMENTED` (нет такого метода).

```proto example
syntax = "proto3";
package food;

message Restaurant {
  int32 id = 1;
  string name = 2;
  string city = 3;
  string cuisine = 4;
  double rating = 5;
}
message RestaurantRequest { int32 id = 1; }

service RestaurantService {
  rpc GetRestaurant (RestaurantRequest) returns (Restaurant);
}
###
RestaurantService/GetRestaurant {"id": 2}
```

Строка `Сервис/Метод {json}` после `###` вызывает метод учебного сервера доставки: запрос пишется в JSON, учебная модель сама превращает его в сообщение. Под ответом видно, сколько байт он занял в protobuf и сколько занял бы в JSON.

Учебный сервер выбирает действие по имени метода: `Get` + сущность — найти одну по первому полю запроса, `List` — список, `Watch` или `Stream` — поток, `Create` — создать, `Delete` — удалить. Настоящий сервер выполняет код, который написали программисты.

### Четыре вида вызовов

Простой вызов «одно сообщение туда, одно обратно» называется **unary**. Благодаря HTTP/2 в gRPC есть ещё потоки: слово `stream` перед сообщением значит, что их будет много, одно за другим.

```proto
service ИмяСервиса {
  rpc Обычный (Запрос) returns (Ответ);
  rpc ПотокОтСервера (Запрос) returns (stream Ответ);
  rpc ПотокОтКлиента (stream Запрос) returns (Ответ);
  rpc ДвустороннийПоток (stream Запрос) returns (stream Ответ);
}
```

- **Unary** — один запрос, один ответ. Как обычный HTTP-запрос: получить ресторан по номеру.
- **Server streaming** — один запрос, а сервер присылает сообщения по мере готовности. Например, клиент подписался на заказы ресторана, и сервер присылает каждый новый заказ.
- **Client streaming** — клиент шлёт много сообщений, сервер отвечает один раз в конце. Например, приложение курьера отправляет координаты каждые несколько секунд, а сервер в конце поездки отвечает итоговым расстоянием.
- **Bidirectional streaming** — обе стороны шлют сообщения независимо друг от друга, пока соединение открыто. Например, чат поддержки: оператор и клиент пишут когда хотят.

Учебная модель умеет вызывать unary и server streaming. Потоки от клиента требуют настоящего соединения, поэтому их вы встретите только в описаниях `.proto`.

```proto example
syntax = "proto3";
package food;

message Restaurant {
  int32 id = 1;
  string name = 2;
  string city = 3;
  string cuisine = 4;
  double rating = 5;
}
message RestaurantsRequest { string city = 1; }

service RestaurantService {
  rpc WatchRestaurants (RestaurantsRequest) returns (stream Restaurant);
}
###
RestaurantService/WatchRestaurants {"city": "Москва"}
```

Сервер прислал отдельные сообщения `Restaurant` — по одному на каждый московский ресторан. Если бы метод был unary, ответом было бы одно сообщение со списком внутри (`repeated`).

### Когда gRPC нужен

- **Внутренние сервисы** обмениваются множеством мелких запросов: protobuf экономит трафик, HTTP/2 — время на соединения.
- **Строгий договор**: по одному `.proto` специальная программа генерирует код клиента и сервера для разных языков (Go, Python, Java). Ошибку в имени поля или типе находят ещё до запуска: код, созданный по `.proto`, знает все поля и их типы.
- **Потоки**: подписки, передача больших данных частями.

Где gRPC неудобен:

- **Браузер** не умеет вызывать gRPC напрямую: нужен промежуточный сервер-переводчик (gRPC-Web). Для публичных API и сайтов чаще выбирают REST или GraphQL.
- **Отладка**: байты не прочитать глазами, как JSON, и `.proto` нужен каждому, кто хочет разобрать ответ.

### Частые ошибки

- `string name = 1;` и `int32 id = 1;` в одном сообщении → разные номера: номер внутри сообщения повторять нельзя.
- `int32 id = 1` без `;` → `int32 id = 1;`: каждое поле и каждый `rpc` заканчиваются точкой с запятой.
- `rpc GetMessage (int32) returns (Message);` → `rpc GetMessage (MessageRequest) returns (Message);`: метод принимает сообщение, а не простой тип.
- `rpc Watch (Request) returns stream (Message);` → `returns (stream Message);`: слово `stream` пишется внутри скобок.

### Шпаргалка

- `syntax = "proto3"; package имя;` — начало файла.
- `message Имя { тип имя = номер; repeated тип список = номер; }` — номера уникальны, начинаются с 1 и не меняются.
- Новое поле — новый номер; удалённое — в `reserved`.
- `service С { rpc М (Запрос) returns (Ответ); }`, вызов — `POST /пакет.С/М`, результат — gRPC-статус.
- Потоки: `returns (stream Ответ)` — от сервера, `(stream Запрос)` — от клиента, оба — двусторонний.

## task beyond-grpc-chat-service

```json
{
  "type": "proto",
  "title": "Сервис сообщений чата",
  "server": "chat",
  "hints": [
    "Разделы «Сервис и метод» и «Четыре вида вызовов».",
    "Каждому методу нужно своё сообщение запроса с одним полем `int32`. У `WatchMessages` слово `stream` стоит перед `Message` внутри скобок `returns`.",
    "```proto\nmessage ChatRequest { int32 … = 1; }\nservice MessageService {\n  rpc GetMessage (…) returns (Message);\n  rpc WatchMessages (…) returns (stream …);\n}\n```"
  ]
}
```

Мессенджер `https://api.chat.local` переводит внутренние сервисы на gRPC. Сообщение `Message` в пакете `chat` уже описано. Допишите файл:

- сообщение `MessageRequest` с одним полем `id` (`int32`, номер 1);
- сообщение `ChatRequest` с одним полем `chat_id` (`int32`, номер 1);
- сервис `MessageService` с двумя методами: `GetMessage` принимает `MessageRequest` и возвращает одно `Message` (unary), `WatchMessages` принимает `ChatRequest` и присылает поток сообщений `Message` (server streaming).

Проверьте на вкладке «Вызов gRPC»: `GetMessage` с `{"id": 2}` возвращает одно сообщение, а `WatchMessages` с `{"chat_id": 1}` присылает по отдельности все сообщения первого чата.

```proto starter
message Message {

  int32 chat_id = 2;
  string author = 3;
  string text = 4;
}

message MessageRequest {
  …
}

  …
}

  …
}
```

```proto solution
syntax = "proto3";
package chat;

message Message {
  int32 id = 1;
  int32 chat_id = 2;
  string author = 3;
  string text = 4;
}

message MessageRequest {
  int32 id = 1;

```
