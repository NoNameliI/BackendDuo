# Мастерская выбора

Сервис доставки растёт. Партнёрам нужен открытый каталог ресторанов, мобильному приложению — десятки разных экранов, сервису цен — тысячи быстрых вызовов в секунду, а экрану заказа — мгновенные обновления статуса. Один стиль API не подходит для всего, и в настоящих продуктах их часто сочетают. В этом уроке вы сравните REST, GraphQL и gRPC на одной задаче, разберётесь, как сервер сам отправляет данные клиенту, и потренируетесь выбирать подход под сценарий.

### Когда нужен push: опрос, SSE и WebSocket

Во всех стилях, которые вы изучили, разговор начинает клиент: спросил — получил ответ. Но часть событий происходит на сервере сама: пришло новое сообщение в чат, курьер забрал заказ. Чтобы клиент узнал о них сразу, серверу нужно отправить данные самому — это называют **push**. Есть три основных способа.

**Опрос (polling)** — клиент повторяет обычный запрос по таймеру, например `GET /orders/1` каждые 10 секунд. Это просто, но новость приходит с опозданием до 10 секунд, а большинство ответов повторяют прошлый: сервер и сеть работают впустую.

**SSE** (Server-Sent Events, события от сервера) — клиент отправляет один обычный HTTP-запрос, а сервер не закрывает ответ и дописывает в него событие за событием:

```http
GET /orders/1/events
Accept: text/event-stream
```

```http
200 OK
Content-Type: text/event-stream

event: status
data: {"status": "cooking"}

event: status
data: {"status": "on_the_way"}
```

- `Accept: text/event-stream` — клиент просит поток событий, а не JSON.
- Ответ приходит один раз с кодом `200` и `Content-Type: text/event-stream`, но тело не заканчивается: сервер дописывает события, пока соединение открыто.
- Каждое событие — строки `поле: значение`, после события пустая строка. `event:` — тип события, `data:` — данные, чаще всего JSON.
- Данные идут только в одну сторону: от сервера к клиенту. Если клиенту нужно что-то отправить, он делает обычный запрос.
- В браузере поток открывает встроенный объект `EventSource`. Если связь оборвалась, он сам переподключается.

**WebSocket** — постоянный двусторонний канал. Он начинается как HTTP-запрос с просьбой сменить протокол, а дальше обе стороны отправляют сообщения когда хотят:

```http
GET /ws
Upgrade: websocket
Connection: Upgrade
```

```http
101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

- Адрес канала пишут со схемой `wss://` (защищённый WebSocket), например `wss://api.chat.local/ws`. Браузер открывает его встроенным объектом `WebSocket`.
- `Upgrade: websocket` — просьба перейти с HTTP на WebSocket. Код `101 Switching Protocols` значит «согласен, переключаемся».
- После этого запросов и ответов больше нет: по тому же соединению клиент и сервер шлют друг другу сообщения, например `{"type": "message", "chat_id": 1, "text": "Привет"}`. Формат сообщений придумывает команда.
- Канал живёт, пока одна из сторон его не закроет. Серверу приходится держать открытыми тысячи соединений, это сложнее, чем отвечать на отдельные запросы.

Учебная среда не моделирует SSE и WebSocket, поэтому здесь они показаны как текст. Похожие возможности есть и в других стилях: в gRPC это server streaming и двусторонний поток из прошлого урока, в GraphQL — подписки (`subscription`), которые обычно работают поверх WebSocket.

### Один запрос тремя способами

Возьмём одну задачу: показать японские рестораны с названием и рейтингом. В REST клиент выбирает адрес и получает то, что решил отдать сервер:

```http example
GET /restaurants?cuisine=japanese
```

В GraphQL клиент отправляет на единственный адрес запрос-форму и получает только названные поля:

```graphql example
{
  restaurants(cuisine: "japanese") {
    name
    rating
  }
}
```

В gRPC клиент вызывает метод, описанный в `.proto`, и получает двоичное сообщение:

```proto example
syntax = "proto3";
package food;

message Restaurant {
  int32 id = 1;
  string name = 2;
  string city = 3;
  string cuisine = 4;
  double rating = 5;
}
message RestaurantsRequest { string cuisine = 1; }
message RestaurantList { repeated Restaurant restaurants = 1; }

service RestaurantService {
  rpc ListRestaurants (RestaurantsRequest) returns (RestaurantList);
}
###
RestaurantService/ListRestaurants {"cuisine": "japanese"}
```

Сравните результаты:

- REST вернул все пять полей каждого ресторана. Зато запрос — обычный `GET` с понятным адресом: его можно открыть в браузере, а ответ можно закэшировать.
- GraphQL вернул только `name` и `rating`. Но все запросы идут как `POST /graphql`, поэтому кэшировать их по адресу, как в REST, не получится.
- gRPC вернул все поля сообщения, но в protobuf ответ заметно меньше JSON. Прочитать байты глазами нельзя, и без `.proto` их не разобрать.

### Несколько полей в одном запросе GraphQL

Экрану часто нужны данные из разных мест сразу. В REST это несколько запросов, а в GraphQL можно перечислить несколько полей верхнего уровня в одном запросе:

```graphql
{
  первое_поле(аргумент: значение) {
    поле
  }
  второе_поле {
    поле
  }
}
```

- Поля верхнего уровня пишутся друг за другом внутри внешних фигурных скобок, у каждого свои аргументы и свой список полей.
- В ответе внутри `data` будет ключ на каждое поле верхнего уровня.

```graphql example
{
  restaurant(id: 2) {
    name
  }
  orders {
    dish
    quantity
  }
}
```

Один запрос — один ответ, а в REST для того же понадобились бы `GET /restaurants/2` и `GET /orders`.

### Сводная таблица

| | REST | GraphQL | gRPC |
|---|---|---|---|
| Как обращаются | много адресов, методы HTTP | один адрес `POST /graphql`, запрос-форма | метод сервиса, `POST /пакет.Сервис/Метод` |
| Формат данных | обычно JSON | JSON | двоичный protobuf |
| Кто выбирает поля | сервер | клиент | сервер (по `.proto`) |
| Договор | по желанию (OpenAPI) | схема обязательна | `.proto` обязателен, по нему генерируют код |
| Браузер | да | да | только через прокси gRPC-Web |
| Кэш HTTP | да, для `GET` | обычно нет | нет |
| Потоки | нет, нужны SSE или WebSocket | подписки поверх WebSocket | встроены (stream) |
| Ошибки | коды статусов HTTP | `200` и поле `errors` | gRPC-статусы |
| Где чаще всего | публичные API, сайты, CRUD | приложения с множеством экранов и связей | общение внутренних сервисов |

И для push:

| | Опрос | SSE | WebSocket |
|---|---|---|---|
| Направление | клиент спрашивает снова и снова | сервер → клиент | в обе стороны |
| На чём работает | обычные запросы | один долгий HTTP-ответ | своё соединение после `101` |
| Когда подходит | данные меняются редко, задержка не важна | уведомления, статусы, ленты | чаты, совместное редактирование, игры |

### Как выбирать

Задайте себе несколько вопросов по порядку:

1. **Кто клиент?** Сторонние разработчики и браузеры — REST: его понимает любой инструмент. Свои внутренние сервисы — можно gRPC.
2. **Насколько разные нужны данные?** Много экранов, каждому свой набор связанных полей, — GraphQL. Несколько простых ресурсов — REST.
3. **Важны ли скорость и размер?** Тысячи вызовов в секунду между сервисами — gRPC.
4. **Нужен ли push?** Только от сервера к клиенту — SSE. В обе стороны — WebSocket. Между сервисами — потоки gRPC.

Если ни один вопрос не перевешивает, начинайте с REST: он проще всего в отладке и знаком каждому. Один продукт может сочетать всё сразу: REST для партнёров, GraphQL для мобильного приложения, gRPC внутри, WebSocket для чата.

### Частые ошибки

- GraphQL для API из трёх простых ресурсов → REST: схема, резолверы и защита от N+1 окупаются только при многих экранах и связях.
- Опрос чата каждую секунду → WebSocket: опрос даёт задержку и тысячи пустых ответов.
- Вызов gRPC прямо со страницы сайта → REST или GraphQL для браузера, gRPC — между сервисами: браузер не умеет говорить на gRPC без прокси.
- WebSocket ради уведомлений, которые идут только от сервера → SSE: он проще и работает поверх обычного HTTP.

### Шпаргалка

- REST — адреса и методы, кэш, понятен всем; GraphQL — клиент выбирает поля, один адрес; gRPC — `.proto`, protobuf, потоки, внутренние сервисы.
- В GraphQL несколько полей верхнего уровня в одном запросе: `{ a { x } b { y } }`.
- Push: опрос — повторять запрос; SSE — `Accept: text/event-stream`, события `data:` от сервера; WebSocket — `Upgrade: websocket`, `101`, сообщения в обе стороны.
- По умолчанию — REST; другой стиль выбирают, когда понятно, какую проблему он решает.

{
  restaurant(id: …) {
    …
  }

  restaurant(id: 4) {

  }
