# GraphQL и gRPC: первое знакомство

Экрану приложения доставки нужны только названия ресторанов и их рейтинг, а `GET /restaurants` отдаёт ещё город, кухню и номер. Мобильному клиенту лишние поля стоят трафика. **GraphQL** решает это иначе: клиент сам перечисляет, какие поля ему нужны. А когда два сервиса внутри компании обмениваются тысячами сообщений в секунду, важен размер каждого байта — там часто выбирают **gRPC** с форматом **Protocol Buffers**. В этом уроке вы попробуете оба подхода на том же учебном сервере доставки.

### GraphQL: один адрес и запрос-форма

У GraphQL-сервера обычно один адрес — `POST /graphql`. Вместо выбора пути клиент отправляет текст запроса, похожий на форму, которую сервер заполняет данными:

```graphql
{
  поле(аргумент: значение) {
    вложенное_поле
    другое_поле
  }
}
```

- Внешние фигурные скобки — весь запрос. Внутри — поле верхнего уровня, например `restaurants`.
- В круглых скобках после поля — аргументы: `имя: значение`. Строки пишутся в двойных кавычках, числа — без кавычек. Несколько аргументов разделяются запятой.
- Во вложенных фигурных скобках перечислены поля, которые нужно вернуть. Каждое поле — с новой строки или через пробел, запятые не нужны.
- Ответ повторяет форму запроса: поля приходят внутри объекта `data` в том же порядке.

Какие поля и аргументы существуют, описывает **схема** сервера. В рабочей области она открыта справа на вкладке «Схема»: `type Restaurant { name: String! ... }` значит, что у ресторана есть поле `name` со строкой, а `!` — что поле всегда заполнено.

```graphql example
{
  restaurants(city: "Казань") {
    name
  }
}
```

В ответ пришли только названия: ни города, ни кухни — их никто не просил. Запрос в рабочей области запускается кнопкой «Выполнить» или `Ctrl+Enter`; в ленте он появится как обычный `POST /graphql` с JSON-телом `{"query": "..."}`.

### Вложенные поля: связанные данные за один запрос

Если поле — объект или список объектов, для него тоже перечисляют поля во вложенных скобках. Так за один запрос можно получить заказы вместе с ресторанами, в которых они сделаны:

```graphql example
{
  orders {
    dish
    restaurant {
      name
    }
  }
}
```

В REST для этого понадобилось бы два запроса: `GET /orders` и `GET /restaurants/1`. Под ответом видно и «Обращений к источнику данных»: для каждого заказа сервер отдельно ищет его ресторан. Когда заказов сотни, таких обращений сотни — это известная проблема N+1, её решают на стороне сервера.

### Ошибки GraphQL

Ошибка в запросе не меняет код ответа: сервер отвечает `200` и кладёт описание в поле `errors`. Тренажёр переводит его на русский под ответом. Частые случаи:

- `У типа Restaurant нет поля «title»` — поля нет в схеме: сверьтесь с вкладкой «Схема».
- `Поле «restaurant» — объект` — для объекта забыли вложенные фигурные скобки со списком полей.
- `Синтаксическая ошибка` — не хватает закрывающей скобки или кавычки.

### Protocol Buffers: схема сообщения

gRPC передаёт данные в двоичном формате **Protocol Buffers** (protobuf). Форму каждого сообщения заранее описывают в файле `.proto`:

```proto
syntax = "proto3";
package пакет;

message Имя {
  тип имя_поля = номер;
  repeated тип список = номер;
}
```

- `syntax = "proto3";` — версия языка, первая строка файла.
- `package` — пространство имён, чтобы имена сообщений разных сервисов не путались.
- `message` — описание одного сообщения; внутри фигурных скобок — поля.
- Поле: тип, имя, знак `=`, **номер поля** и точка с запятой. Частые типы: `int32` (целое число), `double` (дробное), `string` (строка), `bool` (да/нет).
- `repeated` перед типом — список значений.
- Номера полей уникальны внутри сообщения и начинаются с 1.

Номер — главное в поле. По сети уходят не имена, а номера и значения, поэтому сообщение в protobuf заметно меньше JSON. Это же значит, что номер поля нельзя менять после выпуска API: старые клиенты прочитают по этому номеру уже другое поле.

```proto example
syntax = "proto3";
package demo;

message Courier {
  int32 id = 1;
  string name = 2;
  bool on_shift = 3;
}
###
Courier {"id": 150, "name": "Алина", "on_shift": true}
```

Строки после `###` в примерах закодированы в байты: в шестнадцатеричном виде видно, что имён полей там нет.

### gRPC: вызов метода вместо адреса

В gRPC клиент вызывает метод сервиса, как функцию. Сервис описывают в том же `.proto`:

```proto
service ИмяСервиса {
  rpc Метод (СообщениеЗапроса) returns (СообщениеОтвета);
}
```

Запрос уходит по HTTP/2 как `POST /пакет.Сервис/Метод`, а в теле — байты protobuf. У учебного сервера доставки есть сервис `RestaurantService`:

```proto example
syntax = "proto3";
package food;

message Restaurant {
  int32 id = 1;
  string name = 2;
  string city = 3;
  string cuisine = 4;
  double rating = 5;
}
message RestaurantRequest { int32 id = 1; }

service RestaurantService {
  rpc GetRestaurant (RestaurantRequest) returns (Restaurant);
}
###
RestaurantService/GetRestaurant {"id": 2}
```

В заданиях с `.proto` справа три вкладки: «Структура» показывает разобранные сообщения и номера полей, «Байты» кодирует значение, «Вызов gRPC» вызывает метод учебного сервера.

### Частые ошибки

- `{ restaurants }` → `{ restaurants { name } }`: у списка объектов нужно перечислить поля.
- `restaurants(city: Казань)` → `restaurants(city: "Казань")`: строки в аргументах пишутся в кавычках.
- `string name = 1;` и `int32 id = 1;` в одном сообщении → разные номера: номер повторять нельзя.
- `int32 id = 1` без `;` → `int32 id = 1;`: каждое поле заканчивается точкой с запятой.

### Шпаргалка

- GraphQL: `{ поле(аргумент: "строка") { поле1 поле2 } }`, один адрес `POST /graphql`, ошибки — в `errors`.
- Вложенный объект — свои фигурные скобки со списком полей.
- protobuf: `message Имя { тип имя = номер; }`, `repeated` — список, номера уникальны и не меняются.
- gRPC: `service С { rpc М (Запрос) returns (Ответ); }`, вызов идёт как `POST /пакет.С/М`.

  }
}

  }

message Order {
