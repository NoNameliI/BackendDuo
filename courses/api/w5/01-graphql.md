# GraphQL

Экрану приложения доставки нужны только названия ресторанов и их рейтинг, а `GET /restaurants` отдаёт ещё город, кухню и номер. Другому экрану нужны заказы вместе с ресторанами, и в REST это несколько запросов подряд. **GraphQL** решает обе проблемы одним приёмом: клиент сам описывает, какие данные и какой формы ему нужны, а сервер возвращает ровно это. В этом уроке вы прочитаете схему GraphQL-сервера доставки, научитесь писать запросы, передавать переменные и менять данные мутациями.

### Один адрес и запрос-форма

У REST-сервера много адресов: `/restaurants`, `/orders/1`. У GraphQL-сервера обычно один адрес — `POST /graphql`. Вместо выбора пути клиент отправляет текст запроса, похожий на форму, которую сервер заполняет данными:

```graphql
{
  поле {
    вложенное_поле
    другое_поле
  }
}
```

- Внешние фигурные скобки — весь запрос. Внутри — поле верхнего уровня, например `restaurants`.
- Во вложенных фигурных скобках перечислены поля, которые нужно вернуть. Каждое поле — с новой строки или через пробел, запятые не нужны.
- Ответ повторяет форму запроса: данные приходят внутри объекта `data`, поля — в том же порядке, что в запросе.

```graphql example
{
  restaurants {
    name
  }
}
```

В ответ пришли только названия ресторанов: ни города, ни кухни — их никто не просил. В рабочей области запрос запускается кнопкой «Выполнить» или `Ctrl+Enter`. В ленте он появится как обычный HTTP-запрос `POST /graphql` с заголовком `Content-Type: application/json` и телом `{"query": "текст запроса"}`. Ответ — JSON с кодом `200`.

### Схема: какие поля есть

Какие поля можно запросить, описывает **схема** сервера. В заданиях по GraphQL она открыта справа на вкладке «Схема». Схема записана на своём языке:

```graphql
type Тип {
  поле: ТипЗначения!
  список: [ТипЭлемента!]!
  поле_с_аргументами(аргумент: ТипАргумента): ТипЗначения
}
```

- `type Restaurant { ... }` — тип объекта: какие поля есть у ресторана.
- После двоеточия — тип значения поля. Простые типы: `ID` (идентификатор; в ответе приходит строкой, например `"1"`), `String` (строка), `Int` (целое число), `Float` (дробное число), `Boolean` (`true` или `false`).
- `!` после типа — значение всегда есть, `null` не придёт. Без `!` поле может оказаться пустым (`null`).
- `[Order!]!` — список заказов: сам список всегда есть (может быть пустым), и в нём нет `null`.
- Тип поля может быть другим объектом: у заказа есть поле `restaurant: Restaurant` — ресторан, где сделан заказ.
- Два особых типа — точки входа. `type Query` перечисляет поля верхнего уровня для чтения данных, `type Mutation` — для изменения (о мутациях ниже).

На сервере доставки в `Query` четыре поля: `restaurants` (список ресторанов), `restaurant(id: ID!)` (один ресторан по номеру), `orders` (все заказы) и `order(id: ID!)` (один заказ).

```graphql example
{
  orders {
    id
    dish
    quantity
  }
}
```

Обратите внимание: `id` пришёл строкой `"1"`, потому что его тип в схеме — `ID`, а `quantity` — числом, потому что его тип `Int`.

### Аргументы

Поле может принимать **аргументы** — уточнения, что именно вернуть. Они пишутся в круглых скобках сразу после имени поля:

```graphql
{
  поле(аргумент: "строка", другой_аргумент: 10) {
    вложенное_поле
  }
}
```

- Аргумент — `имя: значение`. Несколько аргументов разделяются запятой.
- Строки пишутся в двойных кавычках, числа — без кавычек.
- Какие аргументы есть у поля, видно в схеме: `restaurants(city: String, cuisine: String, limit: Int)` — фильтр по городу, фильтр по кухне и наибольшее число ресторанов в ответе. Тип без `!` значит, что аргумент можно не передавать.
- У `restaurant(id: ID!)` аргумент `id` обязателен: без него сервер не поймёт, какой ресторан нужен. Значение типа `ID` можно записать числом (`id: 3`) или строкой (`id: "3"`).

```graphql example
{
  restaurants(cuisine: "italian", limit: 1) {
    name
    city
  }
}
```

Итальянских ресторанов несколько, но `limit: 1` оставил в ответе только первый.

### Вложенные поля: связанные данные за один запрос

Если поле — объект или список объектов, для него тоже перечисляют поля во вложенных фигурных скобках. Так за один запрос можно получить заказы вместе с ресторанами, в которых они сделаны:

```graphql example
{
  orders {
    dish
    restaurant {
      name
      city
    }
  }
}
```

Связь работает и в обратную сторону: у ресторана есть поле `orders` — его заказы. Уровней вложенности может быть сколько угодно, лишь бы такие поля были в схеме.

### Лишние и недостающие данные

У REST-сервера форму ответа выбирает сервер. Посмотрите, что приходит на запрос одного ресторана:

```http example
GET /restaurants/3
```

Если экрану нужно только название, остальные поля — лишняя нагрузка на сеть. Это называют **over-fetching** — получение лишних данных.

Обратная проблема — **under-fetching**, нехватка данных: одного ответа мало, и клиент делает ещё запросы. Чтобы показать заказ с названием ресторана, REST-клиенту нужны `GET /orders/1` и затем `GET /restaurants/1`. Каждый лишний запрос — ещё одно ожидание сети.

GraphQL снимает обе проблемы: клиент перечисляет только нужные поля и получает связанные данные во вложенных скобках одного запроса. Цена — сложность на стороне сервера: ему нужно уметь собрать любую разрешённую схемой комбинацию полей.

### Проблема N+1

Под каждым ответом GraphQL в рабочей области показано «Обращений к источнику данных» — сколько раз сервер обращался к хранилищу (в настоящем сервере это были бы запросы к базе данных). Запустите пример:

```graphql example
{
  restaurants(city: "Казань") {
    name
    orders {
      dish
    }
  }
}
```

Обращений на одно больше, чем ресторанов в ответе: одно за списком ресторанов и ещё по одному за заказами каждого ресторана. Если ресторанов N, обращений будет N + 1 — отсюда название **проблема N+1**. Запрос выглядит коротким, но при сотне ресторанов сервер сделает сотню с лишним обращений к базе.

На настоящих серверах это решают пакетной загрузкой: сервер собирает номера всех ресторанов и забирает их заказы одним запросом к базе (известная библиотека для этого — DataLoader). Учебный сервер этого нарочно не делает, чтобы проблема была видна.

### Имя операции и переменные

Значения аргументов не обязательно вписывать в текст запроса. Приложение обычно отправляет один и тот же запрос с разными значениями, поэтому значения выносят в **переменные**:

```graphql
query ИмяОперации($переменная: Тип) {
  поле(аргумент: $переменная) {
    вложенное_поле
  }
}
```

- `query` — вид операции: чтение. Короткая запись `{ ... }`, которой вы пользовались до сих пор, — это тоже `query`, просто без имени.
- `ИмяОперации` — имя запроса для людей и для журналов сервера, например `RestaurantsByCuisine`. Его можно не писать, но с ним запрос проще найти.
- В круглых скобках после имени объявляются переменные: знак `$`, имя, двоеточие, тип из схемы. `!` после типа значит, что переменную обязательно передать.
- Внутри запроса переменную подставляют вместо значения: `cuisine: $cuisine`.
- `= значение` после типа — значение по умолчанию: оно используется, если переменную не передали.

Сами значения передаются отдельно от текста запроса, в формате JSON. В рабочей области для этого есть вкладка «Переменные» рядом со «Схемой»: туда пишут объект `{"имя_переменной": значение}` без знака `$`. По сети они уходят в том же теле: `{"query": "...", "variables": {"cuisine": "italian"}}`.

Примеры теории запускаются без вкладки «Переменные», поэтому здесь значение задано по умолчанию:

```graphql example
query RestaurantsByCuisine($cuisine: String = "japanese") {
  restaurants(cuisine: $cuisine) {
    name
    rating
  }
}
```

Если передать `{"cuisine": "caucasian"}`, тот же текст запроса вернёт «Чебуречную».

### Мутации: изменение данных

Чтобы создать, изменить или удалить данные, используют **мутацию**. Она выглядит как запрос, но начинается словом `mutation`, а поле верхнего уровня берётся из типа `Mutation` схемы:

```graphql
mutation ИмяОперации {
  мутация(аргумент: значение) {
    поле_результата
  }
}
```

- `mutation` — вид операции: изменение. Писать его обязательно, иначе сервер будет искать поле в `Query`.
- На сервере доставки три мутации: `createOrder(input: OrderInput!)` создаёт заказ, `updateOrder(id: ID!, quantity: Int!)` меняет количество, `deleteOrder(id: ID!)` удаляет заказ и возвращает `true`.
- Мутация возвращает объект, и в фигурных скобках вы выбираете его поля, как в обычном запросе. Так клиент сразу узнаёт, например, номер созданного заказа.

Аргумент `input` у `createOrder` имеет тип `OrderInput`. В схеме он описан словом `input` вместо `type`: это объект, который клиент передаёт серверу. Значение такого аргумента записывают в фигурных скобках: `{поле: значение, поле: значение}`.

```graphql example
mutation {
  createOrder(input: {restaurant_id: 4, dish: "Карбонара", quantity: 2}) {
    id
    dish
    restaurant {
      name
    }
  }
}
```

Сервер присвоил новому заказу следующий свободный номер и сразу вернул название ресторана. Мутация `updateOrder` меняет количество в заказе с номером `1`:

```graphql example
mutation {
  updateOrder(id: 1, quantity: 3) {
    id
    quantity
  }
}
```

Мутация с переменной пишется так же, как запрос: `mutation Имя($input: OrderInput!) { createOrder(input: $input) { ... } }`. Тогда весь объект заказа лежит во вкладке «Переменные»: `{"input": {"restaurant_id": 4, "dish": "Карбонара", "quantity": 2}}`.

### Ошибки GraphQL

Ошибка в запросе обычно не меняет код ответа: сервер отвечает `200` и кладёт описание в поле `errors`. Тренажёр переводит его на русский под ответом. Частые случаи:

- `У типа Restaurant нет поля «title»` — поля нет в схеме: сверьтесь с вкладкой «Схема».
- `Поле «restaurant» — объект` — для объекта забыли вложенные фигурные скобки со списком полей.
- `Полю «restaurant» нужен аргумент id` — не передан обязательный аргумент (с `!` в схеме).
- `Синтаксическая ошибка` — не хватает закрывающей скобки или кавычки.

### Частые ошибки

- `{ restaurants }` → `{ restaurants { name } }`: у списка объектов нужно перечислить поля.
- `restaurants(city: Казань)` → `restaurants(city: "Казань")`: строки в аргументах пишутся в кавычках.
- `{ createOrder(...) { id } }` → `mutation { createOrder(...) { id } }`: без слова `mutation` сервер ищет поле среди запросов на чтение и не находит.
- Во вкладке «Переменные» `{"$input": ...}` → `{"input": ...}`: знак `$` пишется только в тексте запроса.

### Шпаргалка

- Один адрес `POST /graphql`, тело `{"query": "...", "variables": {...}}`, ошибки — в `errors` при коде `200`.
- Запрос: `{ поле(аргумент: "строка", число: 1) { поле1 поле2 } }`; вложенный объект — свои фигурные скобки.
- Схема: `type`, простые типы `ID String Int Float Boolean`, `!` — не `null`, `[Тип]` — список, `input` — объект-аргумент.
- Переменные: `query Имя($x: Тип!) { поле(арг: $x) { ... } }`, значения — JSON во вкладке «Переменные».
- Мутация: `mutation { createOrder(input: {...}) { id } }`.
- Over-fetching — лишние поля, under-fetching — лишние запросы, N+1 — обращение к базе на каждый элемент списка.

## task beyond-gql-new-order

```json
{
  "type": "graphql",
  "title": "Заказ через переменную",
  "server": "food",
  "hints": [
    "Разделы «Мутации: изменение данных» и «Имя операции и переменные».",
    "Объявите переменную `$input` типа `OrderInput!` после имени операции и передайте её в аргумент `input` мутации `createOrder`. Значения уже лежат во вкладке «Переменные».",
    "`mutation NewOrder($…: …!) { createOrder(input: …) { … … } }`"
  ],
  "variables": { "input": { "restaurant_id": 2, "dish": "Филадельфия", "quantity": 3 } },
  "check": { "state": ["orders"] }
}
```

Приложение отправляет новый заказ одним и тем же текстом мутации, меняя только данные. Во вкладке «Переменные» уже лежит заказ: ресторан `2`, блюдо `Филадельфия`, количество `3` — не меняйте его.

Напишите мутацию с именем операции `NewOrder`: она объявляет переменную `$input` типа `OrderInput!` и передаёт её в аргумент `input` мутации `createOrder`. В ответе запросите номер (`id`) и блюдо (`dish`) созданного заказа. После выполнения на сервере должен появиться ровно один новый заказ.

```graphql starter
mutation NewOrder(…) {
  createOrder(input: …) {
    …
  }
}
```

```graphql solution
mutation NewOrder($input: OrderInput!) {
  createOrder(input: $input) {
    id
    dish
  }
}
```
