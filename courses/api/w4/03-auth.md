# Кто вы: cookie, токены и ключи

Страница «Мои задачи» в трекере показывает задачи текущего пользователя. Но HTTP не помнит прошлых запросов: каждый запрос сервер видит как будто впервые. Значит, клиент должен в каждом запросе предъявлять доказательство, кто он такой. В этом уроке — три главных способа это сделать: cookie сессии, токен в заголовке `Authorization` и API-ключ, а также разница между ответами `401` и `403`.

Все токены и ключи в уроке выдуманы для учебного сервера. Настоящие токены и пароли никогда не вставляйте в учебные задания, чаты и код, который видят другие.

### Аутентификация и авторизация

Это два разных вопроса:

- **Аутентификация** — «кто вы?». Клиент предъявляет cookie, токен или ключ, сервер проверяет, что они настоящие.
- **Авторизация** — «что вам можно?». Сервер уже знает пользователя и решает, разрешено ли ему это действие.

Каждому вопросу — свой код ошибки. Эту пару вы уже встречали в уроке «Методы и коды статусов», здесь разберём её подробнее:

| Код | Когда | Что делать клиенту |
|---|---|---|
| `401 Unauthorized` | не представились или токен неверный, просроченный | войти заново, приложить правильный токен |
| `403 Forbidden` | сервер знает, кто вы, но действие вам запрещено | повторять бесполезно: нужны другие права |

Название `Unauthorized` историческое и сбивает с толку: на деле `401` означает «не аутентифицированы». К ответу `401` сервер добавляет заголовок `WWW-Authenticate` — он подсказывает, какой способ входа ждут, например `Bearer`.

### Сессия и cookie

Классический способ для сайтов. Пользователь вводит логин и пароль, сервер создаёт **сессию** — запись «этот посетитель — Анна» — и отдаёт браузеру её номер в заголовке `Set-Cookie`. Дальше браузер **сам** прикладывает cookie к каждому запросу на этот сайт:

```http
200 OK
Set-Cookie: имя=значение; HttpOnly; Secure

GET /адрес
Cookie: имя=значение
```

- `Set-Cookie` — в ответе сервера: «сохрани это значение».
- `Cookie` — в следующих запросах браузера: «вот что ты мне дал».
- `HttpOnly` — код страницы на JavaScript не может прочитать cookie, только браузер отправляет её сам. Так её не украдёт вредный скрипт.
- `Secure` — cookie уходит только по `https`.

Например, после входа сервер ответил `Set-Cookie: session=demo-session-7; HttpOnly; Secure`, и браузер к каждому запросу трекера добавляет `Cookie: session=demo-session-7`. Сервер находит сессию по номеру и узнаёт пользователя.

Удобно: фронтенду не нужно ничего хранить. Но cookie привязана к браузеру и сайту, а запрос с чужого origin с cookie требует строгих правил CORS — вы видели это в прошлом уроке. Учебный сервер курса cookie не поддерживает; в тренажёре вы будете работать с токенами и ключами.

### Токен в заголовке Authorization

Мобильные приложения, фронтенды на отдельном домене и другие программы чаще используют **токен** — строку, которую сервер выдал после входа. Клиент хранит её сам и прикладывает к каждому запросу в заголовке:

```http
GET /адрес
Authorization: Bearer токен
```

- `Authorization` — стандартный заголовок для учётных данных.
- `Bearer` — схема: «предъявитель этого токена имеет доступ». Между `Bearer` и токеном — один пробел, двоеточия после `Bearer` нет.
- Токен сервер проверяет при каждом запросе. Кто украл токен, тот и «предъявитель» — поэтому токены передают только по `https`.

Во `fetch` это обычный заголовок: `headers: { 'Authorization': 'Bearer demo-token-123' }`.

Отчёт о загрузке команды на учебном сервере доступен только своим. Без токена сервер отвечает `401` с `WWW-Authenticate: Bearer`:

```http example
GET /reports/workload
```

С токеном `demo-token-123` — `200` и данные:

```http example
GET /reports/workload
Authorization: Bearer demo-token-123
```

С выдуманным токеном — снова `401`, но уже с текстом `Invalid authentication credentials`:

```http example
GET /reports/workload
Authorization: Bearer wrong-token
```

### Устройство JWT

Частый формат токена — **JWT** (JSON Web Token). Это три части, разделённые точками:

```
заголовок.данные.подпись
```

- **Заголовок** (header) — как подписан токен, например `{"alg":"HS256","typ":"JWT"}`.
- **Данные** (payload) — сведения о пользователе: `sub` — его номер, `exp` — срок действия, любые свои поля вроде `role`.
- **Подпись** (signature) — контрольная сумма от первых двух частей, вычисленная с секретным ключом, который знает только сервер.
- Первые две части — JSON, записанный в **base64url**: способ записать любые байты буквами, цифрами и знаками `-` и `_`. Это **не шифрование**: кто угодно раскодирует их обратно.

Вот выдуманный учебный токен и его части:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI3IiwibG9naW4iOiJhbm5hIiwicm9sZSI6ImRldmVsb3BlciIsImV4cCI6MTc5ODc2MTYwMH0.demo-signature

заголовок: {"alg":"HS256","typ":"JWT"}
данные:    {"sub":"7","login":"anna","role":"developer","exp":1798761600}
подпись:   demo-signature (заглушка; у настоящего токена здесь длинная строка)
```

`exp` — время в секундах от 1 января 1970 года: `1798761600` — это 1 января 2027 года. После этого момента сервер отвечает на токен `401`.

Как сервер проверяет JWT: заново вычисляет подпись от заголовка и данных своим секретным ключом и сравнивает с той, что в токене. Если кто-то поменял в данных `"role":"developer"` на `"role":"admin"`, подпись перестанет совпадать, и сервер ответит `401`. Поэтому сервер может доверять данным в токене, не храня у себя сессий. Но читать их может любой — пароли и секреты в JWT не кладут.

Учебный сервер знает этот токен по списку и пускает с ним так же, как с `demo-token-123`:

```http example
GET /reports/workload
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI3IiwibG9naW4iOiJhbm5hIiwicm9sZSI6ImRldmVsb3BlciIsImV4cCI6MTc5ODc2MTYwMH0.demo-signature
```

### API-ключ

Когда к API обращается не человек, а программа — скрипт выгрузки, сервис интеграции, бот — ей выдают **API-ключ**: постоянную секретную строку. Чаще всего её передают в заголовке:

```http
GET /адрес
X-API-Key: ключ
```

- `X-API-Key` — распространённое имя заголовка; точное имя назначает каждый API в документации.
- Ключ обычно привязан к проекту или программе, а не к человеку, и живёт долго, пока его не отзовут.
- Ключ — секрет программы, которая обращается к API. В коде фронтенда его хранить нельзя: любой посетитель увидит его в инструментах браузера.

```http example
GET /reports/workload
X-API-Key: test-key-abc
```

### 401 или 403 на практике

Удалять проекты в трекере могут только администраторы. Без токена сервер даже не знает, кто спрашивает, — `401`:

```http example
DELETE /projects/3
```

С токеном обычного разработчика сервер узнал пользователя, но прав на удаление у него нет — `403`:

```http example
DELETE /projects/3
Authorization: Bearer demo-token-123
```

В FastAPI оба ответа выдаёт обработчик через `HTTPException`. Заголовок запроса читают параметром функции с `Header`:

```python
from fastapi import FastAPI, Header, HTTPException

@app.метод("/путь")
def функция(x_api_key: str = Header(default="")):
    ...
```

- `Header` подключается в строке импорта рядом с `FastAPI` и `HTTPException`.
- Имя параметра превращается в имя заголовка: подчёркивания становятся дефисами, регистр не важен. `x_api_key` читает заголовок `X-API-Key`.
- `default=""` — значение, если заголовка нет.
- `KEYS[x_api_key] != "admin"` — обычное сравнение Python: `!=` значит «не равно».

```python example
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()
KEYS = {"test-key-abc": "reader", "test-key-admin": "admin"}

@app.post("/reports/{report_id}/publish")
def publish_report(report_id: int, x_api_key: str = Header(default="")):
    if x_api_key not in KEYS:
        raise HTTPException(status_code=401, detail="Нужен действующий API-ключ")
    if KEYS[x_api_key] != "admin":
        raise HTTPException(status_code=403, detail="Публиковать отчёты может только администратор")
    return {"id": report_id, "published": True}
###
POST /reports/5/publish
###
POST /reports/5/publish
X-API-Key: test-key-abc
###
POST /reports/5/publish
X-API-Key: test-key-admin
```

Без ключа — `401`, с ключом читателя — `403`, с ключом администратора — `200`.

### OAuth2 в двух словах

Кнопка «Войти через …» на сайте — это **OAuth2**: протокол, по которому одна система выдаёт токен для доступа к другой. В нём четыре участника:

- **Пользователь** — владелец данных.
- **Клиент** — приложение, которому нужен доступ, например трекер.
- **Сервер авторизации** — тот, кто проверяет пароль и выдаёт токены (сервис «Войти через …»).
- **Сервер ресурсов** — API, к которому потом идут с токеном.

Как это выглядит: трекер отправляет пользователя на страницу сервера авторизации. Пользователь вводит пароль **там**, а не в трекере, и соглашается дать доступ. Сервер авторизации выдаёт трекеру токен, и трекер обращается к API с `Authorization: Bearer токен`. Главное: пароль пользователя никогда не попадает к клиенту, а токен даёт только те права, на которые пользователь согласился.

### Частые ошибки

- `Authorization: demo-token-123` → не хватает схемы: `Authorization: Bearer demo-token-123`.
- `Authorization: Bearer: demo-token-123` → после `Bearer` пробел, а не двоеточие.
- Токен или ключ в адресе (`/tasks?token=...`) → адреса попадают в журналы серверов и историю браузера; передавайте их в заголовке.
- Считать JWT зашифрованным → его данные читает любой; секреты в нём не храните.
- Отвечать `403` тому, кто не представился → это `401`; `403` — когда пользователь известен, но прав нет.

### Шпаргалка

- `401` — кто вы? (нет или неверный токен); `403` — вам нельзя.
- Cookie: сервер `Set-Cookie: session=...; HttpOnly; Secure`, браузер сам шлёт `Cookie: session=...`.
- Токен: `Authorization: Bearer токен`.
- JWT: `заголовок.данные.подпись`, base64url — не шифрование, подпись защищает от подделки, `exp` — срок действия.
- API-ключ для программ: `X-API-Key: ключ`; во фронтенде не хранить.
- FastAPI: `x_api_key: str = Header(default="")` читает `X-API-Key`.
- OAuth2: сервер авторизации выдаёт клиенту токен, пароль остаётся у сервера авторизации.

## task web-auth-me

```json
{
  "type": "request",
  "title": "Мой профиль",
  "server": "tracker",
  "hints": [
    "Раздел «Токен в заголовке Authorization».",
    "Отправьте `GET /me` без заголовков: сервер ответит `401`. Добавьте во вкладке Headers заголовок `Authorization` со схемой `Bearer`.",
    "`Authorization: Bearer …`"
  ],
  "check": { "headers": ["Authorization"] }
}
```

В шапке трекера показывается имя текущего пользователя. Фронтенд получает его запросом `GET /me`, а сервер отдаёт профиль только с токеном. Соберите запрос `GET /me` с токеном пользователя `demo-token-123` в заголовке `Authorization` по схеме `Bearer`. Отправьте его: сервер должен ответить `200 OK` и вернуть профиль.

```http starter
GET /me
```

```http solution
GET /me
Authorization: Bearer demo-token-123
```
