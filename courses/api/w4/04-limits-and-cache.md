# Ограничения частоты и кэш

Доска трекера обновляется каждые несколько секунд у сотни пользователей сразу, а скрипт интеграции в цикле выгружает задачи без остановки. Сервер тратит силы на одни и те же ответы, а настоящие запросы ждут. Бэкенд защищается двумя приёмами: **ограничивает частоту** запросов и подсказывает клиенту, что ответ можно **взять из кэша**. В этом уроке — оба приёма на уровне идей и заголовков.

### Ограничение частоты (rate limit)

**Rate limit** — правило вида «не больше N запросов за период» для одного клиента. Клиента узнают по токену, API-ключу или адресу.

- Защищает сервер от перегрузки — случайной (ошибка в цикле) или намеренной.
- Делит ресурсы честно: один жадный скрипт не замедляет всех остальных.
- Лимиты описаны в документации API, например: «60 запросов в минуту на ключ, выгрузка — 1 раз в минуту».

Многие API сообщают остаток лимита в заголовках каждого ответа. Имена не стандартные, но встречаются часто:

```http
X-RateLimit-Limit: сколько запросов разрешено за период
X-RateLimit-Remaining: сколько осталось
```

### Ответ 429 и Retry-After

Когда лимит исчерпан, сервер отвечает кодом `429` и говорит, когда приходить снова:

```http
429 Too Many Requests
Retry-After: секунды
```

- `429 Too Many Requests` — «слишком много запросов». Это ошибка клиента (`4xx`): сервер исправен, просто клиент торопится.
- `Retry-After` — через сколько секунд можно повторить запрос.
- Тело обычно короткое, в FastAPI-стиле: `{"detail": "Too Many Requests"}`.

Выгрузку задач на учебном сервере можно делать раз в минуту, и считается, что этот раз уже потрачен: на этот адрес сервер всегда отвечает `429`. Посмотрите на заголовки ответа:

```http example
GET /export/tasks
```

Сервер просит подождать 30 секунд, а `x-ratelimit-remaining: 0` показывает, что запросов не осталось.

### Как клиенту реагировать на 429

Правильная реакция — подождать столько, сколько сказано в `Retry-After`, и повторить. Неправильная — сразу повторять снова и снова: каждый такой запрос тоже считается, и лимит не восстановится. На JavaScript проверка выглядит так:

```javascript
let response = await fetch(адрес);
if (response.status === 429) {
  const seconds = Number(response.headers.get('Retry-After'));
  // подождать seconds секунд, затем повторить запрос
}
```

- `let` — переменная, которой можно потом присвоить новое значение; `const` — нельзя.
- `===` — сравнение «равно» в JavaScript, как `==` в Python.
- `response.headers.get('Имя')` — значение заголовка ответа строкой; регистр имени не важен.
- `Number(...)` — превращает строку `'30'` в число `30`.
- Цикл `while (условие) { ... }` в JavaScript работает как `while` в Python: повторяет тело, пока условие истинно.

Если `Retry-After` нет, клиенты ждут с нарастающей паузой: 1 секунда, 2, 4 и так далее.

### Идея кэша и Cache-Control

**Кэш** — сохранённая копия ответа. Если доска проекта не меняется каждую секунду, браузеру незачем каждый раз скачивать её заново: можно показать сохранённую копию. Сколько копия живёт и где её можно хранить, решает сервер заголовком `Cache-Control`:

```http
Cache-Control: указание, указание
```

- `max-age=60` — копию можно использовать 60 секунд, не спрашивая сервер.
- `private` — хранить только в браузере пользователя: ответ личный.
- `public` — копию могут хранить и общие промежуточные кэши.
- `no-store` — не сохранять вообще: для паролей, токенов и других чувствительных ответов.
- Несколько указаний пишут через запятую: `Cache-Control: private, max-age=60`.

### ETag и ответ 304

Через 60 секунд копия «устарела», но, может быть, доска не изменилась. Чтобы не скачивать её снова, сервер помечает каждый ответ версией — заголовком **ETag**. Вот доска проекта `2`:

```http example
GET /boards/2
```

В ответе `etag: "board-2-v12"` и `cache-control: private, max-age=60`. Когда копия устареет, клиент спросит сервер с **условным запросом**:

```http
GET адрес
If-None-Match: "значение ETag"
```

- `If-None-Match` — «пришли тело, только если версия уже не такая».
- Значение — ETag из прошлого ответа **вместе с кавычками**: кавычки входят в значение.
- Если версия не изменилась, сервер отвечает `304 Not Modified` без тела, и клиент берёт сохранённую копию. Если изменилась — обычный `200` с новым телом и новым ETag.

Так выглядит ответ, когда доска не менялась:

```http
304 Not Modified
ETag: "board-2-v12"
Cache-Control: private, max-age=60
```

`3xx` — не ошибка: сервер говорит «ищите в другом месте», здесь — в собственном кэше. Браузер делает такие проверки для `fetch` сам. Учебный сервер версий не хранит и на условный запрос всё равно отвечает `200` — в тренажёре важно собрать сам запрос правильно.

### Частые ошибки

- На `429` повторять запрос сразу в цикле → ждите `Retry-After` секунд.
- Считать `429` сбоем сервера → это `4xx`: клиент отправляет запросы слишком часто.
- `If-None-Match: board-2-v12` без кавычек → значение ETag копируют целиком: `If-None-Match: "board-2-v12"`.
- `Cache-Control: public` на личных данных (`/me`) → для них `private` или `no-store`.
- Считать `304` ошибкой → это «ничего не изменилось, берите копию».

### Шпаргалка

- Лимит исчерпан: `429 Too Many Requests` + `Retry-After: секунды`; ждать и повторить.
- Остаток лимита: `X-RateLimit-Limit`, `X-RateLimit-Remaining` (имена у разных API бывают другие).
- `Cache-Control: private, max-age=60` — копия в браузере на 60 секунд; `no-store` — не хранить.
- `ETag: "версия"` в ответе → `If-None-Match: "версия"` в запросе → `304 Not Modified` без тела или `200` с новыми данными.
- JavaScript: `response.headers.get('Retry-After')`, `Number(...)`, `===`, `let`, `while`.
