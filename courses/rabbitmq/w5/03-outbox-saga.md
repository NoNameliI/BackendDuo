# Outbox и saga

Сервис заказов сохраняет заказ в базе данных и публикует событие «заказ создан». Это две разные системы, и общей транзакции у них нет. Если база записала заказ, а публикация не удалась, склад ничего не узнает. Если событие ушло, а запись откатилась, склад начнёт собирать несуществующий заказ. Паттерны outbox и saga решают именно такие задачи. Это идеи проектирования, а не команды брокера: песочница их не запускает, поэтому в этом уроке задания — вопросы с вариантами ответа.

### Проблема двойной записи

Сервис должен изменить два хранилища: базу данных и брокер. Выполнить обе операции атомарно нельзя. Порядок «сначала база, потом публикация» теряет событие при сбое между ними. Порядок «сначала публикация, потом база» рассылает событие о том, чего может не оказаться.

Из прошлых уроков вам известны подтверждения издателя (publisher confirms): они говорят, что брокер принял сообщение. Но они не делают запись в базу и публикацию единой операцией.

### Outbox

Outbox («исходящий ящик») — таблица в той же базе данных, где сервис хранит заказы.

```text
транзакция в базе:
  1. записать заказ в таблицу orders
  2. записать событие в таблицу outbox (статус «не отправлено»)
фиксация транзакции

отдельный процесс-ретранслятор:
  3. читает из outbox неотправленные события
  4. публикует их в брокер и ждёт подтверждение
  5. после подтверждения помечает событие отправленным
```

- Шаги 1 и 2 выполняются одной транзакцией базы: либо записаны оба, либо ни одного. Двойной записи нет.
- Ретранслятор публикует событие позже и повторяет попытки, пока брокер не подтвердит приём.
- Если ретранслятор упал между шагами 4 и 5, событие будет опубликовано ещё раз. Поэтому outbox даёт доставку «не меньше одного раза» (at-least-once), но не «ровно один раз».

Отсюда главное следствие: потребитель событий должен быть идемпотентным, то есть повторная обработка того же сообщения не должна менять результат. Напоминание: в первом мире вы включали это свойством потребителя `idempotent`. Обычно для этого в событие кладут уникальный идентификатор, а потребитель запоминает уже обработанные.

В песочнице можно воспроизвести только вторую половину схемы: издатель публикует, брокер подтверждает, потребитель получает дубликат и должен его пережить. Таблицы `outbox` в ней нет.

### Saga

Saga — способ провести бизнес-операцию через несколько сервисов без общей транзакции. Операция разбита на локальные шаги. Каждый сервис выполняет свой шаг в своей базе и публикует событие, по которому действует следующий. Если какой-то шаг не удался, выполняются компенсирующие действия: они отменяют уже сделанное.

Пример: оформление заказа.

1. Сервис заказов создаёт заказ и публикует `order.created`.
2. Сервис склада резервирует товар и публикует `stock.reserved`.
3. Сервис оплаты списывает деньги. При успехе публикует `payment.done`, при отказе — `payment.failed`.
4. По `payment.failed` склад снимает резерв, а сервис заказов отменяет заказ. Это компенсации.

Компенсация не «откатывает» базу, а выполняет новое обратное действие: вернуть резерв, вернуть деньги. Поэтому она должна быть идемпотентной и по возможности не зависеть от того, в каком состоянии остальные сервисы.

Две формы saga:

- Хореография: сервисы реагируют на события друг друга, общего координатора нет. Просто, пока шагов мало. Порядок шагов трудно увидеть целиком.
- Оркестрация: отдельный координатор (оркестратор) говорит каждому сервису, что делать, и сам решает, какие компенсации запускать. Порядок виден в одном месте, но координатор — ещё один сервис.

События саги маршрутизируются обычными средствами брокера. Пример: компенсации получают своим ключом.

```broker example
rabbitmqadmin exchanges declare --name saga --type direct --durable true
rabbitmqadmin queues declare --name stock-compensate --type classic --durable true
rabbitmqadmin queues declare --name orders-cancel --type classic --durable true
rabbitmqadmin bindings declare --source saga --destination-type queue --destination stock-compensate --routing-key payment.failed
rabbitmqadmin bindings declare --source saga --destination-type queue --destination orders-cancel --routing-key payment.failed
rabbitmqadmin publish message --exchange saga --routing-key payment.failed --payload "order 41"
rabbitmqctl list_queues name messages_ready
```

```text
declared exchange 'saga' in virtual host '/'
declared queue 'stock-compensate' in virtual host '/'
declared queue 'orders-cancel' in virtual host '/'
declared a binding from 'saga' to queue 'stock-compensate' with routing key 'payment.failed' in virtual host '/'
declared a binding from 'saga' to queue 'orders-cancel' with routing key 'payment.failed' in virtual host '/'
published the message
name	messages_ready
orders-cancel	1
stock-compensate	1
```

Событие `payment.failed` получили обе очереди: склад снимет резерв, заказ будет отменён. Это обычный direct exchange. Сама логика компенсации живёт в сервисах, а не в брокере.

### Когда что применять

- Outbox нужен, когда событие обязано выйти из сервиса вместе с изменением базы и потеря недопустима.
- Saga нужна, когда операция проходит через несколько сервисов, у каждого свои данные, а общей транзакции нет.
- Оба паттерна требуют идемпотентных потребителей, потому что дубликаты неизбежны.
- Если операция укладывается в одну базу данных, обычная транзакция проще и надёжнее любой саги.

### Частые ошибки

- **Ошибка:** «опубликуем событие внутри транзакции базы». **Верно:** публикация не откатывается вместе с транзакцией, поэтому используйте outbox.
- **Ошибка:** «outbox даёт exactly-once». **Верно:** он даёт «как минимум один раз». Дубликаты гасит идемпотентный потребитель.
- **Ошибка:** «компенсация — это откат базы». **Верно:** компенсация — новое обратное действие, и оно тоже может повториться.
- **Ошибка:** «saga везде». **Верно:** для операции внутри одной базы нужна обычная транзакция.

### Шпаргалка

- Двойная запись в базу и брокер атомарной не бывает.
- Outbox: событие пишется в базу той же транзакцией, ретранслятор публикует и ждёт подтверждение.
- Дубликаты возможны: потребитель идемпотентен.
- Saga: цепочка локальных шагов, при сбое — компенсации. Хореография (события) или оркестрация (координатор).
- Песочница не выполняет outbox и saga: это идеи, а не команды.
