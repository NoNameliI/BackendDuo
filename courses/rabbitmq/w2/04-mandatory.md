# Сообщение без маршрута: mandatory и поиск потерь

Магазин публикует события заказов. На следующий день бухгалтерия жалуется: платежей в её очереди нет, хотя заказы оплачены. Издатель не получил ни одной ошибки, брокер ничего не сообщил. Сообщения не нашли очереди и были отброшены. В этом уроке разберём, что происходит с сообщением без маршрута, как заставить брокер сообщить об этом и как искать причину.

### Три исхода сообщения без маршрута

Сообщение не имеет маршрута, если exchange не нашёл ни одной очереди: нет привязок или ни одна не подошла (другой ключ, другие заголовки). Тогда возможны три исхода.

| Что настроено | Что происходит |
|---|---|
| Ничего (по умолчанию) | Брокер молча отбрасывает сообщение. Издатель не узнаёт об этом. |
| Флаг `mandatory` у издателя | Брокер возвращает сообщение издателю командой `basic.return` с кодом `312` (`NO_ROUTE`). Решает издатель. |
| Alternate exchange у exchange | Брокер отправляет сообщение в запасной exchange (урок 2.3). Для издателя оно доставлено. |

Если настроено и то и другое, побеждает маршрут: сообщение ушло через AE и нашло очередь, значит `basic.return` не будет.

### Флаг mandatory

`mandatory` — свойство публикации, а не exchange и не очереди. Издатель ставит его при отправке каждого сообщения.

- Если маршрут нашёлся, ничего не меняется.
- Если маршрута нет, брокер присылает издателю то же сообщение обратно (`basic.return`, код `312`, текст `NO_ROUTE`). Издателю нужен обработчик возвратов: без него возврат никто не заметит.
- При включённых подтверждениях публикации (мир 3) возврат приходит раньше подтверждения: подтверждение означает лишь, что брокер закончил с сообщением.
- Флаг только сообщает о проблеме. Что делать с сообщением (повторить, записать в журнал, поднять тревогу), решает код издателя.

В консоли лаборатории флаг ставится у каждой публикации `rabbitmqadmin publish message`: если сообщение не нашло очередь, консоль пишет `published the message, but it was not routed to any queue`. Проверки заданий-маршрутизаций тоже публикуют с этим флагом и сравнивают, какие сообщения вернулись.

В сценариях флаг — настройка издателя. Она записывается в свойствах как `участник.mandatory=true`.

Пример. Диспетчер публикует три посылки, но в ключе опечатка: `delivr` вместо `deliver`. Издатель включил `mandatory`.

```scenario example
{
  "sim": "rabbit",
  "seed": 1,
  "durationMs": 2000,
  "setup": "rabbitmqadmin exchanges declare --name shipments --type direct --durable true\nrabbitmqadmin queues declare --name couriers --type classic --durable true\nrabbitmqadmin bindings declare --source shipments --destination-type queue --destination couriers --routing-key deliver",
  "actors": [
    { "id": "dispatch", "kind": "producer", "rate": 10, "count": 3, "message": { "body": "parcel {n}", "exchange": "shipments", "routingKey": "delivr" }, "config": { "mandatory": true } }
  ],
  "faults": [],
  "expect": [
    { "kind": "noLoss" },
    { "kind": "noReturned" }
  ]
}
```

Журнал:

```text
0    publish  dispatch  dispatch опубликовал dispatch-1 в shipments с ключом «delivr»
0    return   broker    dispatch-1 возвращён издателю: basic.return 312 NO_ROUTE
100  publish  dispatch  dispatch опубликовал dispatch-2 в shipments с ключом «delivr»
100  return   broker    dispatch-2 возвращён издателю: basic.return 312 NO_ROUTE
200  publish  dispatch  dispatch опубликовал dispatch-3 в shipments с ключом «delivr»
200  return   broker    dispatch-3 возвращён издателю: basic.return 312 NO_ROUTE
```

Итог: `noLoss` выполнено («Потерь нет»): каждое сообщение вернулось к издателю, значит, о нём известно. `noReturned` не выполнено («Возвращено издателю: 3»): ни одна посылка не доставлена, и условие «возвратов нет» нарушено. С `"mandatory": false` в журнале вместо строк `return` были бы строки `drop` («маршрута нет, сообщение отброшено»), и `noLoss` не выполнялось бы: «Потеряно сообщений: 3», а `noReturned` выполнялось бы, потому что издателю ничего не вернули. Молчание брокера не значит, что всё хорошо.

### Условия сценария: noReturned

`noReturned` — ни одно сообщение не вернулось издателю. Вместе с `noLoss` оно означает: ни потерь, ни возвратов, то есть всё нашло маршрут. Если вы видите «Потеряно сообщений» без возвратов, у издателя нет `mandatory` или нет AE.

### Как искать, куда пропали сообщения

Идите по пути сообщения с начала.

1. **Правильный ли exchange?** Опечатка в имени ведёт к ошибке `404`, но сообщение в exchange по умолчанию (`""`) с неверным ключом исчезнет молча.
2. **Совпадает ли ключ?** Сравните ключ в публикации с ключом привязки буква в букву. Для `topic` проверьте число слов и места `*` и `#`.
3. **Есть ли привязка?** `rabbitmqadmin bindings list` покажет источник, получателя и ключ каждой привязки.
4. **Подходит ли тип exchange?** `headers` не читает ключ, `fanout` читает только список привязок.
5. **Есть ли запасной маршрут?** AE ловит то, что не нашло очереди; с `mandatory` издатель узнаёт о проблеме сразу.

В журнале сценария строка `drop … маршрута нет, сообщение отброшено` содержит имя сообщения. Найдите его строку `publish` выше: там написаны exchange и ключ, с которыми оно ушло.

### Что выбрать

- `mandatory`, если издатель может и должен реагировать: повторить отправку, записать ошибку, остановить рассылку.
- AE, если сообщения нужно сохранить для ручного разбора независимо от издателя, например заказы с неизвестным ключом. Следите за очередью AE: если в ней растут сообщения, это сигнал о поломке маршрутов.
- Оба сразу не требуются: сообщение, ушедшее через AE, считается доставленным, и флаг возврата не сработает.

### Частые ошибки

- **Ошибка:** считать, что публикация без ошибки значит доставку. **Верно:** без `mandatory` и AE сообщение без маршрута пропадает молча. Проверяйте очереди или ставьте флаг.
- **Ошибка:** включить `mandatory`, но не обработать возврат. Сообщения вернутся и будут проигнорированы. **Верно:** обработчик возвратов обязателен: запись в журнал, повтор, тревога.
- **Ошибка:** ждать возврата, когда у exchange есть AE и сообщение ушло в него. **Верно:** сообщение доставлено через AE, и `basic.return` не будет.
- **Ошибка:** исправлять потери увеличением числа потребителей или памяти. **Верно:** сначала убедиться, что сообщения доходят до очередей: ключи, привязки, тип exchange.

### Шпаргалка

- Нет маршрута: по умолчанию сообщение отбрасывается без ошибки.
- `mandatory` у издателя: брокер возвращает сообщение (`basic.return`, `312 NO_ROUTE`); нужен обработчик возвратов.
- Alternate exchange: сообщение без маршрута уходит в запасной exchange и считается доставленным.
- В свойствах сценария: `участник.mandatory=true`.
- `noLoss` — нет потерянных сообщений; `noReturned` — нет возвратов издателю.
- Диагностика: exchange → ключ → привязки → тип exchange → AE.

Издатель `campaign-sms` отправляет в exchange `notices` четыре сообщения с ключом `sms`, `campaign-push` — четыре с ключом `push`. Очередь есть только для `sms`, потребитель `sender` обрабатывает её сообщения. Очередь для `push` появится позже, а пока при проверке видно: потеряно четыре сообщения `push`, и никто об этом не знает. Измените настройку издателя `campaign-push` так, чтобы сообщения без маршрута возвращались издателю, а не отбрасывались молча. Все четыре `sms` должны быть обработаны к 3000-й миллисекунде.
```properties starter
# true — брокер возвращает сообщения без маршрута, false — отбрасывает
campaign-push.mandatory=false
```

```properties solution
campaign-push.mandatory=true
```

Издатель заказов публикует события в exchange `orders` типа `direct`. К нему привязана очередь `billing` с ключом `paid`. Бухгалтерия жалуется, что платежи не приходят, но в логе издателя ошибок нет. Какие изменения помогут не терять такие сообщения молча? Выберите все верные. (В коде условные вызовы: `publish` отправляет сообщение, `on_return` задаёт обработчик возвратов.)

```python code
order_events = broker.exchange("orders")
def send_order(order):
    key = "order." + order.status            # "order.paid"
    order_events.publish(routing_key=key, body=order.json(), mandatory=False)
    log.info("order %s sent", order.id)
```
