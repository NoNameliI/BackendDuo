# Publisher confirms и идемпотентный потребитель

Приложение банка отправляет в очередь поручения на выплату. Потребитель надёжно подтверждает обработку, очередь durable, сообщения persistent. Но остался вопрос на стороне издателя: как приложение узнает, что брокер принял поручение? Без ответа оно не отличит «принято» от «потеряно по дороге». Для этого у издателя есть подтверждения (publisher confirms), а у потребителя — идемпотентность. Подтверждения издателя дают доставку «как минимум один раз», при которой возможны дубли, а идемпотентный потребитель делает эти дубли безвредными.

### Publisher confirms

Подтверждения издателя — это ответы брокера на публикации. Они включаются на канале командой `confirm.select`.

- Каждая публикация получает номер (`seq`), он растёт с единицы.
- Брокер отвечает `basic.ack` с этим номером. Флаг `multiple=true` означает «все номера до указанного включительно».
- Когда приходит `basic.ack`:
  - если сообщение маршрутизировано — после того как его приняли все целевые очереди;
  - если persistent сообщение лежит в durable очереди — после записи на диск;
  - если маршрута нет — как только exchange решил, что очереди нет. Если был флаг `mandatory`, `basic.return` приходит раньше подтверждения.
- `basic.nack` приходит редко: при внутренней ошибке очереди или при переполнении очереди с `reject-publish`.
- Порядок подтверждений обычно совпадает с порядком публикаций, но на это нельзя полагаться.

Вывод: `basic.ack` не говорит, что сообщение обработано. Он говорит, что брокер принял на себя ответственность за него, и то лишь настолько, насколько надёжны очередь и сообщение (урок 3.3).

Консольная команда `publish message` подтверждения не использует. Песочница показывает их в сценариях: свойство издателя `confirms: true` включает `confirm.select`, а в журнале появляются строки `confirm`.

### Подтверждение потеряно: повторная публикация

Подтверждение — тоже сообщение, и оно может потеряться по дороге. Издатель, не дождавшийся ответа, не знает, дошла ли публикация. Единственное безопасное действие — опубликовать ту же работу ещё раз. Тогда в очереди может оказаться две копии одного сообщения.

В песочнице это моделирует отказ `ack.lost` у издателя: следующее подтверждение для него теряется, и издатель публикует то же сообщение через 1000 мс. Пример: приложение выплат отправляет пять поручений, подтверждение третьего теряется на 350-й миллисекунде.

```scenario example
{
  "sim": "rabbit",
  "seed": 1,
  "durationMs": 5000,
  "setup": "rabbitmqadmin queues declare --name payouts --type classic --durable true",
  "actors": [
    { "id": "pay-app", "kind": "producer", "rate": 5, "count": 5, "message": { "body": "payout {n}", "exchange": "", "routingKey": "payouts", "props": { "delivery_mode": 2 } }, "config": { "confirms": true } },
    { "id": "cashier", "kind": "consumer", "queue": "payouts", "processMs": 50, "config": { "auto_ack": false, "idempotent": false } }
  ],
  "faults": [ { "at": 350, "kind": "ack.lost", "actor": "pay-app" } ],
  "expect": [
    { "kind": "noLoss" },
    { "kind": "noDuplicateProcessing", "actor": "cashier" },
    { "kind": "allConfirmed" },
    { "kind": "processedAtLeast", "actor": "cashier", "count": 5, "byMs": 5000 }
  ]
}
```

Журнал:

```text
0     publish  pay-app  pay-app опубликовал pay-app-1 в (default) с ключом «payouts»
10    confirm  broker   pay-app-1 подтверждено (seq 1)
350   fault    pay-app  Следующее подтверждение для pay-app потеряется по дороге
400   publish  pay-app  pay-app опубликовал pay-app-3 в (default) с ключом «payouts»
410   fault    pay-app  Подтверждение pay-app-3 потеряно по дороге
410   fault    pay-app  pay-app не получил подтверждение pay-app-3 и отправит его повторно
450   process  cashier  cashier обработал pay-app-3
1410  publish  pay-app  pay-app опубликовал pay-app-3 в (default) с ключом «payouts»
1420  confirm  broker   pay-app-3 подтверждено (seq 6)
1460  process  cashier  cashier обработал pay-app-3
```

Первое подтверждение пришло через 10 мс: persistent сообщение в durable очереди подтверждается после записи на диск. Подтверждение третьего поручения потеряно, издатель повторил публикацию через секунду, и `cashier` обработал `pay-app-3` дважды. Итог: `noLoss` выполнено, `allConfirmed` выполнено, `processedAtLeast` выполнено («cashier: обработано 6»), `noDuplicateProcessing` не выполнено («cashier: повторно обработано сообщений: 1»).

Новые условия `expect`:

- `allConfirmed` — каждая публикация издателя с включёнными подтверждениями в итоге подтверждена.

### Идемпотентный потребитель

**Идемпотентность** — свойство обработки: повторное выполнение с тем же сообщением не меняет результата. Потребитель запоминает идентификаторы уже обработанных сообщений и пропускает повторные. В реальной системе для этого используют уникальный идентификатор в сообщении и запись об обработанных в базе с уникальным ключом.

В сценарии это настройка потребителя `idempotent`:

- `idempotent: false` — каждая доставка обрабатывается;
- `idempotent: true` — повторная обработка уже виденного сообщения пропускается; в журнале строка «cashier уже обрабатывал pay-app-3 и пропускает дубль».

С `cashier.idempotent=true` пример выше завершается так: `noDuplicateProcessing` выполнено («cashier: дублей нет»), `processedAtLeast` выполнено («cashier: обработано 5»). Дубль пришёл, но не повлиял на результат.

### Откуда ещё берутся дубли

- Потребитель упал после обработки, но до `ack`: брокер вернул сообщение в очередь (урок 1.1).
- Потребитель с ручным подтверждением упал до конца обработки: сообщение вернулось и будет обработано заново. Дубля результата нет, но если часть работы уже сделана (например, письмо отправлено), её нужно уметь пропускать.
- Издатель повторил публикацию без подтверждения.

Все три случая — следствие гарантии «как минимум один раз». Гарантия «ровно один раз» на уровне брокера не обещана. Достигается она идемпотентной обработкой.

### Частые ошибки

- **Ошибка:** считать `basic.ack` издателя подтверждением обработки. **Верно:** он говорит лишь, что брокер принял сообщение. Обработку подтверждает потребитель.
- **Ошибка:** не включить `mandatory` и принять `basic.ack` за доставку. **Верно:** для сообщения без маршрута брокер тоже вернёт `basic.ack`; поймать такой случай помогает `mandatory`.
- **Ошибка:** не повторять публикацию, если подтверждения нет. **Верно:** без подтверждения нужно повторить публикацию и принять дубли, а потребитель сделать идемпотентным.
- **Ошибка:** сделать потребителя идемпотентным, но оставить `auto_ack=true`. **Верно:** идемпотентность не лечит потерю: при автоподтверждении упавшая обработка пропадает насовсем.

### Шпаргалка

- `confirm.select` включает подтверждения; `basic.ack` издателю приходит с `seq`, для persistent в durable — после записи на диск.
- Подтверждение издателя ≠ обработка потребителем.
- Нет подтверждения — повторить публикацию; будут дубли.
- В сценарии: `confirms: true` у издателя, `ack.lost` — потеря подтверждения, `idempotent` у потребителя, `allConfirmed`, `noDuplicateProcessing`.
- «Как минимум один раз» + идемпотентный потребитель = результат без дублей.

```json
{
  "type": "scenario",

    "Раздел «Идемпотентный потребитель».",
    "Издатель повторил публикацию, потому что не получил подтверждение, и это правильно. Повторять публикации нельзя запретить, но потребитель может пропускать уже обработанное. За это отвечает `idempotent`.",
    "В окне свойств установите `ledger.idempotent=…`; `ledger.auto_ack` менять не нужно."
  ],
  "check": {}
}
```

Приложение банка `bank-app` отправляет в очередь `transfers` пять переводов (`transfer 1` … `transfer 5`), все persistent, подтверждения включены. На 350-й миллисекунде подтверждение для издателя теряется, и перевод 3 публикуется повторно через секунду. Потребитель `ledger` записывает каждый перевод в книгу и подтверждает вручную. Сейчас перевод 3 записан дважды.

Настройте потребителя так, чтобы ни один перевод не был записан дважды и все пять были обработаны к 5000-й миллисекунде. Править нужно только свойства.

```properties starter
ledger.auto_ack=false
ledger.idempotent=false
```

```properties solution
ledger.auto_ack=false
ledger.idempotent=true
```
