# Запуск в продакшене: uvicorn, Docker, прокси

Сервис бронирования номеров отлично работает у разработчика: он запускает `fastapi dev main.py`, правит код, сервер перезапускается сам. Теперь приложение нужно выложить на сервер, чтобы им пользовались сотни людей одновременно. Перед сервером обычно стоит прокси, внутри контейнера работает несколько процессов, а наружу виден только порт 443. В этом уроке вы разберёте, чем продакшен-запуск отличается от разработки, и проверите на практике одну деталь, которая действительно запускается в студии: префикс адреса за прокси.

Сразу об ограничениях. В студии нет настоящего сервера, процессов, сети, Docker и прокси: приложение вызывается напрямую, внутри одного Python. Поэтому команды и файлы ниже показаны текстом для вашего компьютера или сервера и в студии не выполняются. Запускаемым остаётся только пример про `root_path`.

### Разработка и продакшен: три способа запуска

```sh
fastapi dev main.py
fastapi run main.py
uvicorn main:app --host 0.0.0.0 --port 8000
```

- `fastapi dev main.py` — режим разработки. Сервер перезапускается при каждой правке файла и по умолчанию слушает только `127.0.0.1`, то есть доступен только с вашего компьютера. На сервере его не используют: перезапуск ради правок не нужен, а следящий за файлами процесс лишний.
- `fastapi run main.py` — режим продакшена: без автоперезапуска. Команда `fastapi` из пакета `fastapi[standard]` запускает `uvicorn`, поэтому по смыслу это почти то же, что третья строка.
- `uvicorn main:app --host 0.0.0.0 --port 8000` — запуск самого сервера. `main:app` читается как «модуль `main`, в нём переменная `app`». `--host 0.0.0.0` значит «слушать все сетевые интерфейсы», иначе сервер внутри контейнера не будет виден снаружи. `--port` задаёт порт.

**uvicorn** — сервер, который принимает сетевые соединения и передаёт запросы приложению по стандарту ASGI. Сам FastAPI сети не касается: он описывает, что делать с запросом. Опция `--reload` перезапускает сервер при правках и годится только для разработки; вместе с `--workers` она не работает.

### Воркеры: сколько процессов запускать

Один процесс `uvicorn` выполняет Python-код в одном потоке на одном ядре процессора. Чтобы использовать все ядра, запускают несколько процессов-**воркеров**:

```sh
fastapi run --workers 4 main.py
uvicorn main:app --workers 4
```

Что это даёт и чего не даёт:

- Нагрузка распределяется между процессами, ядра работают параллельно.
- Если один воркер упал, остальные продолжают отвечать.
- Каждый воркер — отдельная копия приложения со своей памятью: расход памяти растёт кратно числу воркеров.
- **Память воркеров не общая.** Словарь `CARTS = {}`, счётчик или кеш в переменной у каждого воркера свои. Пользователь положил товар в корзину через один воркер, следующий запрос попал на другой, и корзина пуста. Всё, что должно быть общим, хранят во внешнем месте: в базе данных или в Redis.
- Скорость одного запроса воркеры не увеличивают, растёт число запросов в секунду.

Сколько запускать? Универсального числа нет. Практические ориентиры:

- Начинают с числа ядер процессора и проверяют нагрузочным тестом на реальных данных, а не по формуле.
- Приложение, которое большую часть времени ждёт базу и сеть (`async def` с `await`), обходится меньшим числом воркеров: один процесс обслуживает много ожидающих запросов.
- Приложение с тяжёлыми вычислениями упирается в ядро, и воркеров нужно больше.
- Каждый воркер держит соединения с базой. Четыре воркера по десять соединений — это сорок, и сервер базы тоже имеет предел.

**Gunicorn** — старый и зрелый менеджер процессов для Python. Его можно поставить поверх uvicorn: он запускает воркеры, перезапускает упавшие и аккуратно обновляет их. Связка выглядит так:

```sh
pip install gunicorn uvicorn-worker
gunicorn main:app -w 4 -k uvicorn_worker.UvicornWorker
```

- `-w 4` — четыре воркера, `-k` — класс воркера, который умеет говорить по ASGI.
- Класс `uvicorn.workers.UvicornWorker` из самого uvicorn объявлен устаревшим: в документации uvicorn рекомендован отдельный пакет `uvicorn-worker`.
- Для нового проекта gunicorn нужен не всегда: `uvicorn --workers` уже запускает несколько процессов. Gunicorn берут, если нужны его возможности управления воркерами.

Если приложение работает в Kubernetes или похожей системе, принято запускать **один процесс на контейнер** и масштабировать числом контейнеров (в этой системе их называют репликами): о количестве копий и их перезапуске заботится оркестратор.

### Docker: приложение в образе

**Docker** упаковывает приложение вместе с Python и библиотеками в **образ**: на любом сервере из него запускается одинаковый **контейнер**. Образ описывает файл `Dockerfile`: набор инструкций сверху вниз. Это идея, а не то, что вы запустите в студии.

```text
FROM python:3.14-slim
WORKDIR /code
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app ./app
USER nobody
EXPOSE 8000
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
```

- `FROM python:3.14-slim` — основа образа: готовый образ с Python.
- `WORKDIR /code` — рабочая папка внутри образа.
- `COPY requirements.txt .` и `RUN pip install ...` — сначала копируют только список зависимостей и ставят их. Docker кеширует каждый шаг: пока `requirements.txt` не менялся, шаг установки берётся из кеша, и сборка после правки кода занимает секунды. `--no-cache-dir` не оставляет в образе кеш `pip` и уменьшает его размер.
- `COPY app ./app` — код копируют после установки зависимостей: он меняется чаще.
- `USER nobody` — дальше процесс запускается не от администратора контейнера, а от обычного пользователя.
- `EXPOSE 8000` — пометка в описании образа, какой порт слушает приложение. Порт она не открывает, это подсказка для людей и инструментов.
- `CMD [...]` — команда запуска. Запись списком (без оболочки) нужна, чтобы сигнал остановки доходил до сервера, и он завершался корректно.

Рядом кладут файл `.dockerignore` со списком того, что не копировать в образ: `.env`, `.git`, `tests/`, `__pycache__/`. Иначе `COPY` увезёт локальные секреты внутрь образа.

Сборка и запуск, снова текстом:

```sh
docker build -t booking-api .
docker run -p 8000:8000 -e SECRET_KEY=значение booking-api
```

- `-t booking-api` — имя образа; точка в конце — папка, где лежит `Dockerfile`.
- `-p 8000:8000` — порт 8000 снаружи соединяется с портом 8000 контейнера.
- `-e SECRET_KEY=значение` — передаёт секрет в окружение контейнера при запуске. Образ секретов не содержит.

### Обратный прокси

Перед приложением обычно ставят **обратный прокси** (nginx, Traefik, балансировщик облака). Он принимает запросы из интернета и пересылает их приложению. Зачем он нужен:

- завершает HTTPS: сертификаты хранятся и обновляются в одном месте, приложение говорит по обычному HTTP внутри сети;
- распределяет запросы между копиями приложения;
- отдаёт файлы, ограничивает размер запроса, сжимает ответы;
- закрывает приложение от прямых подключений: наружу смотрит только прокси.

Побочный эффект: приложение больше не видит настоящего клиента. Адрес клиента для него — адрес прокси, схема соединения — `http`, даже если пользователь пришёл по `https`. Прокси сообщает исходные данные заголовками:

- `X-Forwarded-For` — адрес клиента;
- `X-Forwarded-Proto` — исходная схема (`https`);
- `X-Forwarded-Host` — исходное имя хоста.

Сервер `uvicorn` умеет читать эти заголовки и подставлять значения в запрос. Это включает опция `--proxy-headers` (в uvicorn она по умолчанию включена, но в документации FastAPI её пишут явно). Ограничение важное: заголовкам верят только от доверенных адресов, список задаёт `--forwarded-allow-ips`.

```sh
fastapi run main.py --proxy-headers --forwarded-allow-ips="10.0.0.5"
```

- `--proxy-headers` — читать `X-Forwarded-*` и подменять адрес клиента и схему.
- `--forwarded-allow-ips="10.0.0.5"` — верить заголовкам только от этого адреса, то есть от вашего прокси. По умолчанию доверие только `127.0.0.1`.
- Значение `"*"` значит «верить любому». Если к серверу можно подключиться напрямую, любой клиент пришлёт `X-Forwarded-For: 1.2.3.4` и подделает свой адрес в журнале и в ограничениях по IP. Звёздочку ставят, только когда напрямую достучаться до сервера нельзя.

Зачем это нужно приложению: журнал должен содержать настоящий адрес, а ответы-перенаправления — правильную схему. Без настройки приложение может перенаправить пользователя с `https://shop.example/items` на `http://shop.example/items/`.

### root_path: префикс адреса за прокси

Часто прокси отдаёт приложение не с корня сайта, а по префиксу: `https://example.com/booking-api/rooms`, а прокси вырезает `/booking-api` и передаёт приложению путь `/rooms`. Пример настройки nginx как идея:

```text
location /booking-api/ {
    proxy_pass http://127.0.0.1:8000/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Маршруты приложения при этом не меняются: оно по-прежнему отвечает на `/rooms`. Но страница `/docs` должна знать, что публичный адрес начинается с `/booking-api`, иначе кнопка «Try it out» отправит запрос на `/rooms` мимо прокси. Эту информацию называют **root_path** («корневой путь»).

```python
app = FastAPI(root_path="/booking-api")
```

- `root_path="/booking-api"` — публичный префикс. Начинается со слэша и не заканчивается им.
- Он не создаёт маршруты и не меняет сопоставление путей: приложение отвечает на те же `/rooms`.
- FastAPI добавляет префикс в описание API: в `/openapi.json` появляется блок `servers` с `{"url": "/booking-api"}`, и страница документации строит адреса с префиксом.
- Значение доступно в обработчике как `request.scope["root_path"]`.
- То же можно задать при запуске флагом `--root-path /booking-api`.

```python example
from fastapi import FastAPI, Request

app = FastAPI(title="Shop API", root_path="/shop-api")


@app.get("/orders")
def list_orders(request: Request):
    return {"root_path": request.scope["root_path"], "orders": [1, 2]}
###
GET /orders
###
GET /openapi.json
```

Первый запрос: `200` и `{"root_path": "/shop-api", "orders": [1, 2]}`; маршрут по-прежнему `/orders`, без префикса. Второй запрос возвращает описание API, а в нём `"servers": [{"url": "/shop-api"}]`. Если убрать `root_path`, блока `servers` в описании не будет.

### Что проверить перед запуском

- Запуск командой без `dev` и без `--reload`.
- Секреты приходят из окружения, а не из образа.
- Приложение слушает `0.0.0.0` внутри контейнера.
- Число воркеров выбрано нагрузочным тестом, общее состояние вынесено из памяти процесса.
- Доверие к `X-Forwarded-*` ограничено адресом прокси.
- Префикс прокси совпадает с `root_path`.

### Частые ошибки

- В образе запущен режим разработки. Неверно: `CMD ["fastapi", "dev", ...]`. Верно: `fastapi run` или `uvicorn` без `--reload`.
- Воркеры и общая память. Неверно: хранить корзины в словаре и запустить `--workers 4`. Верно: хранить их в базе или Redis.
- Код копируется до установки зависимостей. Неверно: `COPY . .` перед `pip install`. Верно: сначала `requirements.txt` и `pip install`, потом код: тогда кеш сборки работает.
- Звёздочка в `--forwarded-allow-ips` у сервера, доступного напрямую. Неверно: `"*"`. Верно: адрес прокси.
- Префикс в маршрутах вместо `root_path`. Неверно: везде дописывать `/booking-api` в пути маршрутов, когда прокси его уже вырезает. Верно: маршруты без префикса и `root_path` в приложении.

### Шпаргалка

- `fastapi dev` — разработка; `fastapi run`, `uvicorn main:app --host 0.0.0.0 --port 8000` — продакшен.
- `--workers N`: параллельные процессы с отдельной памятью; общее состояние во внешнем хранилище; в Kubernetes один процесс на контейнер.
- Gunicorn: `gunicorn main:app -w 4 -k uvicorn_worker.UvicornWorker`, пакет `uvicorn-worker`.
- Dockerfile: `FROM`, `WORKDIR`, `COPY requirements.txt`, `RUN pip install`, `COPY app`, `USER`, `CMD [...]`; `.dockerignore`; секреты через `-e` при запуске.
- Прокси: `--proxy-headers`, `--forwarded-allow-ips`, заголовки `X-Forwarded-For/Proto/Host`.
- `FastAPI(root_path="/префикс")` — публичный префикс для документации (`servers` в `/openapi.json`), маршруты не меняются.
