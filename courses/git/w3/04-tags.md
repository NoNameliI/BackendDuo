# Теги и версии

Вы выпустили первую версию игры, и пользователи уже её скачали. Через месяц приходит жалоба: «в версии 1.0 не работает подсчёт очков». Какой именно коммит тогда ушёл пользователям? Искать по датам долго и ненадёжно. Для этого есть **теги** — постоянные имена коммитов: `v1.0.0`, `v1.1.0`. В отличие от ветки, тег не двигается, когда вы делаете новые коммиты.

### Лёгкий тег

Лёгкий тег — просто имя, которое указывает на коммит. Больше в нём ничего нет.

```sh
git tag имя
```

- `tag` — создать тег;
- `имя` — имя тега; без пробелов, обычно номер версии `v1.0.0` или метка вроде `nightly`;
- без указания коммита тег ставится на текущий коммит (`HEAD`).

```sh example
git tag nightly
git tag
```

Команда создания ничего не печатает. `git tag` без аргументов выводит список тегов: `nightly`.

Чем тег отличается от ветки? Ветка — подвижный указатель: каждый новый коммит сдвигает её вперёд. Тег стоит на своём коммите, пока вы сами его не удалите. Поэтому через год `v1.0.0` укажет ровно на тот код, который ушёл пользователям. Тег можно использовать везде, где Git ждёт коммит: `git log --oneline v1.0.0`, `git switch -c fix v1.0.0`.

Лёгкие теги удобны для личных временных меток. Для выпусков версий берут аннотированные теги.

### Аннотированный тег

Аннотированный тег — отдельный объект Git: кроме ссылки на коммит в нём хранятся автор тега, дата и описание.

```sh
git tag -a имя -m "Описание"
```

- `-a` — создать аннотированный тег (от annotated);
- `-m "Описание"` — описание тега, например что вошло в версию. В песочнице нет редактора, поэтому `-m` обязателен;
- если указать `-m` без `-a`, тег всё равно получится аннотированным.

```sh example
git tag -a v0.9 -m "Бета-версия для друзей"
```

### git show — что внутри тега

```sh
git show тег
```

- для аннотированного тега Git сначала печатает сам тег: строку `tag имя`, автора (`Tagger:`), дату и описание, а затем коммит;
- для лёгкого тега сразу печатается коммит: у тега нет своих данных.

```sh example
git show v0.9
```

Вывод начинается со строк `tag v0.9`, `Tagger: Студент <student@example.com>` и описания «Бета-версия для друзей». Ниже — коммит «Подсчёт очков» с его изменениями. Сравните с `git show nightly`: там вывод сразу начинается со строки `commit`.

### Тег на старый коммит

Тег можно поставить не только на текущий коммит. Допишите в конце команды, какой коммит отметить.

```sh
git tag имя коммит
git tag -a имя -m "Описание" коммит
```

- `коммит` — `HEAD~2`, имя ветки или короткий идентификатор из `git log --oneline`;
- остальные части те же, что и раньше.

```sh example
git tag -a v0.1 -m "Прототип" HEAD~2
git log --oneline
```

`git log --oneline` показывает теги рядом с коммитами: `(tag: v0.1) Первая версия игры`, а у последнего коммита — `tag: v0.9` и `tag: nightly`.

### Список тегов по шаблону

Когда тегов много, список можно отфильтровать.

```sh
git tag
git tag -l "шаблон"
```

- `git tag` — все теги по алфавиту;
- `-l` — показать только теги, подходящие под шаблон (от list);
- в шаблоне `*` означает «любые символы»: `"v1*"` — все теги, которые начинаются с `v1`;
- шаблон берите в кавычки: в настоящем терминале без них оболочка может принять `*` за имена файлов.

```sh example
git tag -l "v0*"
```

Выводятся `v0.1` и `v0.9`, а `nightly` не подходит под шаблон.

### Удаление тега

```sh
git tag -d имя
```

- `-d` — удалить тег (от delete); коммит при этом не трогается;
- Git печатает `Deleted tag 'имя' (was …)`.

```sh example
git tag -d nightly
git tag
```

Остались `v0.1` и `v0.9`.

Переставить существующий тег на другой коммит одной командой создания нельзя: Git ответит `fatal: tag 'v0.9' already exists`. Сначала удалите тег через `-d`, затем создайте заново.

Теги живут в вашем репозитории. На сервер их отправляют отдельно — об этом в мире про удалённые репозитории.

### Семантическое версионирование

Чтобы по номеру версии было понятно, насколько сильно всё изменилось, договорились о схеме `MAJOR.MINOR.PATCH` — **семантическое версионирование** (SemVer). Тег обычно пишут с буквой `v`: `v2.3.1`.

```sh
vMAJOR.MINOR.PATCH
```

- `MAJOR` — несовместимые изменения: то, что работало у пользователей, может сломаться. `v1.4.2` → `v2.0.0`;
- `MINOR` — новые возможности без поломок. `v1.4.2` → `v1.5.0`;
- `PATCH` — только исправления ошибок. `v1.4.2` → `v1.4.3`;
- при увеличении номера все номера правее сбрасываются в ноль;
- версии `0.x.y` — ранняя разработка, когда всё ещё может меняться.

### Частые ошибки

- `git tag -a v1.0.0` без `-m` → в песочнице это ошибка, редактора нет. Пишите `git tag -a v1.0.0 -m "Описание"`.
- Повторный `git tag v1.0.0` на другой коммит → `already exists`. Сначала `git tag -d v1.0.0`, потом создайте тег заново.
- Тег на текущий коммит вместо нужного старого → допишите коммит в конце: `git tag -a v1.0.0 -m "…" HEAD~2`.
- Лёгкий тег для релиза → не видно, кто и когда выпустил версию. Для релизов используйте `-a`.

### Шпаргалка

- `git tag имя` — лёгкий тег на текущий коммит
- `git tag -a имя -m "Описание"` — аннотированный тег
- `git tag -a имя -m "Описание" коммит` — тег на старый коммит
- `git tag`, `git tag -l "v1*"` — список тегов, по шаблону
- `git show тег` — тег и его коммит
- `git tag -d имя` — удалить тег
- `vMAJOR.MINOR.PATCH`: поломки → MAJOR, новые возможности → MINOR, исправления → PATCH

```sh setup
mkdir mobile

```
