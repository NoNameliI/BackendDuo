# Слияние веток

Работа в ветке закончена: раздел готов, проверен, и пора вернуть его в основную версию. Для этого ветку **сливают** (merge) с `main`. Иногда Git при этом просто передвигает метку, а иногда создаёт специальный коммит слияния. В этом уроке вы разберётесь, когда что происходит, и научитесь читать такую историю на графе.

### git merge — влить ветку в текущую

Слияние всегда идёт **в текущую ветку**: сначала переходите туда, куда хотите принять изменения, потом называете ветку, откуда их взять.

```sh
git switch ветка-приёмник
git merge ветка-источник
```

- `git switch ветка-приёмник` — обычно это `main`; проверьте по приглашению терминала, где вы;
- `merge` — слить: добавить в текущую ветку все коммиты источника, которых в ней ещё нет;
- `ветка-источник` — ветка с готовой работой. Сама она не меняется и после слияния остаётся на месте.

Запомните направление: «я на `main` и вливаю в неё `feature`». Если перепутать, `main` вольётся в `feature`, а `main` останется прежней.

Перед примерами посмотрите на исходную историю блога:

```sh example
git log --oneline --graph --all
```

На `main` один коммит «Первый пост», ветка `cats` ушла на коммит вперёд.

### Перемотка (fast-forward)

Если в текущей ветке не было новых коммитов с момента, когда от неё ответвился источник, сливать нечего: источник просто продолжает ту же линию. Тогда Git **перематывает** метку текущей ветки вперёд, на последний коммит источника. Новых коммитов не появляется, история остаётся прямой линией.

```sh example
git switch -c about
echo "Пишу о технологиях" > about.md
git add about.md
git commit -m "Страница об авторе"
git switch main
git merge about
```

Git сообщает о перемотке словами `Fast-forward`:

```
Updating 8c4ce2a..e3860c2
Fast-forward
 about.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 about.md
```

- `Updating 8c4ce2a..e3860c2` — метка `main` переехала со старого коммита на новый;
- ниже — какие файлы изменились в `main` после слияния.

Теперь `main` и `about` указывают на один и тот же коммит.

### Трёхстороннее слияние и коммит слияния

Если новые коммиты появились **в обеих** ветках, перемотать нельзя: линии разошлись. Тогда Git делает **трёхстороннее слияние**. Он сравнивает три версии файлов:

1. **общего предка** — последний коммит, который есть в обеих ветках (точка, где они разошлись);
2. последний коммит текущей ветки;
3. последний коммит источника.

Изменения обеих веток объединяются, и Git записывает результат в новый **коммит слияния**. У обычного коммита один родитель, у коммита слияния — два: последние коммиты обеих веток.

```sh
git merge ветка-источник
git merge -m "Сообщение" ветка-источник
```

- без `-m` Git берёт стандартное сообщение `Merge branch 'ветка-источник'`;
- `-m "Сообщение"` — своё сообщение для коммита слияния, как у `git commit -m`.

```sh example
git switch -c footer
echo "© Блог, 2026" > footer.md
git add footer.md
git commit -m "Подвал сайта"
git switch main
echo "Второй пост" > post2.md
git add post2.md
git commit -m "Второй пост"
git merge footer
```

Пока вы работали над подвалом, в `main` появился второй пост — линии разошлись. Git отвечает `Merge made by the 'ort' strategy.` (`ort` — название алгоритма слияния) и список файлов, пришедших из `footer`.

### Как читать граф слияния

```sh example
git log --oneline --graph
```

```
*   f785286 (HEAD -> main) Merge branch 'footer'
|\  
| * 0484a7e (footer) Подвал сайта
* | 75adff8 Второй пост
|/  
* e3860c2 (about) Страница об авторе
* 8c4ce2a Первый пост
```

Читайте снизу вверх:

- `|/` — здесь линии разошлись: от коммита «Страница об авторе» пошли две ветки;
- `* |` и `| *` — коммиты, сделанные параллельно: левая колонка — `main`, правая — `footer`;
- `|\` над ними — линии сошлись в коммите слияния;
- `*   f785286 … Merge branch 'footer'` — коммит слияния, у него два родителя.

Вкладка «Граф» рисует ту же картину: от коммита слияния идут две линии вниз. Подробный `git log` показывает обоих родителей в строке `Merge:`:

```sh example
git log -n 1
```

- `-n 1` — показать только один, самый новый коммит; вместо `1` можно подставить любое число.

В выводе есть строка вида `Merge: 75adff8 0484a7e` — это короткие идентификаторы двух родителей.

### git merge --no-ff — всегда с коммитом слияния

Иногда перемотка нежелательна: команда хочет видеть в истории, что «здесь была отдельная ветка с исправлением». Флаг `--no-ff` запрещает перемотку, и Git создаёт коммит слияния, даже если линия прямая.

```sh
git merge --no-ff -m "Сообщение" ветка-источник
```

- `--no-ff` — no fast-forward, «не перематывать»;
- `-m "Сообщение"` — как и раньше, сообщение коммита слияния; без него будет `Merge branch '…'`;
- порядок флагов не важен, имя ветки обычно пишут последним.

```sh example
git switch -c typo
echo "Первый пост в блоге" > post1.md
git add post1.md
git commit -m "Исправлена опечатка"
git switch main
git merge --no-ff -m "Исправление опечатки" typo
```

Без `--no-ff` здесь была бы перемотка. С ним Git пишет `Merge made by the 'ort' strategy.`, а на графе появляется «петля»: коммит ветки `typo` сбоку и коммит слияния «Исправление опечатки» на `main`.

### После слияния: удалить ветку

Слитая ветка больше не нужна: её коммиты уже в `main`. Удалите её командой `git branch -d` из прошлого урока. Можно перечислить несколько веток через пробел.

```sh example
git branch -d about footer typo
```

Для каждой ветки Git печатает `Deleted branch … (was …)`. Флаг `-d` здесь безопасен: неслитую ветку он удалить не даст.

### Частые ошибки

- Слияние «не в ту сторону»: вы на `feature` и выполнили `git merge main` → изменилась `feature`, а не `main`. Сначала `git switch main`, потом `git merge feature`.
- Ожидали коммит слияния, а получили `Fast-forward` → в `main` не было новых коммитов. Если коммит слияния нужен, используйте `git merge --no-ff`.
- Опечатка в имени ветки → `merge: … - not something we can merge`. Проверьте имя командой `git branch`.
- `git commit -m` после успешного слияния → `nothing to commit`: коммит слияния Git уже сделал сам.

### Шпаргалка

- `git switch main` и `git merge ветка` — влить ветку в `main`
- `Fast-forward` — перемотка: метка сдвинулась, нового коммита нет
- `Merge made by the 'ort' strategy.` — создан коммит слияния с двумя родителями
- `git merge -m "Сообщение" ветка` — своё сообщение коммита слияния
- `git merge --no-ff ветка` — коммит слияния даже там, где возможна перемотка
- `git log --oneline --graph` — граф: `|/` — расхождение, `|\` — слияние
- `git log -n 1` — только последний коммит; `Merge:` — его родители
- `git branch -d ветка` — удалить слитую ветку

В репозитории `~/docs` ветка `hotfix` на коммит впереди `main`: в ней исправлены ссылки. Вы на ветке `main`.

Команда договорилась, что каждое исправление остаётся в истории отдельной «петлёй». Влейте `hotfix` в `main` **обязательно с коммитом слияния** и сообщением **Исправление ссылок**. Затем удалите ветку `hotfix`.

```sh setup
mkdir docs
cd docs
git init -q
echo "Установка: npm install" > install.md
git add install.md
git commit -q -m "Инструкция по установке"
git switch -q -c hotfix
echo "Подробнее: docs/guide.md" > links.md
git add links.md
git commit -q -m "Исправлены ссылки"
git switch -q main
```

```sh solution
git merge --no-ff -m "Исправление ссылок" hotfix
git branch -d hotfix
```
