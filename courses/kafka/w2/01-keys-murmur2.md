# Ключ и выбор партиции

Служба доставки пишет в Kafka события по посылкам: «принята», «в пути», «вручена». События одной посылки должны оставаться в правильном порядке, а нагрузка должна делиться между партициями. Для этого у каждой записи есть **ключ**. По нему продюсер решает, в какую партицию отправить запись. В этом уроке вы узнаете, как именно считается партиция, и научитесь управлять ею.

### Запись с ключом

Запись в Kafka — это ключ, значение, заголовки и метка времени (урок 1.1). Ключ необязателен. Он не уникален: у многих записей может быть один и тот же ключ, например номер посылки или идентификатор клиента.

Ключ нужен для двух вещей:

- одинаковые ключи всегда попадают в одну партицию (пока число партиций не меняется);
- внутри партиции записи идут в порядке записи, поэтому события одного ключа не перемешиваются.

### Формула партиции

Для записи с ключом продюсер считает партицию так:

```text
партиция = toPositive(murmur2(байты ключа)) % число_партиций
```

- `murmur2` — быстрая хеш-функция. Она превращает набор байт в 32-битное целое со знаком. Ключ-строка сначала превращается в байты в кодировке UTF-8.
- `toPositive(n)` — это маска `n & 0x7fffffff`: она обнуляет старший бит и тем самым убирает знак. Это не `abs`: для отрицательных чисел результаты разные.
- `%` — остаток от деления на число партиций топика. Результат — номер партиции от `0` до `число_партиций - 1`.

Хеш зависит только от ключа. От топика и от времени он не зависит, поэтому в любом кластере один и тот же ключ даёт один и тот же хеш. Меняется только остаток от деления.

### Как считается murmur2

Вам не придётся считать хеш руками. Но алгоритм короткий, и полезно один раз увидеть, что в нём нет случайности. Все операции — 32-битные, умножение берётся по модулю 2³², а `>>>` — сдвиг вправо с нулями слева. Константа `m = 0x5bd1e995`.

1. `h = 0x9747b28c XOR длина_ключа_в_байтах`.
2. Ключ делится на блоки по 4 байта. Для каждого полного блока: число `k` собирается из байт, первый байт — младший (порядок little-endian). Затем `k = k · m`, `k = k XOR (k >>> 24)`, `k = k · m`, `h = h · m`, `h = h XOR k`.
3. Остаток из 1–3 байт. Если их три: `h = h XOR (третий байт << 16)`. Если два или три: `h = h XOR (второй байт << 8)`. Если хотя бы один: `h = h XOR первый байт`, затем `h = h · m`.
4. Финал: `h = h XOR (h >>> 13)`, `h = h · m`, `h = h XOR (h >>> 15)`.

Разберём ключ `abc`. Его байты `0x61 0x62 0x63`, полных блоков нет, остаток — три байта.

| Шаг | Значение `h` |
|---|---|
| начало: `0x9747b28c XOR 3` | `0x9747b28f` |
| `XOR (0x63 << 16)` | `0x9724b28f` |
| `XOR (0x62 << 8)` | `0x9724d08f` |
| `XOR 0x61` | `0x9724d0ee` |
| `· m` | `0xa6e43886` |
| `XOR (h >>> 13)` | `0xa6e10fa7` |
| `· m` | `0x1c941b33` |
| `XOR (h >>> 15)` | `0x1c94221b` |

Итог `0x1c94221b` — это `479470107`. Число положительное, маска ничего не меняет. При трёх партициях `479470107 % 3 = 0`, при шести `479470107 % 6 = 3`.

Для отрицательного хеша маска важна. У ключа `user-2` хеш равен `-324981792`. Маска даёт `1822501856`, партиция при трёх партициях — `2`. Если бы использовали `abs`, получилось бы `324981792 % 3 = 0`. Реализация Kafka использует маску, и песочница тоже.

### Таблица для проверки

Хеши посчитаны алгоритмом выше. Значение `abc` совпадает с тестом клиентской библиотеки Kafka, остальные получены тем же кодом.

| Ключ | `murmur2` | Партиция из 3 | Партиция из 6 |
|---|---|---|---|
| `abc` | `479470107` | 0 | 3 |
| `user-1` | `1404122828` | 2 | 2 |
| `order-42` | `501153024` | 0 | 0 |
| `hello` | `2132663229` | 0 | 3 |
| `user-2` | `-324981792` | 2 | 2 |
| `a` | `-1563381124` | 1 | 4 |
| `key1` | `28543940` | 2 | 2 |
| `""` (пустая строка) | `275646681` | 0 | 3 |

Пустая строка — это ключ, а не его отсутствие. Её хеш считается как у любого ключа.

### Консольный продюсер с ключами

По умолчанию консольный продюсер пишет записи без ключа. Свойства `parse.key` и `key.separator` вы использовали в уроке 1.1. Напомним форму и добавим подробности: чтобы продюсер разбирал строку на ключ и значение, включают свойства читателя строк:

```text
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic ТОПИК \
  --reader-property parse.key=true --reader-property key.separator=РАЗДЕЛИТЕЛЬ
```

- `--reader-property` задаёт свойство того, как разбираются введённые строки. Старое имя `--property` ещё работает, но печатает предупреждение, что оно устарело.
- `parse.key=true` — первая часть строки до разделителя становится ключом.
- `key.separator=:` — разделитель ключа и значения. Если его не задать, разделитель — символ табуляции. Делится строка по первому разделителю, поэтому в значении двоеточие допустимо.
- Если в строке нет разделителя, продюсер печатает `No key separator found on line number N: '...'`. Значит, строка не записана.

Строки пишут в heredoc, как и в уроках первого мира: после `<<EOF` идут строки записей, последняя строка `EOF`.

### Чтение с номером партиции

Консольный потребитель показывает ключ, партицию и offset, если включить свойства форматера:

```text
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic ТОПИК --from-beginning --max-messages N \
  --formatter-property print.key=true --formatter-property print.partition=true --formatter-property print.offset=true
```

- `--formatter-property` задаёт, что печатать. Старое имя `--property` тоже устарело.
- Поля идут в фиксированном порядке и разделены табуляцией: `Partition:…`, `Offset:…`, ключ, значение. Если ключа нет, печатается `null`.
- `--partition N --offset earliest` читает одну партицию `N` с самого начала. `--offset` разрешён только вместе с `--partition`.
- Консоль песочницы читает топик партиция за партицией: сначала всю партицию 0, потом партицию 1 и так далее. В настоящей Kafka записи разных партиций приходят вперемешку.

Пример. В топик `tracking` из трёх партиций пишем события посылок. Ключ — номер посылки или клиента.

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic tracking --partitions 3 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic tracking --reader-property parse.key=true --reader-property key.separator=: <<EOF
abc:parcel 1
user-1:parcel 2
order-42:parcel 3
abc:parcel 4
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic tracking --from-beginning --max-messages 4 --formatter-property print.key=true --formatter-property print.partition=true --formatter-property print.offset=true
```

Результат:

```text
Created topic tracking.
Partition:0	Offset:0	abc	parcel 1
Partition:0	Offset:1	order-42	parcel 3
Partition:0	Offset:2	abc	parcel 4
Partition:2	Offset:0	user-1	parcel 2
Processed a total of 4 messages
```

Сверим с таблицей. `abc` и `order-42` дают партицию 0, `user-1` — партиция 2. Обе записи `abc` лежат в партиции 0 подряд, с offset 0 и 2: между ними оказалась запись другого ключа, но их порядок сохранён. В партиции 1 записей нет.

### Рост числа партиций сдвигает ключи

Партиции можно добавлять, но убавить нельзя:

```text
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic ТОПИК --partitions НОВОЕ_ЧИСЛО
```

Команда `--alter` описана в уроке 1.2: число партиций можно только увеличить, при успехе команда ничего не печатает.

Формула считает остаток от деления на **новое** число партиций, а хеш ключа не меняется. Поэтому часть ключей переезжает. Старые записи остаются там, где были. Новые записи того же ключа уйдут в другую партицию.

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic tracking --partitions 6
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic tracking --reader-property parse.key=true --reader-property key.separator=: <<EOF
abc:parcel 5
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic tracking --partition 3 --offset earliest --max-messages 1 --formatter-property print.key=true --formatter-property print.partition=true --formatter-property print.offset=true
```

Результат:

```text
Partition:3	Offset:0	abc	parcel 5
Processed a total of 1 messages
```

Раньше `abc` лежал в партиции 0, теперь новая запись ушла в партицию 3, как предсказывает таблица: `479470107 % 6 = 3`. Старые записи `abc` остались в партиции 0. Порядок событий одной посылки между старой и новой партицией уже не гарантируется. Подробнее об этом — в уроке 2.2.

Уменьшить число партиций нельзя, консоль отвечает ошибкой. Покажем и ошибку разбора ключа: в строке записи нет двоеточия.

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic oops --partitions 2 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic oops --reader-property parse.key=true --reader-property key.separator=: <<EOF
abc parcel 1
EOF
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic oops --partitions 1
```

Результат:

```text
Created topic oops.
Error: No key separator found on line number 1: 'abc parcel 1'
Error: The topic oops currently has 2 partition(s); 1 would not be an increase.
```

Обе команды завершились с ошибкой: запись не появилась, число партиций не изменилось.

### Запись без ключа

Если ключ `null` (то есть его нет совсем), хеш не считается. Продюсер выбирает партицию так:

- он держится одной партиции, пока в неё не уйдёт `batch.size` байт записей (размер пакета, по умолчанию 16384 байта);
- набрав этот объём, продюсер выбирает следующую партицию случайно;
- запись не привязана ни к какой партиции, поэтому порядок записей одного объекта между партициями не гарантируется.

Адаптивный выбор партиции по длине очередей, который есть в настоящем продюсере, песочница не моделирует. Для записей без ключа число партиций в основном влияет на равномерность нагрузки.

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic clicks --partitions 3 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic clicks <<EOF
click 1
click 2
click 3
click 4
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic clicks --from-beginning --max-messages 4 --formatter-property print.key=true --formatter-property print.partition=true
```

Результат:

```text
Created topic clicks.
Partition:2	null	click 1
Partition:2	null	click 2
Partition:2	null	click 3
Partition:2	null	click 4
Processed a total of 4 messages
```

Четыре маленькие записи не набрали и 16384 байт, поэтому все лежат в одной партиции. Какая именно партиция выбрана, определяет случайный выбор песочницы, и у вас номер может быть другим. Для проверок с публикацией записей без ключа в топик из нескольких партиций лаборатория не годится: результат не фиксирован. Поэтому в заданиях ключ всегда есть.

### Частые ошибки

- **Ошибка:** считать, что ключ — это уникальный идентификатор записи, и подставлять в него номер события. **Верно:** ключ задаёт группу записей, у которых должен сохраняться порядок: номер заказа, посылки, клиента. Записи с разными ключами тоже могут оказаться в одной партиции.
- **Ошибка:** ждать, что при увеличении числа партиций записи старых ключей «подтянутся» за ключом. **Верно:** старые записи остаются в своих партициях, а новые считаются по новому числу партиций.
- **Ошибка:** писать `--reader-property parse.key=true` и забыть про разделитель, когда строки записаны через двоеточие. Тогда продюсер ищет табуляцию и сообщает `No key separator found`. **Верно:** задать `key.separator=:`.
- **Ошибка:** считать пустую строку отсутствием ключа. **Верно:** `""` — полноценный ключ с собственным хешем, а отсутствие ключа — `null`, и такие записи идут по другому правилу.

### Шпаргалка

- Партиция записи с ключом: `toPositive(murmur2(байты UTF-8)) % число_партиций`.
- `toPositive` — маска `& 0x7fffffff`, не `abs`.
- Одинаковый ключ при неизменном числе партиций — всегда одна партиция.
- `--alter --partitions N`: число партиций можно только увеличить; ключи при этом могут переехать.
- Запись без ключа: одна партиция, пока не набрано `batch.size` байт, затем случайная.
- Продюсер: `--reader-property parse.key=true --reader-property key.separator=:`.
- Потребитель: `--formatter-property print.key=true`, `print.partition=true`, `print.offset=true`; поля `Partition`, `Offset`, ключ, значение.
- Читать одну партицию: `--partition N --offset earliest --max-messages N`.
