# Порядок записей и партиция

Интернет-магазин публикует события заказа: «создан», «оплачен», «собран», «отправлен». Склад не должен получить «отправлен» раньше «оплачен». А если все заказы поместить в одну партицию, магазин упрётся в скорость одного потребителя. Нужно понимать, что именно гарантирует Kafka, и не требовать от неё лишнего.

### Порядок только внутри партиции

Партиция — журнал, в который записи дописываются в конец. Каждая получает номер, offset, и потребитель читает партицию строго по возрастанию offset. Это единственная гарантия порядка:

- внутри одной партиции записи идут в порядке записи;
- между партициями порядка нет: что из них прочитано раньше, не определено.

Покажем на примере. В топик `order-events` из трёх партиций пишем события двух заказов вперемешку. Ключ — номер заказа.

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic order-events --partitions 3 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic order-events --reader-property parse.key=true --reader-property key.separator=: <<EOF
order-1:created
order-2:created
order-1:paid
order-2:paid
order-1:shipped
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic order-events --partition 0 --offset earliest --max-messages 2 --formatter-property print.key=true --formatter-property print.offset=true
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic order-events --partition 1 --offset earliest --max-messages 3 --formatter-property print.key=true --formatter-property print.offset=true
```

Результат:

```text
Created topic order-events.
Offset:0	order-2	created
Offset:1	order-2	paid
Processed a total of 2 messages
Offset:0	order-1	created
Offset:1	order-1	paid
Offset:2	order-1	shipped
Processed a total of 3 messages
```

Записи были отправлены вперемешку, но каждый заказ лежит в своей партиции, и его события идут в порядке отправки: `created`, `paid`, `shipped`. Чтобы прочитать одну партицию, консоль получает `--partition N`. Флаг `--max-messages` задаёт, сколько записей прочитать: если указать больше, чем есть, консоль после последней записи напечатает `(песочница: новых сообщений нет)`.

Какая запись из разных партиций будет прочитана первой, зависит от потребителя. Настоящая Kafka присылает записи разных партиций вперемешку, и рассчитывать на их взаимный порядок нельзя. Консоль песочницы читает партицию за партицией, но это только особенность консоли.

### Ключ даёт порядок для сущности

Порядок событий заказа нужен, а порядок между разными заказами — нет. Поэтому ключом делают идентификатор сущности: номер заказа, посылки, клиента. Из урока 2.1: ключ всегда даёт одну и ту же партицию, а в партиции порядок сохраняется. Выходит правило:

- все события одной сущности имеют общий ключ;
- этот ключ даёт одну партицию, пока число партиций не меняется;
- значит, события сущности читаются в порядке записи.

Порядок самих отправок, когда продюсер повторяет неудачную запись, зависит от настроек надёжности. С настройками по умолчанию он сохраняется, подробности — в уроке 3.3.

### Что ломает порядок

- **Ключ не по сущности.** Если ключ — номер события или случайное значение, события одного заказа расходятся по разным партициям.
- **Нет ключа.** Записи без ключа идут пачками в случайные партиции (урок 2.1), и порядок между ними не определён.
- **Рост числа партиций.** После `--alter --partitions` ключ может переехать в другую партицию. Записи до переезда лежат в старой партиции, после — в новой, и общего порядка у них нет.
- **Свойство `partitioner.ignore.keys=true`.** По умолчанию оно `false`. Если его включить, продюсер игнорирует ключи и раскладывает записи так, как будто ключей нет, хотя ключи в записях остаются.

### Общий порядок: одна партиция

Если порядок нужен сразу для всех записей топика, например в аудит-журнале, партиция должна быть одна:

```text
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic ТОПИК --partitions 1 --replication-factor 3
```

- `--partitions 1` — одна партиция: у всех записей общий порядок offset.
- `--replication-factor 3` — три копии партиции на трёх брокерах (о репликации — мир 3).

Цена такого решения: читать партицию в группе может только один потребитель (урок 2.3), поэтому скорость чтения ограничена одним потребителем.

### Сценарий и проверка порядка

В заданиях этого урока порядок проверяет сценарий. Это описание работающей системы в виде JSON. Покажем его части на примере.

```scenario example
{
  "sim": "kafka",
  "seed": 1,
  "durationMs": 20000,
  "setup": "kafka-topics.sh --bootstrap-server localhost:9092 --create --topic order-events-live --partitions 3 --replication-factor 3",
  "actors": [
    { "id": "shop", "kind": "producer", "topic": "order-events-live", "rate": 20, "count": 60, "message": { "body": "event {n}", "key": "order-{n%3}" }, "config": {} },
    { "id": "billing", "kind": "consumer", "group": "billing", "topics": ["order-events-live"], "processMs": 20, "config": { "auto.offset.reset": "earliest" } }
  ],
  "faults": [],
  "expect": [
    { "kind": "noLoss" },
    { "kind": "orderedByKey", "actor": "billing" },
    { "kind": "processedAtLeast", "actor": "billing", "count": 60, "byMs": 20000 }
  ]
}
```

Что здесь что:

- `setup` — команды консоли, которые выполняются до запуска. Здесь создаётся топик.
- `actors` — участники. Продюсер (`kind: producer`) пишет `count` записей со скоростью `rate` записей в секунду в топик `topic`. Тело и ключ задаёт `message`: `{n}` — номер записи, `{n%3}` — остаток от деления номера на 3, так что ключи `order-0`, `order-1`, `order-2` чередуются.
- Потребитель (`kind: consumer`) входит в группу `group`, читает `topics` и тратит `processMs` миллисекунд на обработку одной записи. Что такое группа, вы узнаете в уроке 2.3: пока достаточно знать, что потребитель читает все партиции топика.
- `config` — свойства клиента Kafka. Пустой объект значит значения по умолчанию. `auto.offset.reset=earliest` велит новой группе читать с начала.
- `expect` — условия успеха. `noLoss` — ни одна запись не потеряна. `orderedByKey` — потребитель обработал записи каждого ключа в порядке их отправки. `processedAtLeast` — потребитель обработал не меньше `count` записей к моменту `byMs` (в миллисекундах).

Этот сценарий проходит: каждый ключ лежит в одной партиции, порядок сохранён. Включим `partitioner.ignore.keys=true` и маленький `batch.size`, чтобы продюсер чаще менял партицию:

```scenario example
{
  "sim": "kafka",
  "seed": 1,
  "durationMs": 20000,
  "setup": "kafka-topics.sh --bootstrap-server localhost:9092 --create --topic order-events-mixed --partitions 3 --replication-factor 3",
  "actors": [
    { "id": "shop", "kind": "producer", "topic": "order-events-mixed", "rate": 20, "count": 60, "message": { "body": "event {n}", "key": "order-{n%3}" }, "config": { "partitioner.ignore.keys": true, "batch.size": 64 } },
    { "id": "billing", "kind": "consumer", "group": "billing", "topics": ["order-events-mixed"], "processMs": 20, "config": { "auto.offset.reset": "earliest" } }
  ],
  "faults": [],
  "expect": [
    { "kind": "noLoss" },
    { "kind": "orderedByKey", "actor": "billing" }
  ]
}
```

Здесь `orderedByKey` не выполняется: сообщение проверки — «нарушен порядок по ключу order-0». Записи заказа `order-0` попали в разные партиции, и потребитель обработал более позднюю раньше ранней. Потерь нет: порядок и потери — разные свойства. `batch.size` — размер пакета записей в байтах; значение 64 сделано нарочно маленьким, чтобы партиция менялась часто.

### Свойства: правка конфигурации

В заданиях-инцидентах вы чините конфигурацию без правки JSON. Для этого есть блок свойств — строки вида `актёр.свойство=значение`:

```text
shop.partitioner.ignore.keys=false
```

- `shop` — идентификатор участника из `actors`.
- После первой точки идёт имя свойства клиента Kafka. В нём самом могут быть точки, как у `partitioner.ignore.keys`.
- `#` в начале строки — комментарий. Значения `true`, `false` и числа распознаются сами.
- Свойства накладываются на `config` участника и заменяют прежнее значение.

### Частые ошибки

- **Ошибка:** брать ключом номер события или время. **Верно:** ключ — идентификатор сущности, порядок которой нужен: номер заказа.
- **Ошибка:** ждать порядка между событиями разных заказов или между разными партициями. **Верно:** порядок гарантирован только внутри партиции.
- **Ошибка:** увеличить число партиций «на лету» и считать, что порядок событий заказа сохранён. **Верно:** после `--alter` ключ может уйти в другую партицию. Если порядок критичен, топик нужно проектировать с запасом по числу партиций сразу.
- **Ошибка:** включить `partitioner.ignore.keys=true` ради равномерной нагрузки. **Верно:** это отключает смысл ключа. Для равномерности выберите ключ с большим числом разных значений.

### Шпаргалка

- Порядок гарантирован внутри партиции; между партициями его нет.
- Ключ = идентификатор сущности: события сущности идут в одну партицию по порядку.
- Порядок ломают: ключ не по сущности, нет ключа, рост числа партиций, `partitioner.ignore.keys=true`.
- Общий порядок записей — одна партиция (`--partitions 1`), цена — скорость одного потребителя.
- Сценарий: `setup`, `actors` (producer и consumer), `config`, `expect`; `orderedByKey`, `noLoss`, `processedAtLeast`.
- Свойства: `актёр.свойство=значение`, комментарий — `#`.
