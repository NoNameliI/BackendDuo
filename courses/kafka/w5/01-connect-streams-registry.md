# Connect, Streams и Schema Registry

Интернет-магазин пишет заказы в Kafka. Аналитикам нужна копия заказов в хранилище, и писать для этого потребителя никто не хочет. Бухгалтерии нужна выручка по часам. А команда, которая меняет формат заказа, не должна ломать соседние сервисы. Для этих трёх задач вокруг Kafka есть три инструмента: Connect, Streams и Schema Registry.

Эти компоненты не входят в учебную песочницу. Она моделирует брокеры, топики, группы потребителей и сбои. Поэтому урок — теория: вы научитесь выбирать инструмент и понимать его границы, а проверяют это задания с выбором ответа и разбором.

### Kafka Connect

Connect — готовый фреймворк для переноса данных между Kafka и другими системами. У него есть REST API для управления. Код потребителя или продюсера для типовых случаев писать не нужно: вы описываете, что и куда переносить.

Основные слова:

- **Коннектор** — описание одного переноса: откуда брать и куда класть.
- **Source-коннектор** — переносит данные из внешней системы в топик Kafka (например, из базы).
- **Sink-коннектор** — переносит данные из топика во внешнюю систему (например, в хранилище аналитики).
- **Worker** — процесс, который исполняет коннекторы.

Схема потока:

```text
внешняя система → source-коннектор → топик Kafka → sink-коннектор → внешняя система
```

Два режима запуска:

- **standalone** — один процесс, удобно для разработки и проверки;
- **distributed** — несколько worker работают вместе и делят коннекторы между собой. Этот режим построен на управлении группой, как группы потребителей (урок 2.3).

Позиции чтения (offset) Connect ведёт сам: вам не нужно думать о коммитах, как в обычном потребителе.

Когда выбирать Connect: нужно «перелить» данные между Kafka и стандартной системой, и логика не сложнее «взять как есть». Когда не выбирать: нужна бизнес-логика над записями. Для неё есть Streams или обычный потребитель.

### Kafka Streams

Streams — это **библиотека**, а не кластер. Вы подключаете её к своему приложению, и приложение читает топики, преобразует записи и пишет результат в другие топики. Отдельный кластер Streams не нужен: приложение запускают в нескольких экземплярах, как любой сервис.

Что нужно знать:

- **Топология** — граф обработки: источники, шаги-обработчики (processors), приёмники.
- **KStream** — поток: каждая запись — отдельное событие.
- **KTable** — таблица: для каждого ключа хранится последнее значение.
- **GlobalKTable** — ещё один вид таблицы, которую библиотека даёт приложению для справочных данных.
- **Двойственность потока и таблицы** (stream-table duality): поток можно свернуть в таблицу, а изменения таблицы — это поток.
- **State store** — локальное хранилище состояния (например, текущие суммы). Оно отказоустойчиво: после сбоя состояние восстанавливается.
- **Окна** — агрегация по времени (например, «за час»). У окна есть **grace period**: сколько после конца окна ещё принимаются запоздавшие записи.
- `processing.guarantee` — гарантия обработки. По умолчанию `at_least_once`, то есть возможны повторы после сбоя. Значение `exactly_once_v2` требует брокеров версии 2.5 и выше.

Двойственность видна и на обычном топике. Создадим топик с `cleanup.policy=compact` (урок 4.2: компактация оставляет последнее значение каждого ключа) и запишем остатки на складе:

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic stock --partitions 1 --replication-factor 3 --config cleanup.policy=compact
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic stock --reader-property parse.key=true --reader-property key.separator=: <<EOF
cable:5
lamp:2
cable:7
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic stock --from-beginning --max-messages 3 --formatter-property print.key=true --formatter-property print.offset=true
```

```text
Created topic stock.
Offset:0	cable	5
Offset:1	lamp	2
Offset:2	cable	7
Processed a total of 3 messages
```

Три записи — это **поток** изменений. **Таблица** `stock` — последнее значение по каждому ключу: `cable=7`, `lamp=2`. Так же из потока получается `KTable` в Streams: библиотека держит такую таблицу в state store.

В песочнице Streams не запускается, поэтому свёртку вы видите глазами. Продюсер здесь — консольная команда: `--reader-property parse.key=true` разбирает строки как `ключ:значение`, а `key.separator=:` задаёт разделитель.

### Schema Registry

Schema Registry — продукт Confluent, **не часть Apache Kafka**. Он хранит схемы сообщений и проверяет, что новая версия схемы совместима со старой. Так команда, меняющая формат заказа, не ломает чужих потребителей.

Режимы совместимости:

| Режим | Что значит на практике |
| --- | --- |
| `BACKWARD` (по умолчанию) | сначала обновляют потребителей, потом продюсеров |
| `FORWARD` | сначала обновляют продюсеров, потом потребителей |
| `FULL` | порядок обновления любой |
| `NONE` | совместимость не проверяется |

Есть ещё `BACKWARD_TRANSITIVE`, `FORWARD_TRANSITIVE` и `FULL_TRANSITIVE`: их здесь не разбираем.

Как запомнить: при `BACKWARD` новая схема читает данные по старой, поэтому потребитель с новой схемой справится со старыми записями — его можно выкатывать первым. При `FORWARD` старые потребители должны читать новые записи, поэтому первыми выкатывают продюсеров.

### Частые ошибки

- **Ошибка:** считать Streams отдельным кластером и просить для него серверы. **Верно:** это библиотека в вашем приложении, экземпляры запускаются как обычный сервис.
- **Ошибка:** считать Schema Registry частью Apache Kafka и искать его в дистрибутиве брокера. **Верно:** это продукт Confluent, его ставят отдельно.
- **Ошибка:** при режиме `FORWARD` начинать с потребителей. **Верно:** `FORWARD` — продюсеры первыми, `BACKWARD` — потребители первыми.
- **Ошибка:** включить `exactly_once_v2`, не проверив версию брокеров. **Верно:** значение по умолчанию — `at_least_once`, для `exactly_once_v2` нужны брокеры 2.5 и выше.

### Шпаргалка

- Connect: перенос «как есть» между Kafka и внешними системами; source — в Kafka, sink — из Kafka; режимы standalone и distributed.
- Streams: библиотека; KStream — поток, KTable — последнее значение по ключу; state store; окна и grace period.
- `processing.guarantee`: `at_least_once` по умолчанию, `exactly_once_v2` — брокеры 2.5+.
- Schema Registry — Confluent: `BACKWARD` (по умолчанию) — потребители первыми, `FORWARD` — продюсеры первыми, `FULL` — любой порядок.
