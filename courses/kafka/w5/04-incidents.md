# Инциденты: lag растёт, ребалансы, потерянные записи

Дежурному приходит оповещение: отставание группы растёт, платежи обрабатываются с задержкой. Или: потребители непрерывно перезаходят в группу, и ничего не двигается. Или: после падения брокера бухгалтерия не находит подтверждённых записей. В этом уроке вы разберёте три таких инцидента. В каждом дан сценарий, который нарушает условие, и описано, что наблюдается и что обещано бизнесом (SLA). Вы меняете настройки и состояние кластера так, чтобы условие выполнилось.

### Порядок разбора

1. Посмотрите на группу: `kafka-consumer-groups.sh --describe --group группа`. Столбцы `LAG` и `CONSUMER-ID` показывают, кто читает какую партицию и сколько осталось.
2. Посмотрите на состав группы и её состояние: флаги `--members` и `--state`.
3. Откройте журнал прогона. Выход из группы, повторные ребалансы и потеря подтверждённых записей видны в нём построчно.
4. Сформулируйте одну гипотезу, сделайте одну правку и проверьте, выполнились ли условия.

Таблица причин (механики из миров 2 и 3):

| Что видно | Вероятная причина | Где разобрано |
| --- | --- | --- |
| `LAG` растёт, все партиции у одного `CONSUMER-ID`, остальные экземпляры не в группе | не работают часть потребителей | урок 2.4 |
| `LAG` растёт, потребителей по числу партиций, все заняты | не хватает партиций или скорости обработки | урок 5.3 |
| `LAG` не уменьшается, в журнале повторяются выходы по `max.poll.interval.ms`, группа снова и снова в ребалансе | слишком большая пачка записей между вызовами `poll` | урок 2.4 |
| подтверждённые записи пропали после падения лидера | `acks=1` | урок 3.2 |

### Команды разбора

Пример. В топике `jobs` две партиции, в нём пять записей. Консольный потребитель группы `workers` прочитал три записи и завершился. Посмотрим на группу:

```broker example
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic jobs --partitions 2 --replication-factor 3
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic jobs --reader-property parse.key=true --reader-property key.separator=: <<EOF
a:job 1
b:job 2
c:job 3
d:job 4
e:job 5
EOF
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic jobs --group workers --from-beginning --max-messages 3
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group workers
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group workers --state
```

```text
Created topic jobs.
job 1
job 2
job 3
Processed a total of 3 messages
Consumer group 'workers' has no active members.
GROUP           TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG             CONSUMER-ID     HOST            CLIENT-ID
workers         jobs            0          3               4               1               -               -               -
workers         jobs            1          0               1               1               -               -               -
Consumer group 'workers' has no active members.
GROUP           COORDINATOR (ID)          ASSIGNMENT-STRATEGY STATE           #MEMBERS
workers         broker-3:9092 (3)         -                   Empty           0
```

Как читать:

- `CURRENT-OFFSET` — закоммиченный offset группы, `LOG-END-OFFSET` — конец журнала, `LAG` — разница между ними. В партиции 0 отстаёт одна запись, в партиции 1 тоже одна.
- `CONSUMER-ID` равен `-`, когда активных участников нет: сообщение «has no active members» говорит о том же.
- `--describe --group группа --members` печатает таблицу участников: `GROUP CONSUMER-ID HOST CLIENT-ID #PARTITIONS`. По ней видно, сколько экземпляров реально в группе и сколько партиций у каждого.
- `--state` показывает состояние группы: `Empty` — участников нет, `PreparingRebalance` — идёт ребаланс, `Stable` — работает. Число участников — в столбце `#MEMBERS`.

### Учебные команды и свойства

В заданиях сценарий уже идёт: у него есть продюсеры, потребители и сбои. Для работы с ним вам понадобятся три вещи.

**Время.** `sim run 10s` продвигает виртуальное время на 10 секунд. Сбои сценария, назначенные на момент `0`, срабатывают при первом продвижении времени. Поэтому, чтобы увидеть картину, сначала продвиньте время, а потом смотрите на группу.

**Потребители сценария.** `sim consumer start ID` запускает потребителя сценария: он входит в группу. `sim consumer stop ID` останавливает его. `ID` — имя участника из условия задания. Это учебные команды: настоящей Kafka они не соответствуют.

**Свойства.** Настройки продюсеров и потребителей сценария меняют строками `участник.ключ=значение` в блоке свойств. Участник — имя из условия, ключ — настройка клиента Kafka. Строки с `#` — комментарии. Примеры: `bank.acks=all`, `ship-1.max.poll.records=20`.

Пример сценария. Продюсер `notifier` пишет уведомления в топик из двух партиций. Два потребителя группы `senders` читают их. В середине прогона `sender-2` останавливают (блок `faults`) и снова запускают:

```scenario example
{
  "sim": "kafka",
  "seed": 1,
  "durationMs": 20000,
  "setup": "kafka-topics.sh --bootstrap-server localhost:9092 --create --topic notices --partitions 2 --replication-factor 3",
  "actors": [
    { "id": "notifier", "kind": "producer", "topic": "notices", "rate": 10, "count": 100, "message": { "key": "user-{n%6}", "body": "notice {n}" }, "config": {} },
    { "id": "sender-1", "kind": "consumer", "group": "senders", "topics": ["notices"], "processMs": 30, "config": { "auto.offset.reset": "earliest", "auto.commit.interval.ms": 500 } },
    { "id": "sender-2", "kind": "consumer", "group": "senders", "topics": ["notices"], "processMs": 30, "config": { "auto.offset.reset": "earliest", "auto.commit.interval.ms": 500 } }
  ],
  "faults": [
    { "at": 5000, "kind": "consumer.stop", "actor": "sender-2" },
    { "at": 8000, "kind": "consumer.start", "actor": "sender-2" }
  ],
  "expect": [ { "kind": "lagBelow", "group": "senders", "value": 30, "byMs": 15000 } ]
}
```

- `faults` — сбои по времени: `at` — миллисекунды от начала, `kind` — что произошло, `actor` — с кем. Бывают также `broker.crash` и `replica.stall` с номером брокера в поле `broker`;
- `auto.commit.interval.ms` сокращён, чтобы отставание на графике менялось быстро: по умолчанию оно 5000 мс (урок 3.4);
- условие в `expect`: после 15-й секунды отставание группы не больше 30.

### Потребителей меньше, чем нужно

Если часть экземпляров не запущена или выпала из группы, остальные получают их партиции и не успевают. Признак: в `--describe` все партиции у одного `CONSUMER-ID`, `LAG` растёт, а в `--members` участников меньше, чем должно быть. Исправление — вернуть экземпляры, то есть запустить недостающих. После этого группа ребалансируется и партиции делятся между всеми.

### Шторм ребалансов

Потребитель забирает из Kafka пачку записей вызовом `poll` и обрабатывает её. Если следующего `poll` нет дольше `max.poll.interval.ms` (по умолчанию 300000 мс), потребитель считается вышедшим: его исключают из группы и начинается ребаланс. Потребитель возвращается при следующем `poll`, снова получает большую пачку, снова не успевает — и так по кругу. Пока идёт ребаланс, группа обрабатывает записи хуже, а при eager-стратегии останавливаются все участники (урок 2.4).

Размер пачки ограничивает `max.poll.records` (по умолчанию 500). Условие здоровья:

```text
max.poll.records × время обработки одной записи < max.poll.interval.ms
```

Исправить можно двумя способами: уменьшить `max.poll.records` (меньше записей в пачке) или увеличить `max.poll.interval.ms` (больше времени на пачку). Первый обычно лучше: он не прячет медленную обработку. В сценарии интервал сокращён до 3000 мс, чтобы шторм проявился за секунды.

### Подтверждённые записи пропали

С `acks=1` продюсер получает подтверждение, как только запись попала в лог лидера. Реплики-подписчики ещё могут её не забрать. Если лидер падает именно сейчас, новый лидер этих записей не имеет, и подтверждённые записи теряются. С `acks=all` подтверждение приходит, когда запись видна всем репликам из ISR (урок 3.2), и потеря при падении лидера исключена, пока жива хотя бы одна реплика ISR. В журнале потеря записана строкой «была подтверждена, но новый лидер её не получил».

### Частые ошибки

- **Ошибка:** увеличить число партиций, когда причина — не запущенные потребители. **Верно:** сначала сравните число участников в `--members` с ожидаемым.
- **Ошибка:** поднимать `max.poll.interval.ms` до огромных значений, не уменьшив пачку. **Верно:** сначала `max.poll.records` по условию здоровья.
- **Ошибка:** поправить настройку у одного потребителя из нескольких. **Верно:** свойства задают для каждого потребителя группы, иначе второй продолжит вылетать.
- **Ошибка:** лечить потерю записей настройкой потребителя. **Верно:** потеря возникает на стороне продюсера и брокера: `acks` и `min.insync.replicas`.

### Шпаргалка

- Порядок: `--describe --group`, `--members`, `--state`, журнал; одна гипотеза, одна правка.
- `sim run 10s` — время; `sim consumer start|stop ID` — запуск и остановка потребителя сценария.
- Свойства: `участник.ключ=значение`, например `bank.acks=all`.
- `max.poll.records × время записи < max.poll.interval.ms`.
- `acks=1` теряет подтверждённые записи при падении лидера; `acks=all` — нет.

Сервис `checkout` пишет платежи в топик `payments` из трёх партиций по 30 записей в секунду. Группу `billing` читают три экземпляра `pay-1`, `pay-2` и `pay-3`, каждый обрабатывает около 16 записей в секунду. После выкладки два экземпляра не поднялись. sim run 5s
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing
sim consumer start pay-2
sim consumer start pay-3
```

bank.acks=…
```
