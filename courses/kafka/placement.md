## task kfk-pl-acks

```json
{
  "type": "choice",
  "title": "Запись, которая не должна потеряться",
  "hints": ["Нужно, чтобы подтверждение приходило после того, как запись получили реплики из ISR."],
  "options": [
    "`acks=0`: производитель не ждёт ответа и работает быстрее всего",
    "`acks=1`: подтверждает лидер сразу после своей записи",
    "`acks=all` и `min.insync.replicas=2` при трёх репликах",
    "`acks=all` и `min.insync.replicas=1` при трёх репликах"
  ],
  "answer": [2],
  "explanation": "При `acks=all` подтверждение приходит, когда запись есть у всех реплик из ISR. Но если `min.insync.replicas=1`, ISR может сократиться до одного лидера, и запись будет только у него. Значение `2` гарантирует, что подтверждённая запись лежит минимум на двух репликах. Для `acks=0` и `acks=1` потеря при падении лидера возможна."
}
```

Топик с тремя репликами хранит платежи. Какие настройки лучше защищают подтверждённую запись от потери при падении брокера?

## task kfk-pl-commit

```json
{
  "type": "choice",
  "title": "Когда фиксировать offset",
  "hints": ["Что произойдёт, если потребитель упадёт между обработкой и коммитом?"],
  "options": [
    "До обработки: записи не потеряются никогда",
    "После обработки: при падении запись обработают повторно, но не потеряют (минимум одна доставка)",
    "Коммит offset не влияет на повторное чтение",
    "Только перед началом чтения всего топика"
  ],
  "answer": [1],
  "explanation": "Если закоммитить offset после обработки, то при падении между этими шагами потребитель вернётся к последнему закоммиченному offset и обработает запись ещё раз. Это даёт «как минимум один раз», и обработчик должен выдерживать повторы. Если закоммитить до обработки, при падении запись может быть потеряна: потребитель продолжит уже после неё."
}
```

Потребитель читает запись, обрабатывает её и коммитит offset. В каком порядке выбрать эти шаги, чтобы запись не терялась при падении?
