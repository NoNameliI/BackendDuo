# Задача и событие: одно дело, два брокера

После оплаты заказа происходят два разных дела. Рассылка должна отправить покупателю письмо с чеком: это поручение, его делает один работник, и оно выполняется один раз. Аналитика должна учесть оплату в отчёте: это факт, и он нужен ещё нескольким службам, каждой в своём темпе. В этом уроке мы решим оба дела в RabbitMQ и в Kafka и увидим, чем механизмы отличаются.

Если вы прошли только один курс, ничего страшного: ниже каждый механизм напомнен, а подробности есть в указанных уроках.

### Задача и событие

- **Задача** — «сделай это». Её должен выполнить кто-то один из группы работников. Выполненная задача больше не нужна.
- **Событие** — «это произошло». Его читают все, кому оно интересно, каждый независимо. Событие остаётся фактом и после чтения.

Один поток сообщений часто совмещает обе роли: сообщение «заказ оплачен» для рассылки чеков — задача, а для аналитики — событие. Поэтому важно, что именно делает брокер при двух вещах: как размножает сообщение для нескольких служб и как делит работу между несколькими работниками одной службы.

### RabbitMQ: копии через привязки, работа через потребителей

Напомним по курсу RabbitMQ (уроки 1.2 и 2.1). Издатель пишет в `exchange`. Привязка связывает `exchange` с очередью и задаёт ключ. Каждая очередь, у которой подошла привязка, получает свою копию сообщения. Это и есть размножение: чтобы второй службе досталась копия, ей нужна своя очередь с привязкой.

Несколько потребителей одной очереди работают как бригада: каждое сообщение достаётся одному из них (урок 3.2). Это и есть раздача работы.

Шаблон привязки очереди к `exchange`:

```text
rabbitmqadmin bindings declare --source EXCHANGE --destination-type queue --destination ОЧЕРЕДЬ --routing-key КЛЮЧ
```

- `--source` — имя `exchange`, откуда идут сообщения.
- `--destination-type queue` — получатель привязки очередь (получателем может быть и другой `exchange`, это нам не нужно).
- `--destination` — имя очереди.
- `--routing-key` — ключ привязки. У `direct`-exchange ключ сообщения должен совпасть с ним точно, у `fanout` ключ игнорируется.

Пример. Счета публикуются в `fanout`-exchange. Книга учёта и отчёты читают одни и те же счета, у каждой службы своя очередь. Команды выполняются по порядку, как набранные руками. Команда `rabbitmqadmin publish message` публикует сообщение, `rabbitmqadmin get messages --queue ОЧЕРЕДЬ --count N` читает до `N` сообщений из очереди и подтверждает их.

```broker example
rabbitmqadmin exchanges declare --name invoices-feed --type fanout --durable true
rabbitmqadmin queues declare --name ledger --type classic --durable true
rabbitmqadmin queues declare --name reports --type classic --durable true
rabbitmqadmin bindings declare --source invoices-feed --destination-type queue --destination ledger --routing-key ""
rabbitmqadmin bindings declare --source invoices-feed --destination-type queue --destination reports --routing-key ""
rabbitmqadmin publish message --exchange invoices-feed --payload "invoice 501"
rabbitmqadmin publish message --exchange invoices-feed --payload "invoice 502"
rabbitmqadmin get messages --queue ledger --count 2
rabbitmqadmin get messages --queue reports --count 2
```

Обе очереди получили оба счёта, у каждой службы своя копия. Таблицы, которые печатает консоль, содержат и другие столбцы, нас здесь интересует только тело сообщения: `invoice 501` и `invoice 502` в обеих очередях.

Если вторую очередь не привязать, служба не получит ничего: `exchange` не знает о ней. И ещё одно следствие: очередь, привязанная позже, получает только сообщения, опубликованные после привязки. Прошлое она не увидит.

### Kafka: копии через группы, работа через разделы

Напомним по курсу Kafka (уроки 1.3 и 2.3). Продюсер пишет запись в раздел топика. Читатели объединяются в группы (`group`). Каждая группа получает все записи топика и хранит свою позицию. Чтобы вторая служба получила копию, ничего настраивать на брокере не нужно: достаточно, чтобы её читатели работали под другим именем группы.

Раздача работы устроена по-другому. Внутри одной группы разделы топика делятся между читателями, и у раздела в каждый момент один читатель группы. Значит, число работников группы, которые реально работают, не больше числа разделов. Топик из одного раздела обслужит только одного работника группы: остальные простаивают.

Число разделов можно только увеличить:

```text
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic ТОПИК --partitions N
```

- `--alter` — изменить существующий топик.
- `--topic ТОПИК` — какой топик.
- `--partitions N` — новое число разделов. Оно должно быть больше текущего: уменьшить разделы нельзя.

Увеличение числа разделов меняет соответствие «ключ — раздел», потому что раздел считается как остаток от деления хеша ключа на число разделов (курс Kafka, урок 2.1). Для рабочей очереди без требований к порядку это не страшно. Для событий, у которых порядок важен, это ловушка (урок 1.3).

### Сценарии лаборатории

Поведение системы во времени описывает сценарий: JSON с брокером (`sim`), начальными командами (`setup`), участниками (`actors`) и условиями успеха (`expect`). В заданиях вы не пишете JSON. Команды вводите в консоли лаборатории, а свойства участников правите в окне свойств строками `участник.настройка=значение`. Сначала выполняется `setup` сценария, потом ваши команды, потом сценарий идёт до конца.

У участника-издателя (`producer`) в Rabbit заданы `exchange` и `routingKey`, в Kafka — `topic` и `key`. Потребитель Rabbit читает очередь (`queue`), потребитель Kafka — `topics` под именем `group`. Поле `processMs` — сколько миллисекунд занимает обработка одного сообщения. Условие `processedAtLeast` требует, чтобы участник обработал не меньше `count` сообщений к моменту `byMs`.

Пример на Kafka. Рассылка параллельно обрабатывает посылки двумя работниками одной группы `couriers`, а аналитика независимо читает всё в своей группе. Топик сначала создаётся с одним разделом и тут же увеличивается до двух (команда `--alter` из шаблона выше), и поэтому оба работника получают работу.

```scenario example
{
  "sim": "kafka",
  "seed": 1,
  "durationMs": 12000,
  "setup": "kafka-topics.sh --bootstrap-server localhost:9092 --create --topic parcels --partitions 1 --replication-factor 1\nkafka-topics.sh --bootstrap-server localhost:9092 --alter --topic parcels --partitions 2",
  "actors": [
    { "id": "depot", "kind": "producer", "topic": "parcels", "rate": 20, "count": 12, "message": { "body": "parcel {n}", "key": "parcel-{n}" }, "config": {} },
    { "id": "courier-1", "kind": "consumer", "group": "couriers", "topics": ["parcels"], "processMs": 400, "config": { "auto.offset.reset": "earliest" } },
    { "id": "courier-2", "kind": "consumer", "group": "couriers", "topics": ["parcels"], "processMs": 400, "config": { "auto.offset.reset": "earliest" } },
    { "id": "report", "kind": "consumer", "group": "reports", "topics": ["parcels"], "processMs": 20, "config": { "auto.offset.reset": "earliest" } }
  ],
  "faults": [],
  "expect": [
    { "kind": "processedAtLeast", "actor": "courier-1", "count": 2, "byMs": 12000 },
    { "kind": "processedAtLeast", "actor": "courier-2", "count": 2, "byMs": 12000 },
    { "kind": "processedAtLeast", "actor": "report", "count": 12, "byMs": 12000 }
  ]
}
```

Работники одной группы разделили записи между собой, а группа `reports` прочитала все двенадцать. Начальное значение `auto.offset.reset=earliest` нужно, чтобы новая группа читала с начала журнала, иначе она увидела бы только записи, появившиеся после подключения (курс Kafka, урок 1.3).

### Сравнение на одном деле

| Что нужно | RabbitMQ | Kafka |
| --- | --- | --- |
| Копия второй службе | очередь и привязка на каждую службу | отдельная группа читателей |
| Работники одной службы делят работу | потребители одной очереди | читатели одной группы, по разделам |
| Предел параллелизма | число потребителей очереди | число разделов топика |
| Читатель, подключённый позже | видит только то, что опубликовано после привязки очереди | при `earliest` читает с начала журнала, пока записи не удалены |

### Частые ошибки

- **Ошибка:** повесить две службы на одну очередь, чтобы каждая получила все сообщения. **Верно:** они поделят сообщения между собой. Каждой службе нужна своя очередь и своя привязка.
- **Ошибка:** создать очередь, но забыть привязать её к `exchange`. **Верно:** без привязки копия в очередь не попадёт.
- **Ошибка:** запустить в группе Kafka больше работников, чем разделов, и ждать ускорения. **Верно:** лишние работники простаивают, число разделов нужно увеличить.
- **Ошибка:** ждать от второй группы Kafka «сообщений с момента, когда она появилась» по умолчанию. **Верно:** по умолчанию `auto.offset.reset=latest`: новая группа читает только то, что записано после подключения. Для истории ставят `earliest`.

### Шпаргалка

- Задача: один работник из группы, после выполнения не нужна. Событие: читают все заинтересованные, независимо.
- RabbitMQ: `rabbitmqadmin bindings declare --source E --destination-type queue --destination Q --routing-key K`. Копия на очередь, работа между потребителями одной очереди.
- Kafka: копия на группу, работа между читателями группы по разделам. `kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic T --partitions N` только увеличивает.
- Новая группа Kafka: `auto.offset.reset` `latest` (по умолчанию) или `earliest`.
- Свойства сценария: `участник.настройка=значение`.

## task brk-paid-rabbit

```json
{
  "type": "scenario",
  "title": "RabbitMQ: аналитика не получает оплаты",
  "xp": 20,
  "sim": "rabbit",
  "scenario": "brk-paid-rabbit",
  "hints": [
    "Раздел «RabbitMQ: копии через привязки, работа через потребителей».",
    "Очередь `analytics` существует, но `exchange` о ней не знает. Нужна привязка.",
    "Шаблон: `rabbitmqadmin bindings declare --source … --destination-type queue --destination … --routing-key …`."
  ],
  "check": {}
}
```

Магазин (`shop`) публикует шесть сообщений `order 1 paid` … `order 6 paid` в `exchange` `paid` типа `direct` с ключом `paid`. Рассылка (`mailer`) читает очередь `receipts`, она привязана и получает все шесть. Аналитика (`stats`) читает очередь `analytics`: она создана, но ничего не получает.

Сделайте так, чтобы к 4000-й миллисекунде обе службы обработали все шесть сообщений. Править нужно только топологию командой в консоли.

```broker starter
# привяжите очередь analytics к exchange paid
```

```broker solution
rabbitmqadmin bindings declare --source paid --destination-type queue --destination analytics --routing-key paid
```

## task brk-paid-kafka

```json
{
  "type": "scenario",
  "title": "Kafka: второй работник простаивает",
  "xp": 20,
  "sim": "kafka",
  "scenario": "brk-paid-kafka",
  "hints": [
    "Раздел «Kafka: копии через группы, работа через разделы».",
    "Два работника одной группы делят разделы топика. Разделов сейчас один.",
    "Шаблон: `kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic … --partitions …`."
  ],
  "check": {}
}
```

Магазин (`shop`) пишет в топик `paid` двенадцать записей с ключами `order-1` … `order-12`. Два работника рассылки, `mailer-1` и `mailer-2`, входят в одну группу `mailers`. Группа `analytics` читает топик независимо и уже получает все записи. Топик создан с одним разделом, поэтому `mailer-2` не получает ни одной записи.

Сделайте так, чтобы каждый из работников рассылки обработал не меньше трёх записей. Править нужно только топик командой в консоли.

```broker starter
# увеличьте число разделов топика paid
```

```broker solution
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic paid --partitions 2
```
