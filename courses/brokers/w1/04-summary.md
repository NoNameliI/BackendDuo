# Сводная таблица: RabbitMQ и Kafka

Команда разбирает три потока данных: платежи, статусы посылок и письма-чеки. Для каждого нужно за пять минут решить, какой брокер подходит и почему. Для этого удобна одна таблица с ответами на вопросы из урока 1.1. В этом уроке мы соберём её, добавим то, чего песочница не выполняет, и потренируемся читать чужие решения критически.

### Сводная таблица

| Вопрос | RabbitMQ (очередь) | Kafka (журнал) |
| --- | --- | --- |
| Как устроено | `exchange`, привязки, очереди, потребители | топик из разделов, группы читателей |
| Что после обработки | подтверждённое сообщение повторно не доставляется | запись остаётся до конца срока хранения, по умолчанию семь дней |
| Копия второй службе | своя очередь и привязка | своя группа читателей |
| Работники одной службы | потребители одной очереди делят сообщения | читатели одной группы делят разделы |
| Предел параллелизма | число потребителей очереди | число разделов |
| Порядок | в очереди по поступлению; нарушают несколько потребителей, возврат, приоритеты | внутри раздела; ключ сущности даёт один раздел |
| Перечитывание | у классической очереди нет; есть тип `stream` | сдвиг позиции группы или новая группа с `earliest` |
| Маршрутизация | `direct`, `fanout`, `topic`, `headers`, `alternate exchange` | топик и ключ записи; раздел выбирается по хешу ключа |
| Свойства сообщения | TTL, приоритет, «мёртвая» очередь, повтор с задержкой | срок и размер хранения, compaction (последнее значение на ключ) |
| Надёжность | `ack`, `durable` и `persistent`, publisher confirms, quorum-очереди | `acks=all`, `min.insync.replicas`, репликация, идемпотентный продюсер |
| Дубликаты | возможны при повторной доставке: нужен идемпотентный потребитель | возможны при коммите после обработки: нужен идемпотентный потребитель |

Где разобрано: RabbitMQ — маршрутизация в уроках 2.1–2.2, подтверждения в 3.1, надёжность в 3.3–3.4, TTL и «мёртвые» очереди в 4.1, приоритеты в 4.3, `stream` в 4.4. Kafka — журнал и позиции в 1.3, ключи и порядок в 2.1–2.2, группы в 2.3, надёжность и семантики доставки в 3.2–3.4, хранение в 4.1–4.2.

### Что песочница не выполняет

Песочницы этого и двух других курсов упрощены. Знайте, где проходит граница, чтобы не принять упрощение за свойство системы.

- RabbitMQ: тип очереди `stream` не выполняется (только по документации); репликация между узлами, выборы лидера и поведение при потере кворума не воспроизводятся.
- Kafka: не выполняются транзакции и режим `read_committed`, сжатие записей, новый протокол групп (KIP-848), Kafka Connect, Kafka Streams, реестр схем, внутреннее устройство кворума KRaft. Это материал для теории и заданий с выбором ответа.

### Как пользоваться таблицей

1. Для каждого потока ответьте на вопросы урока 1.1: работа или факт, нужна ли история, сколько читателей, какой порядок, какая маршрутизация.
2. Найдите строки таблицы, которые для вашего потока критичны.
3. Если критичные строки лежат по обе стороны, разделите поток: письма через очередь, события оплаты в журнал.
4. Проверьте решение на частые ошибки из следующего урока.

Пример разбора. Письма-чеки: поручение, история не нужна, читает один из работников. Строки «что после обработки» и «работники одной службы» ведут к очереди. События оплаты: факт, нужен независимый читатель-аналитик и перечитывание. Строки «копия второй службе» и «перечитывание» ведут к журналу. Статусы посылок: порядок по посылке. Строка «порядок» ведёт к ключу посылки в Kafka либо к одному потребителю на очередь в RabbitMQ.

### Частые ошибки

- **Ошибка:** считать, что Kafka «лучше», потому что хранит данные. **Верно:** хранение нужно не всем задачам. Поручение, которое выполняется один раз, естественно решает очередь.
- **Ошибка:** считать, что RabbitMQ «проще», и класть в очередь поток, который придётся перечитывать. **Верно:** подтверждённое сообщение классическая очередь не вернёт.
- **Ошибка:** сравнивать системы по одной строке таблицы. **Верно:** смотрите на все критичные для потока строки сразу.
- **Ошибка:** принимать поведение песочницы за полное описание продукта. **Верно:** границы указаны выше и в уроках курсов.

### Шпаргалка

- Очередь: поручение, один работник из бригады, после `ack` сообщение не возвращается, богатая маршрутизация и свойства сообщений.
- Журнал: факт для многих читателей, история, порядок по ключу в разделе, перечитывание.
- Параллелизм: потребители очереди в RabbitMQ, разделы в Kafka.
- Дубликаты возможны в обеих системах: потребитель должен быть идемпотентным.
- Если требования с обеих сторон, разделите поток.
